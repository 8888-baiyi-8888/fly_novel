# Fly Novel 项目背景与核心设计理念

## 一、项目定位

**项目名称：Fly Novel**

Fly Novel 是一个基于 LLM、Multi-Agent 和 Agent Harness 构建的长篇小说智能创作系统。

目标是支持超过 1000 章的长篇小说创作，能够维持长期的世界状态、角色成长、故事线演化和事件因果关系。

但项目的核心目标并不是简单地将小说创作拆分成多个步骤，然后让 LLM 依次生成大纲、章节和正文。

**我们希望构建的是一个能够持续演化的虚拟小说世界。**

在这个世界中：

- 世界具有自身的设定、规则、历史与运行状态。
- 角色拥有独立的身份、性格、目标、经历与记忆。
- 角色能够基于自身认知和当前环境自主决策。
- 不同角色的行为可以相互影响，推动事件发展。
- 多条故事线可以独立演化、相互交织、分支与合流。
- 事件具有因果关系，并能够不断衍生子事件。
- 导演 Agent 负责在适当层级进行引导与裁决，而不是决定角色的每个行为。
- 写作 Agent 将世界中发生的故事转化为文学作品。
- 人类创作者可以持续参与设定、讨论、修改和干预。

**小说是这个世界演化后形成的叙事结果，而不应该成为世界中所有角色和事件的唯一驱动力。**

---

## 二、核心设计思想

### 2.1 世界驱动，而非章节驱动

传统 AI 小说生成通常采用：

用户需求 → 小说大纲 → 分卷大纲 → 章节大纲 → 正文生成

这个方式容易出现以下问题：

1. 角色只是为了完成大纲而行动。
2. 故事发展受到预先设定内容的过度限制。
3. 角色缺乏独立性，无法产生真正有价值的意外发展。
4. 世界只是主角的背景板，其他角色和事件缺乏自主性。
5. 长篇小说中，前后事件和人物行为容易产生矛盾。

Fly Novel 希望采用另一种思路：

**世界初始化 → 世界持续运行 → 角色自主行为 → 事件演化 → 故事形成 → 文学化表达**

这里并不是完全取消规划，而是改变规划的定位。

规划提供目标、方向、约束和阶段性期待，但不应完全决定故事发展的每一个细节。

### 2.2 角色不是剧情工具

角色应该具有：

- 自己的性格与价值观。
- 自己的目标与动机。
- 自己掌握的信息及认知局限。
- 自己的历史经历与记忆。
- 自己与其他角色的关系。
- 可以随故事推进而改变的状态。

不同角色即使面对同一个事件，也可能做出不同决策。

角色 Agent 的任务不是机械执行导演安排的剧情，而是基于角色自身设定与当前世界状态进行合理行动。

角色应当具有一定自主性，但仍受世界规则、已发生事实和角色认知约束。

### 2.3 世界不应该围绕主角运转

即使主角没有参与，世界中的其他角色、组织、势力和事件也可以继续发展。

例如：

某个宗门内部发生权力斗争。

主角可能完全不知道这件事，但相关角色依然可以采取行动，最终导致宗门局势发生变化。

若主角日后进入这个宗门，面对的应该是已经变化的世界，而不是为主角临时生成的背景。

因此，需要区分：

- **世界中实际发生了什么。**
- **某个角色知道什么。**
- **最终小说向读者展示了什么。**

这三个层次不能完全混为一谈。

### 2.4 人与 AI 共同创作

人类创作者不是单纯提交一个需求，然后等待系统生成整本小说。

尤其在世界初始化阶段：

- AI 可以提出角色和世界设定的初稿。
- 人类可以与 AI 反复讨论。
- 可以修改、替换、增加或删除某些设定。
- 可以要求 AI 发现不同设定之间的冲突。
- 多轮讨论完成后，再将内容融合成一致的正式设定。

一个精彩角色往往依赖独特的背景、人格或经历。

这些独特性既可能来自 AI，也可能来自人类创作者的灵感。

因此，**系统需要保留人机协作空间，不应过早将所有内容固定成不可修改的结构。**

## 三、整体工作流

目前将系统分为两个主要层级：

### 3.1 世界初始化工作流（World Initialization Workflow）

**核心目标：建立一个具备持续演化基础的虚拟小说世界。**

世界初始化工作流负责将人类创作者的初始构想，转化为具有基本规则、角色、组织、关系、矛盾和初始状态的世界。

它不是提前完成整本小说的剧情规划，而是建立世界开始运行所需的初始条件。

主要职责：

1. **创作意图理解**：理解用户希望创造的世界、题材、风格与核心构想。
2. **世界基础设定**：建立世界观、历史背景、地理环境和运行规则。
3. **角色初始化**：创建关键角色，确定身份、性格、动机、目标和初始状态。
4. **势力与关系初始化**：建立组织、势力、人物关系及其利益冲突。
5. **故事线初始化**：创建必要的长期故事线和阶段性故事线，作为后续发展的参考方向。
6. **初始事件构建**：设置世界当前存在的重要矛盾、正在发生的事件和潜在冲突。
7. **人机协同优化**：允许用户与 Agent 对各项设定进行多轮讨论、修改和完善。
8. **全局一致性检查**：检查世界规则、角色关系、历史背景及初始状态之间的逻辑冲突。
9. **世界状态初始化**：整合经过确认的设定，形成可供故事级工作流使用的初始世界状态。

**设计原则：**

- 初始化的是世界，而不是整本小说的完整剧情。
- 不要求预先确定全部角色、事件和故事线。
- 角色、势力和事件可以在后续世界演化中自然出现。
- 初始故事线是发展方向，而不是必须执行的剧情脚本。
- 人类创作者可以参与各项设定的讨论和优化。
- 初始化完成意味着世界具备运行条件，不意味着世界设定永远不可修改。

最终输出应是一个**可持续运行、可演化、可扩展的世界初始状态**，为后续故事级工作流提供基础。

### 3.2 故事级工作流（Story Workflow）

原先曾称为“章节级工作流”，后续明确倾向于更名为**故事级工作流**。

原因是小说世界的发展单位不应该始终是章节。

章节只是最终文学作品的组织单位，并不一定等于故事发展的自然单位。

故事级工作流的任务是：

**基于当前世界状态，推动一个故事事件或一组关联事件自然发展。**

主要过程可能包含：

1. 获取当前世界状态、相关事件、角色与故事线。
2. 确定当前需要推动的父事件或阶段目标。
3. 识别相关角色及其所掌握的信息。
4. 让角色 Agent 根据自身目标、记忆与环境自主行动。
5. 根据角色行动产生互动、冲突和结果。
6. 由导演 Agent 对必要的内容进行协调、判断或裁决。
7. 更新事件状态、角色状态和世界状态。
8. 判断是否产生新的子事件。
9. 评估相关故事线是否得到推进。
10. 将适合呈现的故事内容交给写作 Agent 进行文学化表达。

上述步骤是概念性职责，不代表必须实现成固定的十节点流水线。

某些行动可能需要多轮互动，某些事件可能需要调用工具、检索资料或创建子任务。

**故事工作流应给 Agent 留出足够的自主空间，而不是用大量结构化节点提前规定每一次决策。**

### 3.3 世界初始化、世界演化和小说叙事的关系

从系统职责来看，可以进一步区分三个概念。

**世界初始化**

负责建立虚拟世界的初始条件。

**世界演化**

负责随着角色行为、事件变化及外部因素影响，持续更新世界状态。

故事级工作流是推动世界演化的重要业务机制。

**小说叙事**

负责从世界中发生的事件中选择、组织和表达故事，形成最终作品。

这三个概念不意味着必须分别实现三个独立工作流。

尤其是世界演化，目前更适合作为系统级业务概念，而不是立即创建新的工作流模块。

## 四、事件系统

### 4.1 采用父子事件关系

我们之前讨论过的事件层级包括：

卷 → 小说级事 → 事件 → 章节 → 场景

但后续发现，“大事件”和“小事件”的分类容易让事件模型过于僵硬。

因此，现在更倾向于采用**父子事件模型**。

例如：

父事件：宗门继承权争夺

子事件：

- 大长老秘密联合其他长老。
- 少宗主寻找外部盟友。
- 宗门试炼期间发生暗杀。
- 关键人物发现被隐藏的证据。

其中的子事件可以继续衍生更细的子事件。

事件可以递归展开，而不是必须严格匹配某个预先规定的事件级别。

### 4.2 父事件负责目标，子事件负责演化

父事件可以包含：

- 事件背景。
- 重要参与者。
- 整体发展目标。
- 当前状态。
- 必要约束。
- 完成或结束条件。

子事件则反映父事件推进过程中实际发生的事情。

**父事件定义较高层级的方向，子事件通过角色行动不断演化。**

不应该要求导演提前写好所有子事件，然后强制角色执行。

### 4.3 事件和章节分离

事件不等于章节。

一个事件可能横跨多个章节。

一个章节也可能同时展示多个事件。

一个事件可能从不同角色的视角进行描述。

因此，事件系统负责记录世界实际发生的事情，而章节系统负责选择和组织最终呈现给读者的内容。

### 4.4 事件因果关系

事件之间除了父子结构，还需要考虑因果关系。

例如：

某角色得到秘密情报 → 向敌对势力泄露 → 导致宗门行动失败 → 触发内部调查。

父子关系描述事件如何组织和展开。

因果关系描述事件为什么发生，以及一个事件如何影响另一个事件。

两者不应简单混为一谈。

具体存储结构、关联方式与状态更新机制需要在事件系统开发阶段单独讨论。

## 五、故事线系统

### 5.1 故事线分类

目前讨论形成的分类是：

**长期故事线**

- 重要角色的长期性格成长线。
- 核心故事长期发展线。

**阶段性故事线**

- 角色的阶段性性格成长线。
- 核心故事的阶段性发展线。

长期故事线用于提供较长时间跨度的发展方向。

阶段性故事线用于描述某一时期内正在发生的变化或需要解决的核心矛盾。

### 5.2 故事线与事件的关系

故事线不是事件本身，而是用于描述故事长期或阶段性发展的方向。

一个事件可以推进多条故事线。

一条故事线可以由多个事件共同推动。

例如：

事件：主角在宗门试炼中遭到好友背叛。

可能同时推进：

- 主角的性格成长线。
- 主角与好友的关系变化。
- 宗门内部的权力斗争线。
- 某个反派势力的长期计划。

因此，需要建立 Event 与 Storyline 之间的关联。

### 5.3 故事线评估

事件结束或阶段推进后，应当能够判断：

- 哪些故事线被推进了。
- 哪些角色产生了变化。
- 当前阶段的目标是否发生变化。
- 是否产生新的故事线。
- 某条故事线是否需要分支、合流、暂停或结束。

但这些不意味着每个事件必须推动指定故事线。

**故事线提供叙事连续性，不应该成为限制世界自然发展的硬性任务清单。**

## 六、多 Agent 体系

### 6.1 角色 Agent（Character Agent）

角色 Agent 负责模拟具体角色。

其核心输入可能包括：

- 角色设定。
- 角色当前状态。
- 角色记忆。
- 当前场景和事件。
- 角色能够感知或得知的信息。
- 当前目标与动机。

输出主要是角色的决策、行动、对话或其他反应。

角色 Agent 不应直接获得所有世界真相。

需要区分全局世界信息与角色个人认知。

角色需要具备跨事件、跨章节的持续性，而不是每次都创建一个完全失去历史的新角色。

### 6.2 导演 Agent（Director Agent）

导演不是全知全能、直接编排所有角色行为的脚本控制器。

导演主要负责在当前事件层级内：

- 关注父事件的发展目标。
- 协调必要的角色和事件。
- 判断世界规则及事件约束。
- 处理需要裁决的冲突。
- 在必要时引入合理的变化。
- 维护事件发展的合理性与连续性。

**导演的控制范围是相对当前父事件而言的。**

在当前父事件下，导演关注整体方向，而角色 Agent 可以自主推动具体子事件。

当某个子事件本身需要进一步展开时，也可以在该事件层级继续进行导演协调。

这种方式可以支持递归事件演化。

### 6.3 写作 Agent（Writer Agent）

写作 Agent 负责将故事发展结果转化成小说正文。

它主要处理：

- 文学表达。
- 叙事节奏。
- 场景描写。
- 对话呈现。
- 视角切换。
- 风格一致性。
- 情绪渲染。

写作 Agent 不应该随意修改已经确定的世界事实。

如果写作过程中发现事实不足或逻辑冲突，应当通过相应机制反馈，而不是直接编造新的关键设定。

### 6.4 其他 Agent

世界设定、角色创建、事件规划、剧情评审、设定冲突检查等能力，可以根据实际需要设计为独立 Agent。

但是不应该为了追求多 Agent 数量而机械拆分。

**只有确实需要自主推理、工具使用、持续状态或独立职责时，才应考虑使用 Agent。**

简单、确定性的任务可以直接使用普通函数或其他程序组件。

## 七、记忆、知识与世界状态

长篇小说需要解决跨越数百甚至上千章节的信息一致性问题。

这里至少要区分三种概念。

### 7.1 世界知识

主要保存相对明确的设定和事实，例如：

- 世界规则。
- 地理与势力信息。
- 角色基础资料。
- 组织关系。
- 已确认的历史。
- 世界事件记录。

这些信息应当能够被检索和引用。

### 7.2 世界状态

表示世界当前正在发生什么，例如：

- 某个角色当前位置。
- 某个角色当前目标。
- 组织关系变化。
- 某个事件的进行状态。
- 某条故事线的最新进展。

世界状态需要随着事件发展而更新。

### 7.3 Agent 记忆

记忆用于帮助 Agent 保持跨时间的行为连续性。

之前讨论过角色记忆的三个层次：

- **L1：** 原始输入、输出和反应记录。
- **L2：** 较远历史的信息与事件摘要。
- **L3：** 通过关键词、条件或相关性触发的摘要。

记忆不应简单等于把所有历史聊天记录反复塞入模型上下文。

角色记忆应与世界客观事实区分。

例如，一个角色可能错误地相信某人已经死亡，但世界记录中此人实际上还活着。

角色的判断应当基于自己的认知，而不是直接读取全局真相。

L1/L2/L3 是此前讨论和探索的方向，不代表所有层级均已完整实现。

### 7.4 世界事实与角色认知的隔离

对于需要自主行为的角色 Agent，不能直接把世界完整状态作为其可见信息。

应该由业务层依据角色身份、位置、经历、已知事实和当前事件，确定角色可以访问哪些信息。

这样才能产生合理的信息不对称、误解、隐瞒与冲突。

角色的记忆和认知可以存在错误，但已经确认的世界事实不应因此被直接修改。

## 八、Agent Harness 技术架构

### 8.1 总体方向

项目使用 TypeScript / Node.js 技术栈。

Agent 基础能力参考 DeepSeek Harness 的工程思想，并采用 Cordis 插件机制进行能力装配。

希望实现一个可复用的 Agent Harness，而不是让小说业务直接依赖某个固定 Agent 框架。

基础模块可能包括：

- Agent Factory / Agent Manager
- Preset / Plugin Registry
- Agent Loop
- Session
- SystemPrompt
- LLM Runtime
- Tool Runtime
- Memory
- Context 管理

具体 Agent 通过 Preset 或配置组合所需插件。

不同 Agent 可以拥有不同的模型、工具、提示词、记忆策略和执行能力。

### 8.2 插件化原则

底层 Harness 不应该直接了解小说中的角色、导演或故事线等具体业务概念。

小说业务应当建立在 Harness 提供的通用能力之上。

例如：

Character Agent 使用当前 Agent 实例所装配的 Session、Memory、SystemPrompt、LLM 和 Tools。

Agent Loop 只通过能力接口调用这些服务，不应该硬编码具体使用哪个记忆插件。

### 8.3 Agent Manager

Agent Manager 负责管理 Agent 实例的生命周期。

此前讨论过的职责包括：

- 通过 Agent Factory 创建 Agent。
- 根据 Agent ID 管理实例。
- 防止重复 ID 创建冲突。
- 处理初始化期间的并发创建。
- 获取已创建的 Agent。
- 统一释放和清理 Agent 资源。

具体接口应以当前仓库实现为准。

### 8.4 Session

Session 负责保存与管理 Agent 的会话历史及运行记录。

之前讨论过消息类型：

- system/message
- developer/message
- user/message
- assistant/message
- tool/result

对于小说中多个角色之间的互动，需要区分：

- 模型协议里的消息角色。
- 小说业务里的实际说话人或参与者。

不要直接使用小说角色名称替代底层模型消息的 `user` / `assistant` 等协议角色。

可以在业务层维护 senderId、recipientId、characterId 等信息，再将其转换成模型能够理解的消息结构。

另外，应区分：

- 会话消息。
- 工具执行记录。
- Agent 运行事件。

并不是所有运行事件都应该直接转换成发送给 LLM 的消息。

### 8.5 SystemPrompt

SystemPrompt 负责组装 Agent 所需的系统提示词。

不同 Agent 可以具有不同的提示词内容。

例如：

- 角色 Agent 需要角色身份、性格、行为规则。
- 导演 Agent 需要事件目标和裁决职责。
- 写作 Agent 需要写作风格和叙事要求。

SystemPrompt 应支持通用能力与业务特定内容的组合。

此前也讨论过通过插件注册提示词段落、变量提供者等方式扩展功能。

### 8.6 Agent Loop

Agent Loop 是 Harness 的执行协调层。

其职责不是只调用一次 LLM，而是管理一次完整的 Agent Turn。

一个 Agent Turn 可能包含：

1. 接收当前输入。
2. 读取 Session 历史。
3. 组装 SystemPrompt 和其他上下文。
4. 调用 LLM Runtime。
5. 处理模型返回结果。
6. 判断是否需要执行工具。
7. 执行工具并记录结果。
8. 根据工具结果继续调用模型。
9. 将最终消息记录到 Session。
10. 返回本轮 Agent 执行结果。

是否需要多轮工具调用，由具体 Agent Loop 实现及配置决定。

此前开发计划采用逐步增强方式：先完成真实模型调用，再逐步增加工具调用循环、异常处理和其他能力。

### 8.7 Tool Runtime

Agent 需要能够读取和操作小说相关资料，而不只是依赖预先注入的固定提示词。

工具系统应支持注册、发现和执行不同工具，并保留必要的执行记录。

目前讨论过优先实现本地文件读取工具，再逐步扩展参数校验、工具调用循环和其他能力。

后续可以为不同 Agent 配置不同的可用工具与权限。

本地工具可以由 Harness 内部直接注册和执行，不要求全部经过 MCP。

MCP 可以作为外部工具接入的一种方式。

### 8.8 Workflow 与 Harness 的关系

Workflow 用于协调业务流程和状态变化。

Harness 用于执行具体 Agent。

两者职责不同。

例如：

- Workflow 决定什么时候需要角色参与、事件需要如何推进。
- Agent Harness 负责执行角色 Agent 的推理、工具调用和会话管理。
- 事件与世界状态模块负责保存确定的业务结果。

此前项目使用 LangGraph 构建 Workflow，并通过 AgentPort 等接口隔离 Workflow 与 Agent 的具体实现。

后续是否继续使用现有 LangGraph 实现，应结合代码现状评估，不应因为 Harness 重构而无条件推翻已有工作流。

## 十、设计上需要特别避免的问题

### 10.1 不要过度结构化

早期设计曾倾向于为小说创作的每一步规定固定输入、输出、JSON Schema 和工作流节点。

这种设计虽然容易控制，但也可能限制 Agent 的自主性。

应根据任务性质决定结构化程度。

需要可靠持久化、程序校验和状态更新的结果可以采用结构化数据。

而创造性讨论、探索、角色互动和故事推演不应该全部被固定字段所限制。

### 10.2 不要把 Agent 降级为一次 LLM 调用

Agent 应具有根据任务需要自主决定后续操作的能力，例如：

- 读取资料。
- 查询历史。
- 使用工具。
- 多轮推理。
- 发现问题。
- 根据结果继续行动。

不是所有步骤都必须用 Agent，但被定义为 Agent 的模块，不应天然限制成一次简单生成。

### 10.3 不要让导演代替角色思考

导演应该保证较高层级的事件方向和世界一致性，而不是强制决定角色所有行动。

角色的自主决策是系统的核心能力之一。

### 10.4 不要混淆世界演化与小说表达

世界中的事件发生顺序、因果关系和参与者，不一定等于最终小说的章节结构和叙事顺序。

写作 Agent 负责表达，而不是直接决定全部世界事实。

### 10.5 不要提前规划整个小说世界的未来

世界初始化阶段不应预先决定全部事件结果、角色结局和所有故事线的发展过程。

可以确定核心背景、必要约束、初始矛盾以及重要发展方向。

但应为后续世界演化保留开放空间。

### 10.6 不要过早锁定设计

目前很多内容属于项目方向或概念模型，尚未形成最终接口。

在实现具体模块前，应结合现有代码、真实使用场景和系统边界讨论。

不能把历史上的初步想法误认为已经确定且不可更改的最终方案。

## 十一、项目最终愿景

Fly Novel 不只是一个自动写小说的工具。

理想状态下，它更像一个**由多个 Agent 参与、能够持续运行和演化的虚拟世界创作系统**。

人类负责提出构想、塑造方向、参与讨论与创作决策。

世界提供规则、状态和历史。

角色在世界中自主行动并互相影响。

事件承载世界变化，故事线体现长期和阶段性发展。

导演负责必要的协调和控制。

写作 Agent 将值得讲述的世界演化过程组织成小说。

最终形成一部具有长期一致性、角色自主性、多线发展能力和文学表现力的长篇小说。

**核心思想：不是让 AI 按照预先写好的故事行动，而是在合理的世界规则和创作方向下，让故事能够自然发生。**
