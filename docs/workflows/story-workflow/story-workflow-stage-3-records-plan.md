# 故事级工作流第三阶段：故事、场景与运行记录

本文细化[总体开发计划](story-workflow-development-plan.md)的第三阶段。业务约定以[故事级工作流](story-workflow.md)为准。以下步骤是建议实施顺序，步骤中的能力以各自验收为准。

按[学习型开发要求](../../development-plan.md#学习型开发要求)推进。每步先确定当前使用方式和必要接口，再做最小实现、示例和验证。按实际涉及的记录或会话边界对照 DeepSeek Harness，说明可比范围。完成当前一步后，按用户指示进入下一步。

## 当前基础与阶段目标

[现有模块](../../../src/story-workflow/README.md)已保存初步规划、父子故事节点、拆分与推进决定、模拟经过、回报、提前汇报、父故事评估及批次暂停记录。已有整轮和分批测试可作为回归基线。当前模拟器提供最小子故事的模拟经过，模块缺少供后续角色演绎使用的独立场景记录，以及能从同一个故事身份查到场景、结果和推进位置的核查路径。

本阶段从现有故事记录出发，先让调用方查到故事及其层级，再让一个最小子故事拥有可独立保存和读取的场景，最后核对场景经过、子故事回报与整轮进度。贯穿示例使用曲水城。父故事安排“商队夜间抵达”，第一个场景是城门交涉。测试可让可信模拟器提供“守卫拒绝开门，商队暂留城外”的经过。该经过标为模拟，场景结束与父故事目标达成分别判断。

阶段范围截至业务记录和记录核查。世界资料接入、真实角色 Agent 调用与认知、行动判断和世界事实写入按[总体计划](story-workflow-development-plan.md)的后续阶段开展。完整的异常恢复、并行调度和写作也在本阶段之外。

## 记录边界

| 对象 | 本阶段的职责 | 示例 |
| --- | --- | --- |
| 故事与初步事件 | 保存任务、计划身份、父子关系、推进顺序和已保存的回报引用。初步事件沿用现有身份，选中后关联相应故事。 | “商队夜间抵达”是初步事件。其子故事任务可以是“处理入城请求”。 |
| 场景 | 归属一个可直接演绎的最小子故事。保存相对顺序、处境、演绎经过和结束结果，使调用方能分别读取设置和结果。 | “城门交涉”与“城外安置”是两个可分别核查的场景。 |
| 运行记录 | 记录本轮和本批推进位置，核对故事、场景、回报及完成证据。 | 第一个场景有模拟经过，第二个仍待处理，本轮保持未结束。 |
| 世界事件与状态 | 保留与未来已发生事实及状态写入的职责边界。现阶段使用模拟结果，不从计划、场景或回报生成世界事实。 | 模拟中的“商队扎营”只保留在故事运行内。 |
| Agent Session 与 Memory | 由 Agent 管理。业务记录可关联已有身份供核查。完成由业务结果判断。 | 有一条“已经完成”的消息，但缺少已保存的场景结果时，业务仍待核查。 |

下面建议沿用当前故事工作流的文件存储和身份，不为开发步骤创建源码模块。字段、记录版本、写入约束和查询方式在对应步骤确定。对已有数据，优先采用新增记录的方式。若确实需要变更旧格式，先确定显式兼容、迁移或拒绝读取策略及验证样例，再改读取和写入。

## 分步开发

### 1. 核查现有配置与入口

**输入与动作。** 从[故事应用入口](../../../src/app/story-workflow.ts)、[真实模型调试入口](../../../src/app/story-workflow-debug.ts)和固定替身测试追踪实际生效的配置。核对规划与运行记录的根目录、受保护目录、目录的创建方和读取方，以及每批数量、模型、模拟器、取消和超时分别在哪里设置。按需对照[配置说明](../../../src/config/README.md)和已保存样例，区分入口参数、代码默认值、测试配置与本机配置。

**本步交付。** 一份配置核查清单，每项记录来源、生效入口、默认值或必填条件，以及是否能直接复用。列出文档、配置或实现之间的差异，以及第三阶段确实需要补的缺口。模型配置只记录非敏感设置和凭据引用是否可用。

**完成标准。** 能说明一次曲水城调试的记录写到哪里、由谁指定、继续时读取哪一套目录，并能区别真实调试和固定替身使用的配置。此步只读核查，完成后再进入记录盘点与后续实现。

**曲水城调试实例。** 调试入口在当前工作目录下创建 `tmp/story-workflow-debug-*`，打印目录，并建立 `plans` 与 `collaborations`。本机样例 `tmp/story-workflow-debug-oR1uMH` 的规划 ID 为 `7047c5b7-3b43-45f0-aabb-8299f49d161f`。初步规划位于 `plans/<规划 ID>.json`，第一批暂停位于 `collaborations/<规划 ID>.1.paused.story.json`。调试循环传回同一对目录、原规划 ID 和暂停批次启动下一批。该样例的第 1、2 批均有对应的暂停和消费标记，目录中有补充安排，根故事结果文件缺失。

**文档与入口差异。** 配置说明原先记载固定绝对路径，实际模型配置随当前工作目录定位到 `.fly-novel`，其说明已按[路径实现](../../../src/config/paths.ts)校准。[业务流程图](story-workflow.md#总体流程)将配额检查放在判断可直接演绎之后，当前代码在结算已处理完的父故事后，于开始下一子项前检查配额。下一子项可能尚未作出继续、取消或拆分判断。

### 2. 盘点现有记录，确定最小读取路径

**输入与动作。** 用固定模型替身跑一次曲水城规划、多层子故事和分批暂停，从已有记录追踪规划、根故事、子故事、模拟经过、回报、暂停和整轮结果。分别记录每种文件的写入者、身份、读取入口、完成证据和部分写入时的含义。

**本步交付。** 定出第三阶段所需的最小查询清单，包括按规划找到根故事、按故事找到上级和当前安排、按故事列出场景及结果、按批次核查运行位置。确定哪些读取可以直接复用，哪些需要新增。明确老记录缺少场景时的读取语义。

**完成标准。** 能用现有文件解释曲水城一次暂停处于哪个故事和批次，区分已有记录与待补能力。保留一份现有版本样例作为后续兼容验证输入。

#### 现有记录清单

以下为多层推进路径。文件名中的 `P` 是规划 ID，也是运行 ID，`S` 是故事 ID，`B` 是批次编号，`N` 是提前汇报 ID。规划文件在 `plans/`，其余在 `collaborations/`。JSON 记录使用 `formatVersion: 1`，继续标记为空文件。文件由存储独占创建，跨文件写入可能只完成一部分。见[记录类型](../../../src/story-workflow/types.ts)和[存储实现](../../../src/story-workflow/store.ts)。

| 文件 | 写入时机和身份 | 现有读取入口与证据 |
| --- | --- | --- |
| `P.json` | `createStoryPlan` 校验导演响应后写入规划输入、事件 ID 和顺序，或无可推进事件的原因。 | `readStoryPlan` / `PlanStore.read`。只证明规划已保存。 |
| `P.siblings.json`、`P.S.story.json` | `runStoryTree` 先占用规划并登记根故事 ID，再写根节点。创建下级节点时保存运行、故事、直接上级和任务。 | `readRootStoryId`、`readStoryNode`。根登记已存在但节点缺失时，说明启动记录不完整。节点存在仅证明任务已保存。 |
| `P.S.decision.story.json`、`P.S.supplement.story.json` | `runStoryTree` 保存根或子导演的拆分与直接演绎安排，并在父导演决定补充时追加一个有独立 ID 的子项。 | `readStoryStep` 按类型读取。拆分列表及其补充项给出顺序，候选子项可以还没有节点。直接演绎安排尚不表示演绎完成。 |
| `P.S.choice.story.json` | `runStoryTree` 在创建下级任务前记录父导演对候选子项的继续、调整或取消决定，保存直接上级 ID。 | `readStoryChoice`。取消项可以没有节点。继续或调整已保存而节点缺失时，只能确认推进决定已记录。 |
| `P.S.N.notice-report.json`、`P.S.N.notice-decision.json` | `simulateStory` 先保存子导演提前汇报，再保存直接上级的决定，随后才将决定返给模拟器。 | `readStoryNotice`。有汇报而无决定时，上级处理尚不可确认。两者均存在仍需核对后续演绎和回报。 |
| `P.S.simulation.story.json`、`P.S.result.story.json` | `runStoryTree` 先保存模拟器返回的经过，再请导演形成回报并交直接上级接收。回报写入并重读后才结算直接演绎的子故事。 | `readStoryStep`。仅有经过时可核查模拟内容，子故事回报仍未确认。两份文件均保留在故事运行内。 |
| `P.S.assessment.story.json` | `runStoryTree` 在结算父故事时先保存评估，再保存结果。提前终止的直接演绎也写评估。 | `readStoryStep`。根故事通过 `readStoryRoundResult` 联合校验原规划、根身份、安排、结果和评估。只有评估文件时整轮结算仍无法确认。 |
| `P.B.paused.story.json`、`P.B.continued.story.json` | `runStoryTree` 到达暂停点时保存规划摘要和推进栈。继续在核对证据后独占创建消费标记。 | `readStoryProgress` 可重读暂停快照。`restoreStoryProgress` 还会核对关联记录并消费批次，纯查询应避免调用。消费标记只证明该暂停位置已被领取。 |

#### 最小读取路径

1. **按规划找根故事。** 给定可信的两个记录根和规划 ID，复用 `readStoryPlan`、`readRootStoryId` 和 `readStoryNode`。核对根节点没有上级，根安排与规划事件一致；单事件协作记录与多层故事节点分别使用各自的读取入口。
2. **按故事找上级及当前安排。** 给定规划和目标故事 ID，复用节点、决定与步骤读取，从 `parentStoryId` 定位直接上级，并在上级的拆分列表和补充项中验证归属及顺序。下一步补一个调用方可用的组合读取入口，区分已安排未开始、已取消、已完成以及记录缺失或不一致。
3. **按故事列场景与结果。** 当前只有故事级 `simulation` 与 `result`，沿用它们核查已有模拟和回报。后续新增场景归属、排序及结果引用。读取版本 1 样例时，将场景表示为旧格式未记录，保留可独立核实的旧回报。对于要求场景证据的新记录，缺少场景结果时应显示待核查。
4. **按批次核查位置。** 复用 `readStoryProgress` 读取栈顶故事及其下一项，复用现有校验规则比对规划、上下级、决定与结果。后续补无需消费批次的进度核查入口，区分暂停可继续、已领取、证据不全和整轮已完成。整轮完成沿用 `readStoryRoundResult`。

#### 曲水城版本 1 样例

使用固定替身运行[整轮测试](../../../src/story-workflow/tests/round.test.ts)，在夹具清理前复制原始文件，并从副本重读两份暂停快照和第一轮结果。样例保存在本机 `artifacts/story-workflow-v1-Odzpbo/`，由 Git 忽略，供本地兼容验证使用。副本包含 2 份规划和 47 个协作目录文件。第一轮规划 ID 为 `0c1c2d19-4aaf-4603-82f0-16fa91209cdc`，根故事 ID 为 `e48799e2-7ebc-453b-9fca-a1f0d9fddfc5`。

- 第 1 批结束后，栈顶为「商队夜间抵达」，本层已处理「查验身份」，下一项为「交涉入城」。根层虽已指向「处理货物」，仍需先结算当前下级。
- 第 2 批完成「交涉入城」和补充的「协商临时仓位」，结算「商队夜间抵达」。暂停快照只剩根层，下一项为「处理货物」。
- 第 3 批处理货物并结算根故事，重读评估为 `achieved`。随后从调用方提供的新局势创建独立规划。副本采自测试结束时，两个暂停均已有消费标记，可用于只读核查。

DeepSeek Harness 的持久化接口按 Session 保存和重读 Agent 交互事件，读取可使用独立的只读句柄。这里同样需要让核查与取得续跑位置各自有明确入口。曲水城进度依据故事节点、决定和结果文件，Session 证据只覆盖 Agent 交互层。见 [DeepSeek Harness Session Persistence](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/session/session-persistence/README.md)。

### 3. 跑通父子故事读取，建立场景的归属基础

**输入与动作。** 给定可信记录目录、规划 ID 和目标故事 ID，复用或补齐读取能力。沿已保存的根故事、拆分和补充安排定位直接上级、同层顺序及下级结果。查询时区分已安排但还没有节点的事件、已取消事件和已完成故事。

**本步交付。** 一个调用方可用的故事读取入口。它能返回故事任务、直接上级和有记录依据的子项进展，并明确报告身份不匹配、资料缺失或结果无法确认。

**完成标准。** 从重新打开的存储读取根故事、子故事和孙故事，查到正确上级。用其他规划的故事 ID、失配的父 ID 和缺失记录验证拒绝路径。同一规划里尚未开工的子项仍可在安排中找到。

**读取入口。** [应用层 `readStory`](../../../src/app/story-workflow.ts) 接收可信记录根、规划 ID 和可选的故事 ID。调用方可以先读取根故事，再从返回的子项取得「商队夜间抵达」的故事 ID，由该故事查询「交涉入城」。读取时沿上级链核对归属，未开工或取消的子项可在上级安排中查看。结果字段及不完整记录的处理见[读取父子故事](../../../src/story-workflow/README.md#读取父子故事)。

### 4. 保存和重读一个场景

**输入与动作。** 给定一个已确定直接演绎的子故事，用固定资料建立“城门交涉”场景。先实现创建和读取，并能按故事和顺序找到场景。随后用第二个场景验证同一故事可包含多个场景，同一场景只属于一个故事。

**本步交付。** 场景有程序分配的业务身份，关联运行、故事与场景顺序。场景设置至少能表达当前处境和导演准备信息。地点、时间、参与者的引用只纳入本步有实际用途且可核查的部分。

**完成标准。** 重开存储后能找到两个场景并按同一顺序读取。跨运行或错误故事的关联、重复身份或顺序冲突得到明确错误，已有记录保留。已保存设置的场景显示为待演绎。

**场景设置入口。** 调用方为「商队夜间抵达」分别保存「城门交涉」与「城外安置」的处境和导演准备信息，再按故事重读两份待演绎设置。每份设置使用单独的版本 1 文件，由程序按运行、故事和顺序生成身份。见[应用接口和存储行为](../../../src/story-workflow/README.md#保存和读取场景设置)及[曲水城测试](../../../src/story-workflow/tests/scenes.test.ts)。

### 5. 保存场景经过和结果，关联子故事回报

**输入与动作。** 让现有可信模拟器和固定模型替身给“城门交涉”写入一份模拟经过与结束结果，分别验证场景设置已保存、演绎结果已保存、子故事回报已保存三个时点。让一个子故事从两个场景汇总，保留结果引用以便从回报定位原始经过。

**本步交付。** 提供场景结果的保存和读取能力。沿已有演绎与回报入口接入记录，明确一次可信结果何时允许结算场景，何时可以形成子故事回报。单场景结束后仍可继续同故事的下一个场景。正常结束、终止和未决的处理由实际记录区分。

**完成标准。** 重新读取回报时能追到两个场景的原始记录，并明确这些结果是模拟。验证场景结果不可被重复写入覆盖、引用其他故事的场景会被拒绝，以及有设置但无结果或有场景结果但无故事回报时均可正确核查。

**模拟结果与回报引用。** 曲水城固定替身用例保存「城门交涉」及「城外安置」的模拟结果，再从已保存的子故事回报重读两份原始经过。设置、结果与回报分别落盘，回报失败后可单独核查场景。见[结果契约与版本规则](../../../src/story-workflow/README.md#保存模拟结果并形成故事回报)及[曲水城测试](../../../src/story-workflow/tests/scenes.test.ts)。

### 6. 从保存的证据核查运行进度

**输入与动作。** 分别模拟正常按量暂停、场景设置后中断、结果写入后回报失败，以及整轮结束。用已保存的故事节点、场景结果、子故事回报和批次记录重读这些状态。保留区别正常暂停、结果不确定与完成所需要的最小信息。

**本步交付。** 一个运行进度核查路径。可定位当前故事、相关场景、已经确认的结果和下一待处理位置。在现有按量暂停继续入口上核查新增场景记录与已保存的完成证据，沿用批次独占消费方式。

**完成标准。** 正常暂停可继续，已确认的演绎不重复执行。缺失证据或写入结果不确定时能指出待核查的位置，不自动重放。模拟完成数量仍按最小子故事计算，一个故事包含多个场景也只计一次。Session 有记录而业务结果缺失时，核查结果仍为未完成或待核查。

**进度核查入口。** `inspectStoryProgress` 只读核对当前故事、场景、回报及最新暂停。曲水城用例区分设置后中断、结果已保存但回报失败、可继续的暂停和整轮完成。即使一个父故事已经结算，其后代的场景证据缺失时仍拒绝消费暂停。见[核查与继续契约](../../../src/story-workflow/README.md#核查运行进度)及[进度测试](../../../src/story-workflow/tests/progress.test.ts)。

### 7. 验证从故事到场景和整轮结果的完整读取

**输入与动作。** 使用曲水城的固定资料通过声明入口跑完整例子。规划父子故事，为最小子故事保存两个场景，保存模拟结果并向上回报，按量暂停后重开存储继续，再核对整轮完成记录。

**本步交付。** 可重复运行的集成用例、必要的记录和入口说明，以及供后续场景演绎接入的最小契约。更新相关模块文档和受影响的目录说明。

**完成标准。** 用一组运行 ID 和故事 ID 能查到初步计划、层级、场景设置与经过、回报、暂停或整轮结果。聚焦验证覆盖旧格式、未知版本、损坏、冲突、部分写入、取消和重复继续。报告实际跑过的命令与结果。固定替身用于验证流程和存储，真实模型若另行运行，应单独报告观察范围。

**整轮验证。** [曲水城用例](../../../src/story-workflow/tests/round.test.ts)从固定初步规划推进「商队夜间抵达」，在最小子故事「查验身份」保存城门交涉与城外安置的设置和模拟经过。第一批重读场景引用并核查下一项「交涉入城」，第二批继续交涉及补充故事，第三批处理货物并重读整轮回报。该用例检查损坏与未知版本的暂停文件、并发重复继续及无场景的旧格式回报。场景冲突、部分写入和取消由同模块的聚焦测试覆盖。启动与查询示例见[曲水城整轮验证](../../../src/story-workflow/README.md#曲水城整轮验证)。

**本机样例。** 含场景记录的固定替身副本保存在 `artifacts/story-workflow-scenes-MdcoIR/`，由 Git 忽略。规划 ID 为 `ff92c2b7-54f6-4c5c-b36a-564e742943c0`，带场景回报的最小故事 ID 为 `e4c27c66-6930-4a4d-8780-65d740afec77`。两份历史暂停已消费，可从归档读取，整轮核查确认为完成，共 4 个最小故事。第 2 步保留的版本 1 样例继续用于兼容验证。

**验证结果。** `pnpm run build:tests` 和 `node --test .test-dist/story-workflow/tests/*.test.js` 通过，故事工作流共 36 项测试。`pnpm run build` 通过，使用构建产物的应用入口重读版本 1 样例及含场景样例。验证使用固定替身，未发起真实模型请求。
