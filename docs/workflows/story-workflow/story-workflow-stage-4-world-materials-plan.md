# 故事级工作流第四阶段：世界资料接入与按需补充

本文细化[总体开发计划](story-workflow-development-plan.md)的第四阶段，业务约定见[故事级工作流](story-workflow.md)。按[学习型开发要求](../../development-plan.md#学习型开发要求)逐步推进。每步先用曲水城示例核对输入、输出和拒绝条件，再确定所需接口、实现及验证。完成当前步骤后按用户指示继续。

## 当前基础与阶段目标

第三阶段已经能重读规划、父子故事、场景、模拟结果和运行进度。[故事入口](../../../src/app/story-workflow.ts)仍由调用方传入任务、事实和发展方向。导演可以获取这些输入，场景演绎由可信模拟器提供。第四阶段让导演从可信应用选定的世界和资料范围取得可追溯的故事起点，并在当前任务需要时请求补充设定。

首个贯通示例只覆盖曲水城与城门。初始化交付可以提供夜间闭门的规则和商贸趋紧的发展方向。商队是否已经抵达应看选定的可信局势或事件依据。若已授权读取的城门资料缺少可用等候点，导演可以请求地图 Agent 提议一处临时安置点。应用核对提案适用的地点、依据和冲突，再决定本次场景是否可采用。用固定模拟器验证组织场景所需资料已经齐备，角色调用、角色认知、世界事实写入和通用发布仍按后续阶段推进。

## 读取与补充边界

- 可信调用方选定世界、交付 ID、可读资料及故事关注范围。导演只能提出业务查询或补充需求，应用用已绑定的来源、范围和业务 ID 解析。缺少授权、同名异世界、引用失配分别报告。
- 输入至少分清已交付设定、当前可信事实或已发生事件、发展方向、明确留白和未覆盖范围。资料读取失败、权限不足、引用过期与确实缺少资料分别处理。交付中暂留的候选保留其候选身份。相同主题在交付与当前来源出现不同版本时保留两者依据，按实际来源及适用时点解释，无法确认时暂停受影响的决定。
- 规划或场景使用的资料要能按世界、来源身份和版本重读。优先引用可验证的不可变交付正文。可变来源若无法按旧版本取回，保存本次实际使用的必要内容及其摘要，或明确报告旧版本无法重建。先确定记录范围、体积限制和拒绝或兼容策略，再引入对应存储字段。
- 专用 Agent 返回的补充先以提案记录。应用独立核对来源、结构化引用、与已确认资料的冲突及任务所需信息。若允许本次场景采用，应标明采用者、适用故事和场景以及补充来源。世界正文、资料目录、既有交付及正式发布由原有职责管理。Session 可用于追溯交互，业务进展由资料与故事记录核对。

## 分步开发

### 1. 核查配置、交付和可用读取入口

**输入与动作。** 从故事入口反查规划、导演调用和场景设置的真实输入，再沿[世界初始化入口](../../../src/app/world-initialization-entry.ts)、[交付读取](../../../src/world-init/recovery/delivery.ts)、资料目录、地图存储和地图 Agent 追踪调用关系。盘点世界 ID、交付 ID、目录、权限、资源生命周期和可重用测试。用现有固定数据核查一份城门资料的正文、版本及交付范围。

**本步交付。** 可核对的配置和资料清单，写明每类来源的读取者、选择者、版本、可见范围和失败方式。确定曲水城最小输入及验收数据来源。

**完成标准。** 能说明一条城门规则、一个商贸发展方向和一项缺口分别从哪里取得。能指出交付快照、目录简介和当前正文的不同用途。本步只做只读核查。

### 2. 绑定世界并重读一份初始化交付

**输入与动作。** 可信调用方提供有权限的世界配置、交付 ID 和本轮关注范围。从现有交付中选择城门规则及发展规划，核对世界和交付身份，读取实际正文和交付版本。

**本步交付。** 一个可复用的只读接入路径，为故事调用方提供有来源依据的交付资料、已知留白和未覆盖信息。确定目录、同世界校验、读取句柄的归属和释放方式。

**完成标准。** 重开后能重读同一交付及所选内容。拒绝同名异世界、错误交付 ID、无权、未知版本和损坏。缺少交付的旧工作区保留现状并明确报告缺失，第三阶段的固定输入路径仍可使用。

### 3. 接入当前资料并形成导演输入

**输入与动作。** 用最小授权范围读取曲水城相关的地图、已提供的当前局势或已发生事件。优先用所属模块结构化身份查询，目录用于定位来源。把当前资料与交付时点、发展方向和明确留白一并传给初步规划导演。若没有可信的当前事件来源，示例显式提供固定资料并标注其来源。

**本步交付。** 一份可供导演规划的世界背景及其可重读凭据。确定哪些内容会随规划保存、如何在父子调用中传递、继续时怎样核对原输入和变化的来源。字段及版本规则在实现前随接口确认。

**完成标准。** 导演能区分夜间闭门规则、商贸趋紧方向和已发生事件。把规划里「商队预计夜间抵达」误作事实的输入可被发现。测试覆盖范围之外、授权拒绝、目录或正文读取失败、来源变化，以及确实没有相关记录或存在明确留白。

### 4. 在选择或组织当前场景时发现资料缺口

**输入与动作。** 选中「处理入城请求」后，只核对城门位置与商队可用的等候点。导演用业务问题指出还需什么资料、关联地点和预期用途。可信应用检查现有来源，区分可直接回答、需要补充，以及因无权、读取异常或版本变化需要先核查的情况。

**本步交付。** 串通一个场景设置前的资料核对点。缺口要能关联当前故事、目标地点、查询范围和未满足的条件，并保留足够证据供暂停后查看。

**完成标准。** 资料充分时继续组织场景，无需调用地图 Agent。确认缺少等候点时给出具体补充请求。无权、索引不完整和读取失败都有可区分的结果，并保持当前场景待处理。

### 5. 通过可信装配委派一次地图补充

**输入与动作。** 用单个曲水城地图缺口验证委派输入，包含目标地点身份、适用范围、已知约束和完成条件。应用选择和装配地图 Agent，限制其资料访问范围。优先复用现有 Agent 生命周期和只读地图工具，用固定替身返回临时等候点的结构化提案。

**本步交付。** 一条有明确完成和取消语义的地图补充路径。记录请求与当前故事的关系、提案正文及引用依据。调用结束后按实际生命周期释放实例、工具注册和借用资源。

**完成标准。** 成功提案可独立重读。超时、取消、拒绝或内容无效时保留可核查状态，不产出可用于场景的有效资料。测试确认 Agent 只获得授权范围内的数据，也无法通过该调用改写世界正文。

### 6. 核对补充结果并接回场景准备

**输入与动作。** 重读提案及相关世界来源，核查地点身份、来源版本和原始缺口。比较与已知城门、地形和约束是否冲突。由可信调用方决定是否允许该提案用于本故事中的场景，并记录依据及适用边界。

**本步交付。** 一条从资料缺口经补充、复核到场景设置的证据链。场景需要而仍无法核实的条件保持待处理。核对继续时同一提案的重读与重复请求语义，无法确定已有调用结果时保留状态供核查。

**完成标准。** 采用的等候点能在场景记录追溯到原提案和依据。验证落在错误地点、来源版本变化、与现有设定冲突、补充仍不充分及调用方未采用的情况。世界正文和既有交付仍能按原版本重读。

### 7. 验证曲水城从交付到场景的完整读取

**输入与动作。** 通过声明入口使用固定交付、当前资料和模型替身，依次执行故事规划、发现城门缺口、委派地图 Agent、重新核查及保存场景设置。重开世界资料与故事记录，沿运行、故事和场景身份追溯所用版本及补充决定。

**本步交付。** 可重复运行的集成用例、相关入口说明和供下一阶段使用的最小资料契约。验证后对照 [DeepSeek Harness 委派能力的项目对照记录](../../modules/agents/tool-subagent-development-plan.md)，说明可比的权限装配、调用生命周期与结果边界。记录实际运行的命令及结果。

**完成标准。** 可以追溯同一场景采用了哪份交付、哪些当前资料和哪条补充。缺失、无权、读取失败、补充失败和来源过期均得到明确结果。旧故事记录可重读，固定替身验证与任何真实模型观察分别报告。第四阶段完成后按用户指示进入下一阶段。
