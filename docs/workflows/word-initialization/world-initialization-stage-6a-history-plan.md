# 第 6A 阶段：历史设定详细开发计划

本文细化[内容模块逐项开发计划的历史设定步骤](world-initialization-stage-6a-content-modules-plan.md#5-历史设定)，供历史资料、专用插件、Agent 和验证逐步开发。除明确标注为用户已确认的内容外，字段、工具名称和实现方式均是设计提案，不代表已经实现或成为最终契约。

## 目标与业务边界

历史设定记录世界初始化选定起始时点之前已经发生的过去，以及这些过去如何影响世界。一个世界可以服务多部小说，历史不以单一主角为中心；重要历史按近期需要展开，远古、其他地区或隐秘内容可以概述、未知或明确留白，不要求填满一条完整年表。初始化成果供用户整体审阅，保存、目录登记或 Agent 返回均不等于用户确认事实。

历史专用 Agent 负责历史内容的创建、读取和完善，主 Agent 识别需要、委派、核对和整合；主 Agent 仍可主动补充十个模块之外的必要内容。历史 Agent 引用其他模块成果，不直接修改其他负责人文件。历史正文不预设未来角色选择、故事结局，也不启动世界运行或事件推进。

| 内容 | 归属与关系 |
| --- | --- |
| 初始化起点前发生的战争、迁徙、制度形成和其他往事 | 历史设定维护事件经过、时间信息、参与者、相关说法和已知影响。 |
| 起始时点仍然存在的危机、组织关系和整体局势 | 初始局势维护当时状态；历史可以说明历史影响线索并供其引用，不独立维护另一份当前局势。 |
| 未来可能发生的战争或变化 | 宏观发展蓝图维护可能的方向与条件，不写成已经发生的历史。 |
| 地点本身及空间关系、组织本身及成员关系、人物资料与私人认知 | 分别归地图、组织、人物模块；历史按需引用其 ID 或保留未关联线索，不复制权威资料或擅自修改。 |
| 角色的个人经历和对往事的认识 | 人物正文可记录该人物知道或认为的内容；世界历史和人物认知可以不同，不能自动替角色补全知识。 |
| 世界演化后发生的实际事件、历史快照和角色记忆 | 后续世界运行和历史留存机制负责；不把初始化事件文件、Session 或文件修改时间冒充事件推进和长期记忆。 |

## 当前实现及可复用能力

历史专用 Agent、历史插件、事件格式和结构化时间线已实现，具体范围见[历史包说明](../../../src/agents/plugins/history/README.md)和[应用入口说明](../../../src/app/README.md)；尚无历史与角色运行时认知联动接口。成果可通过[工作区与资料目录](../../../src/world-init/README.md)按世界、负责人和目录读取；目录简介只是导航，不能替代正文或用户确认。

[地图插件](../../../src/agents/plugins/map/README.md)提供地点 ID 和地图查询；[组织插件](../../../src/agents/plugins/organization/README.md)维护组织、组织关系和成员关系，并提供规划者及按组织授权的角色查询；[人物插件](../../../src/agents/plugins/character/README.md)维护人物及公共人物关系。引用这些资料须复用可信应用提供的已打开句柄或后续明确的共享读取能力，核验实际世界和身份；不能假设存在统一对象存储、自动跨模块关联服务或路径无关读取接口。

沿用现有 TypeScript、Cordis Preset、SystemPrompt、Tools、Session、工作区和文件后端；专用插件的格式、存储、查询及工具定义集中在插件内，Agent 的职责提示词与应用装配按现有专用 Agent 惯例组织。Session 能恢复对话，不证明历史成果已保存或任务完成；单可信写入进程和现有路径检查不等于跨进程锁或系统级隔离。

## 已确认的历史组织方式

1. **事件与子事件。** 用户确认按需建立子事件。例如“青河战争”作为一项历史事件；水渠争夺和停战谈判若需要单独查询、关联或继续展开，可分别建立子事件并关联战争。没有独立建档的经过可以写在战争正文中；不要求每个章节、阶段或所有往事都建立文件。
2. **公开与隐藏内容。** 用户确认同一事件分别记录公开说法和隐藏事实；隐藏事实可以未知或留白。例如公开说法是争夺水源，幕后原因仍未确定时，只记录“未知”，不能由 Agent 把猜测写成真相。多个相互矛盾的说法可并存，不因出现一个说法就自动认定其他说法为假。
3. **角色认知与隐藏历史。** 用户确认历史 Agent 和世界规划者可读取完整历史资料。角色对历史的认知来自初始化时赋予其自身的已知内容，或来自后续故事中的实际经历、交流和发现；不需要为角色预先授予历史事件或秘密的权限，也不在历史事件中维护角色知情名单。角色可能不知道事实、只知道部分说法，或持有错误认知。不能因为组织身份、历史事件的公开标签或未来可能发生的故事，自动断定角色知道某项内容。
4. **时间基准。** 用户确认允许事件时间相对初始化起始时点或某个已知纪年表达，二者可以共存，并记录所用参考对象；缺少可靠时间基准或换算关系时保留原文，不自动换算。初始化起始时点如何跨模块统一，在初始局势等相关模块设计时衔接。
5. **历史事件修改。** 用户确认初始化期间未确认的历史资料按读取版本直接更新；已确认历史的设定修改保留待审候选；世界演化造成变化时保留原状态及世界时间依据。保存与用户确认仍是不同操作，候选提交和演化留存机制需要后续实际开发。
6. **子事件多重归属。** 用户确认子事件在需要时可以关联多个上级事件，并明确每条关联的含义。例如一场停战谈判可以同时是多场冲突的组成部分；普通的主题关联、先后和因果仍分别表示，不能自动当作上级关系。

上述“公开／隐藏／未知”描述世界内信息及认知；“待审／已确认”描述人机审阅状态。某项隐藏内容即使已写入，也不自动成为用户确认的世界事实；初版保存与用户整体审阅继续分开。

## 两种世界走查

### 开放式修仙世界

三百年前某次灵脉变动引发青云宗迁徙，事件可以只有“约三百年前”和大致地区；迁徙细节未知则留白，不凭空补齐具体年份或所有参与者。若近期故事需要，可以将“山门迁建”单独建为迁徙的子事件；只作背景时保留在迁徙事件内。

青云宗和山门地点有档案时按真实 ID 关联；尚未建档的散修只保留身份线索，不能用姓名冒充 ID。公开传说可能认为迁徙由自然变化引起，隐藏原因可能未知，也可能已有明确设定；两种情况均不能把某个角色视为自动知情。若人物资料写到林岚亲历三百年前的迁徙，应结合其寿命和时间线报告待核实冲突，不能自动修改人物年龄或历史。

### 资源有限的城邦群

青河战争持续若干年，水源争夺与谈判是可按需建立的子事件。其间另一座城邦发生的短期冲突可能与战争时间重叠；未知道确切先后时不强排。战后停水造成的损失属于历史影响；初始化时仍存在的供水紧张及各城关系归初始局势。未来可能再爆发战争是发展规划。

曲水城地点引用地图，曲水议会引用组织；两者即使同名也不是同一个 ID。公开记载和秘密档案分别存放在同一事件的相应内容中；历史规划者可查看完整资料。初始化时林岚已知的部分记录在其人物资料中，顾青不知的内容不会因为历史里存在就自动进入顾青认知；两人后来通过实际经历得知的新内容留给世界运行与角色认知机制处理。若后续档案显示幕后原因不同，初始化期间如何修改应保留版本冲突保护，不能把原始说法静默改成事实。

## 资料、时间和关联设计提案

### 事件粒度与内容

建议以独立事件为最小可定位单位，每个事件有世界 ID、程序生成的事件 ID、名称、可选别名、概述、按需正文、时间表达、相关资料引用、子事件或其他关联、公开说法、隐藏内容和明确留白。名称允许重复；事件 ID 与名称分离，改名不改变引用。名称或信息不足时允许未建档线索，不凭名称自动合并事件。

重要子事件按需独立建档，并可按已确认的多重归属关联多个上级；嵌套深度、循环拒绝和不完整路径的处理在格式步骤通过实例确定。事件可有多个参与人物、组织与地点，不因参与关系推断组织成员、控制权、人物认知或角色行动。

建议资料展开程度沿用概念上的未展开、概况、详细，并与审核状态、公开或隐藏内容以及时间确定程度分开；这是提案，枚举名称和是否需要该字段待实现前确认。不存在文件不代表事件不存在；没有记录的子事件不等于没有发生，结果应标明未覆盖或未知。

### 时间表达与查询

支持事件相对于初始化起始时点或某个已知纪年表达时间并记录参考对象；两种表达可共存。不要求每个世界采用公历或共享一种纪年，也不要求每个事件有精确日期。建议分别表达：确切时间、约略时间或范围、只知先后、时间未知；持续事件允许起止、持续时间或其中一端未知。是否引入世界纪年定义、不同纪年如何换算由实际世界规则决定，没有可靠基准或换算时保留原表述。

例如：迁徙“约三百年前”、战争“某王朝末期持续数年”、谈判“发生在战争之后”、另一次冲突只知与战争部分重叠。工具不能把文字中的“约”处理为精确值，不能把无法比较的年代强制排成全序，也不能将文件修改时间、目录登记时间或 Session 时间当作世界时间。

时间线按可比较的世界时间和已记录先后关系组织；相对顺序不足或可能互相矛盾时，返回不可比较、待核查或冲突提示，并说明查询覆盖范围。明确的先后、因果、上下级和共同参与是不同关系；有先后不自动意味着因果，有共同参与不自动意味着人物知情。因果应是有依据的记录或明确标出的假说，不能把相关性自动升级成事实。

### 跨模块引用及一致性

事件引用地点、组织、人物时使用类型与稳定 ID；姓名、地点名和组织名展示时从对应模块当前资料解析，历史正文保留必要叙述但不维护另一份权威资料。相应资料不存在时使用明确线索或待关联状态，不创造虚假 ID；同名先列候选，由可信流程核验，不根据名称自动关联。事件可引用其他事件；相关的初始局势可引用历史，不自动反向写入其他模块。

查询区分已解析、未建档线索、记录缺失、不可访问、世界不匹配、资料过期和读取失败；不能将错误或未查询范围当作“不存在”。冲突检查应对实际读到的历史、时间、人物、组织、地图和世界规则逐项报告发现、依据及未检查范围；不要求全局自动一致性服务，也不自动更改其他模块。保存历史与修改关联模块不是跨文件事务。

## 存储与版本方案提案

建议参照地图和组织，每个历史事件一份版本化 JSON，放在可信应用配置的历史负责人专属目录，例如 `history/events/<事件ID>.json`；这里的 `history` 是示意相对目录，不要求用户目录命名固定。每个事件同时承载其公开、隐藏及留白内容，子事件是独立文件，通过稳定 ID 关联。长篇经过可放在 JSON 正文字段；优先维持一份权威事件正文，不另做需要同步维护的总览文件。

事件间关联若记录在事件文件中，建议由被编辑的事件单侧维护并通过查询反向查找；如何防止关系语义重复或因果 / 层级矛盾须在契约步骤按实际场景确定。索引如有，只作为可重建的查询加速，损坏不能伪装成历史不存在；扫描范围、文件大小 / 数量上限、分页版本和部分结果语义由实现明确。

新格式从明确的版本开始；未知版本、重复 JSON 字段、非法 ID、损坏文件和跨世界文件拒绝读取并保留原文件。旧世界如果只有 Markdown 叙述或目录记录，不自动解析、覆盖、迁移或删除；先以授权原文或线索引用，是否转换及迁移方式另行设计。目录登记与事件保存独立，前者不代表确认或长期事实。

初始化期间未确认事件读取版本后直接更新，旧版本冲突时拒绝并重新读取；已确认资料的修改保留待审候选，由后续确认流程处理。世界演化造成变化时保留原状态及世界时间依据；候选、世界演化后的历史留存和跨文件事务均不能因本方案自动视为已有实现。

## 历史插件与拟提供的工具

建议建立 `src/agents/plugins/history/` 独立工作区包，集中历史事件格式、受控存储、查询、工具定义和插件注册；历史 Agent 使用自己的 Preset 和 SystemPrompt。以下名称均为规划，参数及接口以开发时确认的契约为准；工具不接受模型指定世界、目录、身份、权限或初始化阶段。

| 工具提案 | 用途与关键约束 |
| --- | --- |
| `history_event_create` | 创建一个已发生或明确待核实的历史事件；事件 ID 由程序生成，未建档参与者使用线索。 |
| `history_event_read` | 历史 Agent 或世界规划者按事件 ID 读取正文、公开说法、隐藏内容及版本；其他使用场景须由可信应用控制读取范围。 |
| `history_event_update` | 初始化阶段按版本更新允许修改的事件；明确提交完整内容或局部修改的语义，不静默丢失未编辑内容。 |
| `history_event_search` | 按名称、关键词、时间范围、地点、组织或人物引用查询；同名返回多个候选，分页携带结果版本。 |
| `history_event_children` / `history_event_ancestors` | 查询已记录的子事件或上级事件，限制深度并报告多条路径、未展开和截断，不将路径当成完整历史。 |
| `history_timeline` | 查询可比较的事件及明确的先后、持续或重叠；对未知或无法比较的时间分组报告，不捏造排序。 |
| `history_event_relations` | 查询事件之间已记录的先后、因果和其他关联，保持方向、依据和不确定性；不自动推断新的因果。 |
| `history_reference_check` | 通过可信应用绑定的同世界只读解析器核验人物、组织和地点引用；缺失解析器、无权、缺失与错误分别报告。 |
| `history_consistency_check` | 在明确的授权范围内检查已有事件的时间和引用等可机械核验问题，列出检查范围、冲突和未覆盖项；不自动改写其他模块。 |

角色认知不是历史模块中的访问权限或等级。初始化时角色资料维护该角色已知的信息；后续如何通过经历、交流和发现形成记忆与更新认知，留给世界运行及角色认知机制设计。历史 Agent 和规划者可以读取完整历史，但现有完整历史文件和工具不能直接交给故事角色，否则角色可能读到自己尚不知道的内容；实际读取隔离及普通文件、搜索等旁路由后续角色运行装配解决，不在本模块预建角色权限系统。

## Agent、目录与失败恢复

建议创建历史设定专用 Agent，负责读取世界背景、地图、组织和人物已有资料，确定近期需要的历史重点，创建事件及必要子事件，保留公开／隐藏说法和未知，并向主 Agent 返回可核查成果、来源、影响线索及遗漏。主 Agent 通过专用委派工具传递任务和必要背景；可信应用绑定世界、历史负责人、专属目录、Session、模型、引用服务和权限。Agent 可独立运行或被委派；历史工具与专用委派遵循现有插件和应用装配方式。

目录按历史负责人登记实际文件。面向故事角色的资料入口不能通过目录简介、普通文件或搜索把角色未知的历史直接暴露给角色；在后续角色运行机制明确读取边界前，不能声称角色认知隔离已经实现。规划者对历史的读取和角色知道什么是不同问题。

初始化中断时保留已写入事件和会话；重启后先核查真实成果、ID 和版本，再决定补做，不能因为 Session 恢复或工具异常就认定未创建并重复写入。单文件独占创建和按版本替换的成功、取消、冲突和结果不确定应分别报告；目录登记与事件写入分别报告。Windows 文件替换出现 1175 时按实际失败报告，不借历史模块开发擅自重写文件后端。

固定替身与真实模型的验证入口和覆盖范围见[历史 Agent 验证指南](../../cookbook/history-agent-validation.md)。

1. **核对现状与样例。** 核对地图、组织、人物、目录、世界基础信息的实际读取、身份及测试；用上述两世界明确历史起始边界、事件／子事件粒度、时间不确定和角色认知。核查历史目录、事件和相关工具均不存在，确认首版范围及尚待业务决定的事项。
2. **资料契约与时间表达。** 确定事件 JSON、版本与旧资料策略、时间及先后表达、子事件关联、公开／隐藏和留白、引用及初始化修改规则；使用真实目录样例检查独立文件、同名、未知时间、部分展开、循环和未知版本拒绝。具体字段及关联约束在该步骤定稿，不能把本提案自动视为最终契约。
3. **插件与查询工具。** 在历史插件内实现已确认的存储、创建、读取、版本更新、检索、时间线、事件关联和引用工具；验证排序不确定、父子与其他关系、跨世界、无效引用、缺失、损坏、版本冲突、取消和发布结果不确定。检查索引与正文一致性及结果不完整说明。
4. **历史 Agent 与可信装配。** 实现独立历史 Agent 和主 Agent 专用委派，绑定世界、历史目录、持久 Session、目录工具以及获授权的地图、组织、人物只读能力。核验多 Agent 共存、跨负责人写入拒绝、启动失败和取消后的资源释放、未配置引用的线索处理，以及同一会话恢复。
5. **角色认知边界。** 检查初始化人物资料能表达角色已知的历史与错误认知；历史 Agent 不替角色建立知情名单、不提前安排未来发现。明确完整历史工具和文件不能直接当作故事角色的认知，后续通过实际经历形成记忆及读取隔离交给世界运行与角色认知步骤设计，不在本阶段构建角色历史权限系统。
6. **端到端验证。** 使用固定模型替身分别走查开放修仙世界和城邦群，从主 Agent 委派到事件文件、子事件、时间线、关联与成果核对；覆盖旧数据、时间未知、冲突、目录变化、跨世界读取拒绝、取消、恢复和结果不确定。另行用真实模型检查工具使用和历史规划质量；替身不证明真实模型会正确规划。完成本模块后等待用户指示，不自动进入初始局势模块。

**验收：** 事件和必要子事件可按世界定位，公开说法、隐藏内容、未知与审核状态清晰；时间不确定及资料缺失不会被伪造为确定事实；规划者读取、相关资料引用和失败结果可核查。角色认知与历史演化只按实际实现和验证范围报告。
