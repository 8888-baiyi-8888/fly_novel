# 世界初始化第四阶段：逐包接入 DeepSeek Harness 文件能力

本文细化[世界初始化开发计划的第四阶段](world-initialization-development-plan.md#4-文件工具能力调研与验证)。按建议实施顺序逐包复用 DeepSeek Harness 官方实现：每个包单独核对依赖、接入、验证并记录结果。下文区分实际依赖与为了集成验收而安排的先后顺序。包的实际依赖和顺序以选定上游提交为准；发现额外必需包时，将其作为独立步骤插入相应消费者之前。

## 目标与统一约定

目标是让 Agent 在授权工作区内读取和搜索 UTF-8 文本，创建、编辑和删除草稿。优先直接使用官方包或同步官方源码，保留官方实现，仅适配项目构建、服务契约和必要的访问边界。文件工具不代替世界资料业务接口；已确认资料由受控应用代码管理，子 Agent 不直接改写。资料范围见[世界资料共享与读取设计](../../modules/world-information-access.md)。图片、PDF、音视频和远程文件系统不在本阶段范围内。

开始前固定可获取的上游提交，记录提交号、许可证和包版本，检查发布包可用性、Node.js、ESM 与本项目 CommonJS 构建的兼容性。逐包检查实际运行依赖、peer dependencies、所需服务和第三方许可证，区分测试依赖；确认直接依赖或同步源码的方式。源码同步时记录来源、许可证、固定版本、更新步骤和本地改动，并遵守仓库第三方源码管理规则。每步同步清单、锁文件和所属文档，运行该包相关的聚焦检查；需要的上游辅助库按依赖先行接入，不预先假定数量。

下列包名和职责参照官方[文件工具说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/fs/tool-fs/README.md)、[文件系统接口](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/fs/fs/README.md)和[工具目录](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-catalog.md)。实施时以固定提交核实，不把当前 `master` 当成固定版本。

## 包的目录安排

文件系统能力统一放在 `src/agents/plugins/fs/`，按上游能力拆成并列的独立工作区包；该目录既包含基础库和服务，也包含向 Agent 注册工具的插件，不表示每个子包都是模型工具。现有补丁包见 [`fs-patch`](../../../src/agents/plugins/fs/fs-patch/README.md)。

```text
src/agents/plugins/fs/
├── fs-patch/                补丁解析和文本修改
├── fs/                      文件系统服务契约
├── fs-local/                本地文件系统后端
├── fs-observation-policy/   文件观察策略
├── fs-sandbox/              文件修改范围限制
├── tool-fs/                 Agent 文件操作工具
└── tool-fs-search/          Agent 文件搜索工具
```

除 `fs-patch/` 和 `fs/` 外，上图是本阶段计划的目录，按各包实际引入时创建。辅助包按各自职责确定位置，不因依赖文件系统工具而自动放入 `fs/`。测试放在所属一级模块的 `src/agents/tests/`，不在各包下另建 `tests/`；引入时同步工作区清单、构建配置及相关目录说明。

## 依赖关系与实施顺序

已核对的关系是：`dsh-fs-patch` → `dsh-fs` → `dsh-fs-local` → `dsh-fs-sandbox`；`dsh-fs-local` 也直接依赖补丁库。观察策略依赖文件契约和事件，不依赖本地后端；文件工具依赖文件系统服务，观察策略和沙箱是可选组合，不是工具的必需依赖。搜索工具通过子进程执行 ripgrep，不依赖文件系统工具；本计划先完成文件工具再做搜索，是为了验证搜索结果能在同一授权视图中读取。箭头仅表示本段所列依赖，完整包依赖须对固定提交展开。`dsh-fs-sandbox` 扩展本地后端，运行时作为 `ctx.fs` 后端使用，而非同时注册两个后端。

## 逐包实施

### 1. `dsh-fs-patch`：补丁基础库

- 详细开发步骤见 [`dsh-fs-patch` 开发计划](world-initialization-stage-4-fs-patch-plan.md)。
- **前置**：固定上游提交，核对本包的直接与传递依赖；先接入其必需辅助库。
- **开发**：引入补丁解析与处理所需实现，保留官方格式和错误语义，调整包引用和构建配置；记录实际保留的接口及本地改动。
- **验收**：包在干净工作区可构建；用固定样例检查新增、修改、删除、移动补丁的解析、hunk 应用及无效补丁拒绝。此步只验证库，不声称 Agent 已能修改文件。

### 2. `dsh-fs`：文件系统契约

- 详细开发步骤见 [`dsh-fs` 开发计划](world-initialization-stage-4-fs-plan.md)。
- **前置**：步骤 1 的补丁依赖可用；核对上游 `dsh-fs` 的其他依赖与 Cordis 版本。
- **开发**：接入 `ctx.fs` 服务契约、路径和错误类型及文件事件；核对本项目作用域和类型定义，保留后端与工具之间的官方接口。
- **验收**：类型检查和构建通过；以受控替身验证服务注册、获取与释放，以及工具和后端需要的契约。此步不提供本机文件访问。

### 3. `dsh-fs-local`：本机文件后端

- 详细开发步骤见 [`dsh-fs-local` 开发计划](world-initialization-stage-4-fs-local-plan.md)。
- **前置**：步骤 1、2 完成；核对 `chokidar`、`koffi` 等固定版本实际依赖及平台兼容性。
- **开发**：接入本地文件系统提供方，验证文本读取、创建、修改、补丁、删除和移动所需操作及版本检查；明确文件句柄和监听资源的归属与释放。
- **验收**：在临时目录验证读写、删除、文件不存在、非文本和失败行为，以及选用的版本保护；验证关闭后资源释放。`cwd` 只作为路径解析基准，本步骤不把它宣称为授权边界，也不向生产 Agent 暴露未受限后端。

### 4. `dsh-fs-observation-policy`：文件观察策略

- 详细开发步骤见 [`dsh-fs-observation-policy` 开发计划](world-initialization-stage-4-fs-observation-policy-plan.md)。
- **前置**：步骤 2 的契约完成；步骤 3 的本地后端用于集成验证，并非该策略的必需依赖。检查上游策略依赖和事件契约，单独接入实际必需的辅助包。
- **开发**：接入文件观察事件和修改前状态检查，明确观察状态的作用域与释放方式，验证其与本项目 Agent 生命周期的关系。观察策略不承担路径授权。
- **验收**：验证按选定策略读取后修改、未观察文件修改、文件在观察后变化的处理，以及 Agent 销毁时清理；不将该策略误称为目录沙箱。

### 5. `dsh-fs-sandbox`：文件修改边界

- 详细开发步骤见 [`dsh-fs-sandbox` 开发计划](world-initialization-stage-4-fs-sandbox-plan.md)。
- **前置**：步骤 2、3 完成；逐项检查 `dsh-sandbox`、`dsh-sandbox-policy` 等依赖，将选定实现所需的服务分别接入并验证。
- **开发**：评估并接入官方修改限制，明确可信应用如何指定每个 Agent 的工作区和草稿可写范围；如果官方组件不适合项目契约，记录原因并实现满足相同边界的最小适配。另行落实读取和搜索的授权，不能假设上游修改沙箱限制了读取。
- **验收**：验证允许范围内的修改和删除，以及绝对路径、父目录遍历、符号链接等越界拒绝；验证只读授权无法修改。读取、搜索和已确认资料的保护在相应工具与集成步骤继续验证。

### 6. `dsh-tool-fs`：模型文件工具

- **前置**：步骤 1 至 3 及本项目选定的授权机制完成；步骤 4、5 是计划采用并验证的策略组合，不是官方工具的必需依赖。逐项核对官方 `tools`、`fs`、`systemPrompt`、`workingDirectory` 及其依赖，解决与项目服务的接口差异。
- **开发**：复用并注册 `read`、`write`、`edit`、`apply_patch`；显式启用补丁能力，删除通过补丁执行。图片工具暂不装配。检查现有 `read_file` 和 Skill 资源访问调用方，确定保留或替换方式并同步引用。
- **验收**：通过项目实际工具服务验证读取、创建、编辑、补丁删除和错误结果；覆盖不存在文件、授权范围外读取与修改、符号链接越界及文件状态变化。验证多文件补丁的部分成功或结果未知时如实报告，不假定失败自动回滚。工具随所属作用域注销。

### 7. `dsh-subprocess` 及本地提供方：搜索执行基础

- **前置**：核对固定版本 `dsh-tool-fs-search` 实际要求的子进程接口、提供方、超时策略及其依赖；必要辅助包分别接入。
- **开发**：逐包接入搜索所需的子进程契约和本地提供方，复用官方进程启动、取消、输出与清理能力；明确搜索执行目录及资源所有者。超时策略如为独立包，单独接入并验证。
- **验收**：用固定测试子进程验证启动、退出、错误、取消、超时及所属作用域销毁后的清理；不通过 Shell 拼接模型提供的命令。

### 8. `dsh-tool-fs-search`：文件搜索工具

- **前置**：步骤 7 及搜索工具所需的项目服务完成；步骤 6 用于跨工具集成验收，并非上游搜索工具的依赖。引入并检查 `@vscode/ripgrep` 与选定版本的其他实际依赖。
- **开发**：复用并注册 `glob` 和 `grep`，让可信应用提供搜索范围；搜索视图与文件读取授权一致，结果截断和错误保持明确。
- **验收**：验证路径和内容匹配、无结果、截断、执行失败、取消和超时；验证搜索不能返回授权范围外的路径或内容，搜索结果可在同一视图中读取。

### 9. 主、子 Agent 装配与端到端验证

- **前置**：上述包及必要辅助包的验收通过。
- **开发**：由可信应用为世界初始化主 Agent 配置工作区和工具；子 Agent 的读取与修改权限单独配置。对照现有 `read_file`、Skill 资源访问和方案工作区规划，更新入口、相关文档及架构说明。
- **验收**：用固定模型替身通过真实注册和执行链完成读取、搜索、草稿创建、修改与删除；验证不同 Agent 的授权边界、子 Agent 无法改写已确认资料，以及失败、取消和销毁后的清理。运行相关聚焦测试、类型检查和必要的构建产物冒烟检查；真实模型检查单独报告是否执行。

## 阶段交付

交付逐包来源与依赖清单、固定提交、许可证、本地适配与更新方法；记录各包实际验收结果、未引入的候选包及原因。主、子 Agent 的文件工具仅在明确授权的工作区工作；已确认资料仍经业务层受控提交。未解决的兼容、平台或验证限制明确记录，不将文件工具描述为已完成的世界资料业务接口或长期持久化方案。
