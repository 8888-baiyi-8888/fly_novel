# 世界初始化第二阶段：基础主 Agent 开发计划

本文规划[世界初始化开发计划](world-initialization-development-plan.md#2-基础世界初始化主-agent)中的基础主 Agent。世界初始化的使用场景和业务要求见[第一阶段计划](world-initialization-stage-1-plan.md)。

本阶段按以下顺序推进：编写主 Agent 专有系统提示词，定义专有提示词插件，创建 Skill 相关工具，实现主 Agent 的创建，最后实现和验证理解用户构想与规划等功能。每一步先讨论实际使用方式、输入输出和预期行为，确认后再实现；完成并验证后等待用户指示，不自动进入下一步。

## 阶段目标

建立一个基于现有 Harness 的世界初始化主 Agent。它能够理解用户的创作构想，必要时与用户多轮澄清，展示自己的理解，并在理解得到确认后识别世界规划重点、组织初步方案。主 Agent 可以通过 Skill 工具按需获取相关指导。

本阶段先验证主 Agent 自身的能力；子 Agent 的创建与委派、主子 Agent 协作生成完整第一版、世界资料管理和冲突处理，分别在[后续开发阶段](world-initialization-development-plan.md#开发阶段)实现。

## 1. 编写主 Agent 专有系统提示词

### 要解决的问题

主 Agent 需要明确自己的身份、目标和职责，知道如何理解用户的构想、何时询问、如何归纳理解结果，以及如何在后续进行世界规划。用户提供的内容可能很少，也可能杂乱；Agent 需要主动理解，不能依靠固定题材清单决定重点。

### 提示词需要涵盖的内容

- **身份与目标**：负责世界初始化，围绕可持续演化的世界开展规划；世界不只是某部小说或某个主角的背景。
- **理解用户构想**：理解创作方向和明确要求，对模糊或矛盾的内容按需多轮询问，向用户展示理解结果；这一过程不擅自补充世界设定。
- **识别规划重点**：理解确认后，根据具体构想确定需要规划的世界内容、重点和详略，不把示例类别当作强制栏目。
- **主动规划**：Agent 负责提出有意义的世界方案和故事规划，用户通过审阅和修改参与，不要求用户先补齐主要设定。
- **保持演化空间**：区分已经发生的事实与未来规划，不预先固定所有事件过程、角色选择和结局；角色可以有独立目标与成长方向。
- **按需使用 Skill**：当已提供的 Skill 与当前任务相关时，按工具提供的方式获取指导；具体使用机制在第 3 步确定。

提示词的具体文本、内容组织和是否拆分为多个段落，在本步结合使用示例讨论。用户确认、超时和正式资料更新属于程序控制边界，不能只靠提示词保证。

### 验收

提示词能清楚表达主 Agent 的职责和边界，并能用不同世界构想检查是否存在固定题材假设。此时先审阅提示词内容，不要求已经完成插件注册或主 Agent 创建。

## 2. 定义主 Agent 专有提示词插件

### 要解决的问题

把第 1 步编写的主 Agent 提示词接入现有 Harness，让主 Agent 创建时获得自己的系统提示词，并与其他 Agent 的提示词隔离。

### 开发内容

- 参考现有[导演 Agent 提示词插件](../../../src/agents/director/system-prompt-plugin.ts)，通过项目的 SystemPrompt 服务注册主 Agent 专有提示词。
- 明确插件依赖、注册定义以及加入现有插件注册表的方式；插件作用域结束时清理其注册内容。
- 保持提示词插件与后续 Skill 工具的职责清晰；Skill 工具的创建与装配在后续步骤处理。

### 验收

验证主 Agent 的提示词能通过插件注册并组装到模型请求中；其他 Agent 不受影响，销毁时专有注册得到清理。提示词内容变化应同步检查相关文档和测试。

## 3. 创建 Skill 的相关工具

### 要解决的问题

让主 Agent 知道有哪些可用 Skill，并能在任务需要时读取相应指导内容。Skill 承载可按需使用的指导；它和工具注册执行能力、主 Agent 的专有系统提示词是不同职责。

### 参考实现

参考 DeepSeek Harness 的 [Skill 子系统](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/skills.md)、[Skill 工具](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/skill/tool-skill/README.md)及[文件系统 Skill 提供方](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/skill/skill-filesystem/README.md)。其实现区分 Skill 注册与来源、文件系统发现，以及面向模型的 Skill 目录与加载工具；开发前核对实际源码与参考版本，再决定本项目需要的最小能力，不直接假定所有上游能力都适用。

本项目已有 [Tools 服务](../../../src/agents/plugins/tools/README.md)，提供工具定义、注册和执行；需要结合该扩展点确定 Skill 如何接入。Skill 的发现、提供和读取如何分工，以及哪些能力需要独立服务或插件，应先通过实际使用方式讨论，不预先规定包结构。

### 开发内容

1. 明确 Skill 从哪里提供、如何被发现，以及主 Agent 能看到哪些 Skill 的名称和用途。
2. 设计主 Agent 按需获取 Skill 内容的工具，包括输入、输出、未找到或读取失败时的行为。
3. 基于实际示例明确 Skill 文件或内容的组织方式，以及访问范围如何确定；用户通过 Agent 使用 Skill 时不必知道底层路径。
4. 将所需工具接入现有 Tools 和 Agent Loop，验证模型可以发现并调用它，读取结果进入后续模型交互。
5. 用完成验证所需的示例 Skill 检查完整路径；具体业务 Skill 的内容和数量依据主 Agent 的实际任务确定，不预先按每种世界或设定创建一套固定 Skill。

### 验收

能够以一个示例说明 Skill 从提供、发现到被 Agent 按需读取的过程。验证可用 Skill 的识别、正确内容返回、无匹配和读取失败，以及工具注册与清理；对照 DeepSeek Harness 解释采用的能力与未纳入本阶段的部分。

## 4. 实现主 Agent 的创建

### 要解决的问题

使用现有 Harness 创建一个可运行的世界初始化主 Agent，将它的专有提示词、Skill 工具及必要基础服务组合起来。

### 开发内容

- 参考现有[导演 Preset](../../../src/agents/director/preset.ts)及 [Harness 创建方式](../../../src/agents/README.md#cordis-harness)，定义主 Agent 的 Preset，并按现有注册方式加入可创建的 Agent。
- 装配完成运行所需的 Agent Loop、Session、SystemPrompt、LLM 及相关 Skill 工具；模型路由和适配器由应用按现有方式提供。
- 根据主 Agent 的实际身份处理现有 `AgentRole` 类型，确定创建参数、实例归属和释放方式，不另建一套重复的 Agent 创建框架。
- 提供足以验证创建、调用和销毁的使用入口；具体入口形式先讨论确认。

### 验收

能够创建主 Agent，确认其获得预期插件与工具，并完成一次受控调用；验证创建失败、模型调用失败和实例销毁时的行为。主 Agent 的服务和状态应与其他 Agent 实例隔离。

## 5. 实现主 Agent 的相关功能

### 5.1 理解用户构想

用户输入可能零散、详细程度不一。主 Agent 需要识别用户表达的创作方向与明确要求；遇到影响理解的模糊或冲突，可以反复询问用户，再整理和展示自己的理解。

**使用示例**：用户提出“想写非常规修仙世界，法无好坏，人有好坏，角色有自己的判断”。主 Agent 可就含义不明之处提问，结合用户回答展示理解结果；在这一过程中不擅自补充门派、地区或角色设定。

**验证**：通过同一 Agent 的多轮交互检查用户输入、澄清、修正和理解结果是否衔接；使用固定模型替身验证输入输出及会话行为，并结合实际模型输出审阅理解质量。

### 5.2 识别规划重点并组织初步方案

在理解结果确认后，主 Agent 根据用户构想判断世界需要重点规划什么，选择合适的内容和深度，主动组织初步方案。具体业务方向参考[第一阶段的第一版内容说明](world-initialization-stage-1-plan.md#2-生成第一版供审阅)；本阶段用于验证单个主 Agent，不代替后续主子 Agent 协作完成的第一版。

主 Agent 可以按任务需要使用第 3 步提供的 Skill 工具。它应给出有实际内容的规划，而不是只列出栏目并让用户补齐；不同地区、角色和故事可以详略不同，未来事件和角色成长保留演化空间。

**验证**：使用至少两个规划重点不同的构想，检查 Agent 是否根据输入调整重点、是否主动提出具体规划，以及是否按需使用 Skill；区分固定模型替身的交互验证与真实模型的内容质量评估。

### 5.3 与用户确认的边界

第一阶段约定：理解结果由用户确认；用户在系统配置的等待时间内没有回复等行为时，默认该次理解符合想法。确认针对展示的理解结果，不自动确认后续方案。

本步需要结合实际运行入口，确定如何将用户确认或超时结果交给主 Agent，再进入规划。系统配置、等待和确认由程序负责，不能仅靠提示词或模型自行判断；具体程序接口和实现范围在本步结合使用示例确认。

## 阶段验收

1. 主 Agent 拥有专有系统提示词，并通过现有插件和 Preset 机制创建。
2. Skill 能被发现并按需读取，主 Agent 可以通过工具使用；相关错误和资源清理有验证。
3. 主 Agent 能在同一会话中接收构想、多轮澄清、接受修正并展示理解结果。
4. 理解结果经确认后，主 Agent 能识别规划重点并组织初步方案；不同构想的示例不依赖固定题材清单。
5. 用户确认及超时的程序边界与本阶段实际实现保持一致；未实现的行为明确说明，不把提示词约束当作程序保证。
6. 运行与实际变更相关的测试和示例；真实模型验证缺少配置或凭据时说明未执行。对照 DeepSeek Harness 对应实现，解释主要设计异同。

第二阶段完成后等待用户指示，再进入子 Agent 委派机制的开发。
