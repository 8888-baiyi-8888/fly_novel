# 建立角色创建子 Agent：详细开发计划

本文细化[角色创建计划的第 2 步「建立角色创建子 Agent」](world-initialization-stage-5-character-creator-plan.md#2-建立角色创建子-agent)，并列出其所需提示词、资料工具、Agent 装配和委派验证的实施顺序。业务职责与场景见角色创建计划，资料、分类与查询设计见[角色资料与分类读取设计](character-information-design.md)。本文件是开发计划，不代表计划中的 Agent、角色资料服务或共享工作区已实现。

## 目标和范围

角色创建 Agent 可独立运行，也可作为子 Agent 接受世界初始化主 Agent 委派。它根据世界背景和近期故事创建一个或多个角色、主动设计角色关系，并根据用户要求修改指定的现存角色。第一梯队以约十人以内为初始化参考；第二、第三梯队只创建近期故事需要的人物，其他角色随故事发展按需补充。角色越重要，规划越深入；不将示例字段和题材分类强加给所有世界。

本步交付独立 Agent、角色资料服务和专用工具、持续 Session、主 Agent 委派入口及受控目录中的端到端验证。角色资料按[资料设计](character-information-design.md)保存，程序分配 ID，支持按名称和多维分类查找与批量读取；修改先形成待审内容，可信确认后由受控入口提交。整体影响检查、用户确认界面、工作区资料目录和长期记忆按后续流程实现。角色设定是建议，保存或工具成功不代表用户确认。

可信应用显式提供测试世界、角色根、读取范围、Agent 稳定身份和 Session 存储配置；模型不能通过参数授予目录或世界权限，不预设生产世界根目录。共享工作区第 3 步尚未完成时，只在受控测试目录验证本步实际实现的权限和文件行为，不声称已完成跨世界或跨 Agent 生产隔离。

## 实施前核对

1. 阅读[通用子 Agent Preset](../../../src/agents/generic-subagent/preset.ts)、[通用创建器](../../../src/agents/runtime/subagent-in-process-creator.ts)、[通用委派工具](../../../src/agents/plugins/subagent/tool-subagent/index.ts)、[Agent Loop](../../../src/agents/plugins/loop/README.md)和[Session 持久化契约](../../../src/agents/plugins/session-persistence/README.md)，核对提示词、工具注册、取消、清理及 Session 恢复方式。
2. 核对[受控世界初始化入口](../../../src/app/agents/world-initialization.ts)、文件读取与沙箱、相关测试及[工作区契约](world-initialization-stage-5-workspace-plan.md#1-核对现状并确定工作区契约)。确认当前 Spawn 通用创建器拒绝子 Agent 的持久化 Session ID；Fork 复制受限父会话历史，也不提供角色创建 Agent 的持续会话。
3. 根据实际入口与测试更新实施细节，保留用户修改。持久化格式、确认与恢复语义在创建真实数据前确定；未知版本必须拒绝或按明确迁移规则处理，不删除或静默误读用户数据。

## 1. 固化任务和资料契约

1. 用两个场景验证职责：根据世界和近期故事创建不同层级角色；用户选择现有角色后，只对该角色形成待审修改。分别列出任务要求、可读取资料、返回结果、资料缺失及建议与确认的区别。
2. 用户明确数量时按用户要求处理；未指定时使用可信配置提供的默认数量，结合实际需求生成，不为了凑数创建无用途角色。首版建议默认值为 3，该值是设计建议，不是已由用户确认的业务契约；应用入口应校验为正整数。
3. 以资料设计为依据，细化角色文件、角色需求、索引与分类的可解析格式、状态、版本、错误和恢复机制。明确用户要求、建议、待审与已确认的表示；角色名称可重复，名称查询返回候选并用 ID 定位。
4. 委派请求包含非空任务及必要背景，角色创建 Agent 可使用授权工具补充资料；缺少资料时向调用方说明，不虚构已确认内容。回复使用自然语言，不要求统一的角色正文结构。

**验收**：示例能说明输入、资料来源、角色输出、缺口和确认边界；各持久化格式及异常行为足以编写测试，尚未确定的建议不写成已确认事实。

### 场景走查：创建近期故事所需角色

- **任务与输入**：用户要求围绕宗门失踪案创建调查者和相关人物，明确要求调查者不得违背宗门限制；世界资料说明宗门禁止私自调查。调用方传入任务和可定位的故事线索，读取范围由可信应用提供。
- **读取与处理**：Agent 读取授权的世界与故事资料，查找已有角色和需求清单。已有合适人物时关联其 ID；确有缺口时创建所需角色，主动构思不同立场和人物关系。用户指定数量优先；没有指定数量时按可信配置的默认数量，并结合实际需求，不为凑数制造角色。
- **结果与状态**：角色资料服务生成 ID，创建逐角色文档及索引；用户要求与 Agent 补充的动机、关系分别表达，生成内容标为建议。自然语言回复概述已创建人物、可定位信息和未解决问题；保存成功不代表用户确认。
- **资料不足**：若无法读取宗门限制，Agent 报告缺少该资料，不能宣称已检查规则；可标明待定并返回调用方，不编造为已确认背景。

### 场景走查：修改已选角色

- **任务与输入**：用户在修改入口选中一名现存宗门长老，要求其更重视宗门稳定，同时保留与弟子的既有关系；调用方提供已选择角色的定位信息和修改要求。
- **读取与处理**：Agent 读取该角色当前资料及有权读取的必要背景，在候选中修改其动机和相关描述；不修改弟子或宗门资料。名称重合时先返回候选供选择，不自行选人；角色缺失、读取失败或无权读取时报告，不能转为创建新角色。
- **结果与状态**：服务保存独立待审候选与当前资料基线，保留原资料和当前索引；Agent 自然语言说明修改及未定内容。用户继续讨论时更新候选；整体影响检查及用户确认由后续流程负责，可信提交前不得覆盖当前资料。
- **确认与失败**：受控提交绑定经确认的候选与原资料基线；任一内容变化则拒绝提交并重新检查。保存或提交失败报告实际阶段，保留候选和可恢复资料；详细恢复规则以[资料设计](character-information-design.md#创建修改与索引一致性)为准。

两例是可验证的任务样例，不代表指定角色或故事已成为世界事实；详细结构及异常路径由资料设计维护。

## 2. 建立角色创建系统提示词插件

1. 沿现有角色和导演的 SystemPrompt 插件、插件定义及 Preset 注册方式，建立角色创建专用提示词插件。该插件表达角色设定的创建、完善和修改职责，不使用角色扮演提示词，也不承担程序授权或文件写入校验。
2. 提示词引导 Agent 根据世界背景与近期故事识别角色需求，先检查现有角色，再创建需要的人物；主动设计人物关系，并按重要程度决定规划深度。第一梯队参考约十人以内，第二、第三梯队只为近期故事按需创建；不把参考数量当作严格上限或角色总数。
3. 规定用户明确的数量及要求优先；未指定数量时使用可信配置提供的默认值。配置的具体默认值仍是待确定的业务选择，不将建议值表述为用户已经确认。
4. 提示词区分用户要求、Agent 建议、待审修改与已确认资料；资料不足时先使用获授权的资料工具，仍不足时向调用方说明。修改仅处理指定角色本身，不直接改写其他角色或世界资料；输出自然语言及可供后续读取的资料。
5. 使用固定模型替身验证专属提示词进入实际模型请求；针对创建多个角色、修改现有角色、资料不足及用户指定数量检查提示词内容与输入传递。固定模型测试不证明真实生成质量。

**验收**：插件可按现有机制注册和释放，独立 Agent 能装配该职责；提示词明确角色规划、修改、资料不足及确认边界，不含角色扮演职责。

## 3. 建立角色资料专用工具

1. 按[角色资料与分类读取设计](character-information-design.md)建立可信角色资料服务，由程序生成稳定角色 ID；调用方提供可信角色根目录，模型不提供路径授权或自行分配 ID。资料服务负责角色文件及名称、多维分类索引；具体包归属以现有模块职责和依赖为准。
2. 提供创建、名称与分类查找、按 ID 单个或批量读取，以及准备现存角色待审修改的工具。先按名称查询候选，再使用 ID 定位；同名不自动选中。分类按世界需求扩展，批量结果逐项报告成功和失败，并说明分页或读取不完整。
3. 支持角色需求记录，让 Agent 根据世界及近期故事检查现有角色和未满足需求；第二、第三梯队随近期故事按需补充，不预建未来所有角色。输入资料缺失时记录或返回缺口，不虚构已有角色及已确认事实。
4. 修改时保留原资料、候选和基线；工具执行成功不代表用户确认。可信提交入口必须绑定经确认的候选及基线，提交前检查变化并保留备份；用户确认界面与整体冲突修复在后续流程实现。文件与索引部分更新时明确报告状态并保留恢复信息。
5. 按资料设计定义格式版本、无效数据拒绝、索引重建、并发冲突和失败恢复；测试 ID 碰撞、同名角色、多分类批量查询、缺失和损坏文件、未知版本、待审隔离及取消。测试使用可信应用提供的受控临时目录，不宣称完整共享工作区权限已实现。

**验收**：Agent 通过专用工具创建和读取角色资料，ID 由程序生成；现有角色修改不覆盖未确认资料，角色索引与实际文件一致或明确报告不一致。

## 4. 组装角色创建 Agent

1. 基于现有 Preset 和插件注册机制，组合第 2 步提示词插件、第 3 步角色资料工具、标准 Agent Loop、LLM 和 Session；建立可信应用创建入口，使 Agent 能独立接收创建及修改任务。模型路由、默认数量、角色资料根和可用工具由可信应用装配。
2. 复用项目现有 Session 持久化机制：应用显式装配 `sessionPersistence` 后端；首次通过 `sessionId` 创建，重新实例化时通过 `resumeSessionId` 恢复。稳定 Agent 身份与 Session ID 的对应关系由可信应用提供；恢复不存在的会话和重复创建已有会话按现有机制报错，不静默新建或覆盖。
3. 通过固定模型替身验证同一 Agent 多轮处理创建和修改任务；销毁后重建并恢复原 Session，检查之前的对话进入请求。Session 保存对话，不代替角色资料、确认状态或长期记忆；会话压缩和记忆模块不在本步实现。
4. 处理实例初始化失败、运行取消和释放；等待 Loop 与 Session 收尾，避免同一 Session 被并发写入。依据[工作区契约](world-initialization-stage-5-workspace-plan.md#1-核对现状并确定工作区契约)安排同一世界和 Agent 身份的独占与失败清理，不宣称现有后端已提供跨进程并发保护。

**验收**：可信调用方可独立创建角色创建 Agent、交付任务、释放并恢复原 Session；专属提示词、角色工具与模型路由在真实运行链中生效。

## 5. 接入主 Agent 委派

1. 建立角色创建专用委派工具，由可信应用绑定角色创建 Agent 的 Preset、世界、稳定身份、模型及 Session 配置；模型只提供本次业务任务与所需背景。保留现有通用 `delegate` 和角色扮演 `delegate_character` 的职责。
2. 使用独立的 `persistent` Provider 和共享运行驱动，由可信创建函数装配角色创建 Agent 的持久化 Session；普通 `spawn` 保持独立会话约束，不使用 Fork 的父会话快照代替子 Agent 自己的会话。
3. 委派工具拒绝空任务和错误父身份，等待子 Agent 结果并释放运行；启动、执行、取消和释放失败明确报告，执行与释放同时失败保留两个原因。将工具注册到可信主 Agent 入口并随作用域清理。

**验收**：主 Agent 经专用工具、`persistent` Provider 和角色创建 Agent 接收结果；后续委派可继续该 Agent 自己的 Session，父会话不被误当作子 Agent 会话；取消和作用域释放无资源遗留。

## 6. 集成验证与交付

1. 使用固定模型替身完成两个场景：根据世界和近期故事创建多个不同层级角色，程序生成 ID 并保存资料；按名称定位既有角色，形成待审修改，重建 Agent 后继续讨论。核对实际模型请求、文件、索引、Session 和委派结果。
2. 覆盖资料不足、同名、多维分类批量读取、索引失效、待审与当前资料区分、可信提交、启动失败、取消、父作用域销毁和清理失败。以受控测试目录和可重复替身验证，不将测试替身称为真实模型质量验证。
3. 更新实际受影响的模块 README、架构和必要 Agent Note；执行对应聚焦测试、类型检查及必要构建，检查文档链接和 Git 空白。共享工作区跨 Agent 权限、跨世界隔离和资料目录仍按后续步骤实施验收。

**交付验收**：角色创建 Agent 可以独立运行并被主 Agent 委派；专属提示词、角色资料工具和现有持续 Session 机制协同工作，任务成功与失败、取消及释放均可验证。
