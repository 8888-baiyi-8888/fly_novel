# 文件能力第三包：`dsh-fs-local` 本机文件后端开发计划

本文细化[第四阶段的 `dsh-fs-local` 步骤](world-initialization-stage-4-file-tools-plan.md#3-dsh-fs-local本机文件后端)。目标是复用上游本机文件系统提供方，对接项目文件服务契约，并以临时目录和真实文件操作验证其行为。用户指定以下载的官方源码快照为本包依据，来源及哈希见[包说明](../../../src/agents/plugins/fs/fs-local/README.md)。

## 范围和边界

计划在 `src/agents/plugins/fs/fs-local/` 建立独立工作区包，测试放在 `src/agents/tests/`；前置包为 [`@fly-novel/fs`](../../../src/agents/plugins/fs/fs/README.md) 和 [`@fly-novel/fs-patch`](../../../src/agents/plugins/fs/fs-patch/README.md)。实施按下列编号逐步进行，每步先完成验收，再进入下一步。

本机后端提供文件操作，不提供模型工具、观察策略或路径授权。`cwd` 是相对路径解析基准，绝对路径、父目录和符号链接不能因设置了 `cwd` 就被视为受限；未经后续授权机制保护，不向生产 Agent 装配该后端。测试仅使用独立临时目录和可信路径，不把临时目录当作安全沙箱。

文件契约暂时移除了上游 `sandboxMode` 与修改方法的 `sandboxPolicy` 参数；本包适配这一现状并记录差异，不单独引入 `sandbox-contract` 或通用沙箱。接入 `dsh-fs-sandbox` 前再对照上游恢复并验证所需契约。本阶段不接入观察策略、文件工具或搜索工具。

## 1. 核对上游、依赖和接入方式

1. 获取固定提交 [`fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159` 的 `fs-local`](https://github.com/deepseek-ai/deepseek-harness/tree/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/fs/fs-local)，逐项检查包清单、源码、公开入口、配置、测试及仓库和文件级许可证；记录版本、文件清单、版权声明和更新来源。若固定提交不可获取，记录阻塞，不以其他版本的内容冒充已核对基线。
2. 区分运行时、类型、构建和测试依赖，确认 `chokidar`、`koffi` 等是否实际使用、使用位置、版本与许可证；核对 Node.js 24、项目 CommonJS 构建、Cordis 版本和 Windows 平台兼容性，以及原生模块安装、加载失败与其他目标平台的处理。不能仅凭依赖名称假设其可选或必需。
3. 对照上游调用点与项目 `fs`、`fs-patch` 的类型和运行时身份，列出导入、错误、方法签名、沙箱参数和服务注册的差异；确认后续 `fs-sandbox` 继承或消费的公开接口。发现必需但不兼容的辅助包时，将其作为独立前置任务，不用空类型或关闭检查绕过。
4. 比较官方发布包与固定提交源码同步的依赖、模块格式和适配成本；选定后记录理由，不因版本号相同就假设内容一致。核对上游实现对锁、原子发布、文件监听、取消和平台能力的真实保证，列出不能验证或需要适配之处。

**验收**：形成来源、许可证、依赖及接口映射，明确平台支持、待解决问题和最小本地改动；不可获取或不兼容的问题有明确处理方式。

### 第 1 步核对结果

**来源与范围。** 上游固定提交为 [`fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159`](https://github.com/deepseek-ai/deepseek-harness/tree/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/fs/fs-local)。已读取该提交的[入口](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/fs/fs-local/src/index.ts)、[README](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/fs/fs-local/README.md)和 [`fs-sandbox` 入口](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/fs/fs-sandbox/src/index.ts)。README 列出的实现文件为 `src/index.ts`、`src/fsio.ts` 和 `src/win32.ts`；后两个文件、固定提交的包清单与测试尚未取得，不能把发布包内容认作已核对的固定源码。

**发布包与许可。** 已下载并检查 [npm 发布包 `@deepseek-ai/dsh-fs-local@0.2.2-rc.1`](https://www.npmjs.com/package/@deepseek-ai/dsh-fs-local/v/0.2.2-rc.1)：包内许可证为 MIT，版权声明为 `Copyright (c) 2026 DeepSeek`；包含编译后的 `lib/index.js`、类型声明、文档、许可证和语言文件，不含 TypeScript 实现及测试。包元数据没有 `gitHead`，不能仅凭版本号断定与固定提交完全一致。同步源码时须再次核对固定提交的文件级声明并保留适用许可。

**依赖与平台。** 发布包为 ESM；运行依赖为 `chokidar@5.0.0`、`koffi@3.1.1`、`@deepseek-ai/schemastery@~3.19.0`、`@deepseek-ai/dsh-fs-patch@0.2.2-rc.1`，peer 为 `@deepseek-ai/cordis@~4.1.0` 和 `@deepseek-ai/dsh-fs@0.2.2-rc.1`。固定提交入口静态导入 `chokidar` 用于监听、`schemastery` 用于配置；发布包在 Windows 替换路径惰性加载 `koffi`，调用 Windows API 复制 DACL 和替换文件。`chokidar@5.0.0` 和 `koffi@3.1.1` 的 npm 元数据均声明 MIT；前者要求 Node.js `>=20.19.0`。固定提交清单、完整测试及构建依赖和其他平台的行为仍须核对。

当前 Windows x64、Node.js `v24.20.0` 临时安装发布包后，CommonJS `require` 可加载其公开入口，并可通过 `koffi` 加载 `advapi32.dll`、`kernel32.dll`。npm 12 阻止了 `koffi` 自动安装脚本；在临时目录单独执行该包声明的安装脚本成功。该冒烟不验证 pnpm 冻结安装、原生加载失败、DACL、实际文件操作或其他平台，也不代表项目构建兼容已通过。

**接口映射和接入决定。** 固定提交的 `LocalFileSystem` 继承上游 `FileSystem`，入口消费 `FsError`、`FsVersion` 和 `Fs*` 类型，并使用 `fs-patch` 的 `applyHunks`、`PatchHunk`；发布包还从 `fs` 导入 `FsTargetKey`。本地适配时分别改用 `@fly-novel/fs` 与 `@fly-novel/fs-patch`，使错误、服务基类及品牌类型保持项目身份；显式在可信调用方的实例作用域注册服务。项目 `fs` 已移除 `sandboxMode` 和修改方法的 `sandboxPolicy`，而上游沙箱子类继承 `LocalFileSystem` 并对五种修改加策略检查；接入沙箱前须恢复并验证必要契约。本阶段不接入沙箱。官方包直接依赖上游 `fs` 和不同 Cordis 版本，优先按固定提交同步源码并适配项目包，发布包用于对照；具体源码和构建适配须在后续步骤验证。

**行为边界。** 固定提交入口的锁属于后端实例；不推断跨实例或跨进程互斥。监听等待 `ready`，初始化失败关闭监听，成功后由调用方关闭；文件监听过滤父目录事件。上游 README 描述同目录暂存后发布、移动按目标顺序加锁并先发布目标再删除源，源删除失败以 `sourceDeleted: false` 报告；Linux 父目录删除重建后的监听恢复未提供。`cwd` 仅作路径解析基准，不提供授权。这些是上游代码或文档结论，不代表本项目已完成真实后端验证。

**验收状态。** 部分核对完成，尚未取得固定提交的辅助源码、测试和包清单，无法完成逐项来源、依赖和文件级许可核验。恢复固定来源后先完成这些检查并更新本节，再按验收条件决定是否进入第 2 步；不以发布包或其他提交冒充固定源码。

## 2. 建立工作区包和明确装配方式

本步骤按用户指定的官方源码快照实施；该快照没有可核验的提交标识，不沿用第 1 步的固定提交作为其身份。源码哈希、许可证、导入调整和更新方式见[包说明](../../../src/agents/plugins/fs/fs-local/README.md)。

1. 按第 1 步结论建立独立包，引入固定来源源码及适用许可证，配置公开入口、声明、依赖和构建；同步工作区清单、锁文件、必要的源码路径映射及构建边界，保证源码检查与产物检查各有明确前置条件。
2. 按现有契约适配导入和必要签名，逐项记录改动及对后续 `fs-sandbox` 的影响；不顺手改写无关算法。包导入不自动创建后端或访问磁盘。
3. 对照项目 Harness 的 `provide: 'fs'`、实例作用域和依赖启动规则，确定可信调用方如何显式装配后端及其配置；不修改生产 Preset，不在根作用域隐式注册后端。测试中验证未装配实例无法继承根文件服务、两个实例互不替换以及初始化失败后的清理。
4. 包 README 记录来源、许可证、公开入口、配置、无授权边界、平台限制、本地改动和更新步骤；同步受影响的 `AGENTS.md`、Agent 目录说明和架构文档，按项目规则记录重要决定。

**验收**：包的来源可追溯，依赖和构建配置完整；仅可信测试显式装配后端，服务随所属作用域注册和释放，生产 Agent 没有获得文件访问能力。

## 3. 路径、元数据和读取

1. 在每项测试独立创建的临时目录中验证相对路径与 `cwd`、绝对路径、缺失目标、路径别名及规范化；覆盖 `resolve`、`processPath`、宿主路径映射、文件 URI、`contains` 与目标标识的一致性。检查文件及目录符号链接、最终分量 `lstat` 和 `stat` 的差异；平台不支持符号链接时报告原因，不静默作为通过。
2. 验证常规文件、目录、缺失目标及实际可构造的特殊文件的元数据和单层列表；检查稳定排序、目录项类型、错误映射和列表不读取正文。按固定上游实际行为记录平台差异。
3. 验证完整文本、分块文本、跨块 UTF-8、换行及二进制或无效文本的处理；对照上游实现确认判定规则，不能凭样例推断支持任意编码。验证 `readBytes` 的包含上限、超限失败，以及字节窗口在文件尾和越界时的结果；检查不返回截断结果冒充完整读取。
4. 覆盖可观察的取消、文件不存在、非文件、权限或 I/O 错误及底层原因；权限用例在特权账户或平台无法可靠制造拒绝时明确跳过原因。验证打开的文件句柄和流在正常结束、失败及取消后释放。

**验收**：路径、身份、读取和错误行为符合项目契约及已记录的本地差异；平台限制和未执行的用例明确报告，不将路径解析视为授权。

第 3 步的 Windows x64 聚焦测试覆盖路径解析、目录链接、元数据和列表、跨块 UTF-8、字节边界、文件增长、取消及流关闭。文件符号链接在沙箱和宿主重试均因 `EPERM` 跳过；Windows `chmod` 不能可靠制造读取拒绝，权限用例需要受控 ACL 环境。当前环境未验证其他平台或特殊文件。读取采样和底层 I/O 错误边界见[包说明](../../../src/agents/plugins/fs/fs-local/README.md)。

## 4. 修改、版本保护和并发

1. 以真实临时文件验证创建、覆盖、字面编辑、补丁、删除和移动；覆盖无条件操作与创建、已有版本、过期版本等保护条件，确认错误码、返回的版本及修改前后内容。验证补丁不匹配、编辑无匹配或多匹配、同一目标移动和非普通文件的失败行为。
2. 对照上游验证 LF 与 CRLF、文件模式及目标发布行为；验证移动先发布目标、再删除源的结果，并通过可控的实际故障或可注入文件操作验证源删除失败时 `sourceDeleted: false` 及错误信息，不把整个移动说成原子事务。
3. 核对锁的作用范围和所有者，在同进程中以受控同步点测试同目标并发写入、版本竞争、相反方向移动和失败释放；验证不会丢失约定的保护或永久等待。对跨进程、外部写入与符号链接替换，仅声称实际实现和测试能够证明的保证，明确 TOCTOU 与操作系统限制。
4. 检查取消在发布前及提交阶段的契约、临时文件和句柄的成功与失败清理；使用可控失败验证残留与原内容，不凭空假设所有文件系统都提供相同原子性。区分已有目标、目标发布后和源删除前等可观察状态。

**验收**：修改结果、版本保护和部分失败符合文件契约；同进程竞争、取消及失败后的资源状态有可重复测试，未验证的跨进程与平台保证明确记录。

第 4 步使用真实临时文件及受控同步点验证创建、覆盖、编辑、补丁、删除、移动、版本保护、实例内竞争、取消和失败清理；源删除失败及发布后清理失败的部分结果单独验证。Windows 不提供 POSIX 模式位语义，模式位用例跳过；未验证其他平台、跨进程或外部路径替换竞争。提交点和锁边界见[包说明](../../../src/agents/plugins/fs/fs-local/README.md)。

## 5. 监听与生命周期

1. 对照上游明确监听文件、目录、缺失路径的支持范围，初始化完成时机、回调错误、取消传播、监听句柄所有者和异步关闭语义；检查 `chokidar` 或其他监听依赖在各平台的实际行为。
2. 在临时目录验证初始化完成后的变更通知、关闭后不再通知、初始化失败与取消、关闭期间可能发生的回调，以及重复关闭的实际约定。使用受控同步点和有界等待，避免依赖固定睡眠或事件数量、顺序等平台不保证的细节。
3. 通过实际 Harness 装配和销毁验证服务注册与依赖；分别检查调用方持有的监听句柄与后端自身资源，明确谁负责关闭、失败如何报告以及清理是否可重复。不能以替身自行实现的关闭行为证明真实后端正确。

**验收**：监听和服务生命周期在当前平台可重复验证，取消、失败、关闭及资源归属明确；无法可靠验证的竞争或平台差异单独记录。

第 5 步在 Windows x64 使用真实后端和临时目录验证目录、文件及缺失文件的就绪后通知、重复关闭及关闭后的通知边界；通过实际 Harness 验证服务销毁后由调用方持有的监听句柄仍需显式关闭。已验证创建监听器前的取消和元数据失败；监听器创建后的初始化取消、监听器错误和关闭期间的回调竞争未能以真实后端受控复现，不以替身结果充当真实验证。其他平台及 Linux 父目录重建行为未运行。资源归属和上游实现语义见[包说明](../../../src/agents/plugins/fs/fs-local/README.md)。

**验收**：干净构建、公开入口和当前平台聚焦测试有可复现结果；来源、限制和后续接口清楚，未受限后端未装配到生产 Agent。
