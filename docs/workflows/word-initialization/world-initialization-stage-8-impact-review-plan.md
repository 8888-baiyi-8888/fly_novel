# 第 8 阶段：影响检查、用户选择与受控提交开发计划

本文细化[世界初始化总开发计划](world-initialization-development-plan.md#8-影响检查用户选择与受控提交)的第 8 阶段，承接[第 7 阶段讨论与候选契约](world-initialization-stage-7-discussion-contract.md)和[集成验证交接](../../../.agents/notes/world-discussion-integration.md)。本文是开发计划；拟议字段、状态、目录和示例均不是现有接口，也不是已由用户确认的全部业务规则。先结合样例确认待定事项，再实现相应契约。

## 目标与边界

1. 针对用户选定的待审候选，读取当前正文、候选全文及其版本，查找可能受影响的资料，展示实际检查范围、发现的问题、处理建议和未覆盖范围。关联记录是线索，不自动构成语义冲突；没有发现冲突不等于世界中没有冲突。
2. 主 Agent 理解修改意图、组织检查和解释结果；已划分的内容模块由所属专用 Agent 按需分析。可信应用负责世界、目标、版本和权限绑定，模型建议、对话或目录登记不能代替用户选择和程序检查。
3. 用户明确选择优先。用户明确确认继续处理但未对某项单独选择时，使用该项已经展示、内容完整且仍有效的 Agent 建议；未确认、建议缺失、无法执行或检查结果已变化时不得推断同意或编造默认处理。先向用户展示确认的范围、已选项及将采用的默认建议。
4. 确认与提交绑定用户实际审阅的候选、检查结果、选择和相关版本。提交前重新核验；目标、候选、已读取依赖、查询范围或选项变化时，按影响范围重新检查并要求重新审阅，不能静默沿用旧确认。
5. 只通过可信应用提供的受控提交能力修改当前方案。讨论 Agent、检查 Agent、普通文件工具和目录工具不能借确认名义直接绕过选择、检查或版本校验；已确认状态和当前方案状态不能仅从 Session 或候选保存推断。
6. 支持本阶段实际接入的已有目标修改。新增、删除目标、人物关系新增条目和地图概览 / 连通候选仍是第 7 阶段的限制，不以直接创建或覆盖冒充支持；是否扩展另行讨论。最终完成初始化、完整工作流恢复和后续世界演化属于第 9 阶段及以后。

## 业务样例

### 城门规则与人物经历

曲水城的当前资料写着城门昼夜开放；候选改为夜间关闭。检查读取地点正文，并通过已有的地点层级、历史和人物 / 组织引用等实际可用路径查找相关资料。若林岚的人物经历写明其夜间带商队进城，报告该资料、实际依据及可能冲突；若只发现名称线索、资料未展开、读取失败或没有可用反向查询，分别报告不确定和未覆盖范围，不把线索包装为已证实冲突。

检查建议可以是“保留商队夜间通行例外”，或“保留关闭规则并修改人物经历”。前者若需要改动已审阅的地点候选，必须形成新的明确候选及版本并让用户审阅；后者若涉及人物，须形成归人物模块所有的独立候选，不得因为地点确认就直接改写人物。用户明确选择某一处理方案时遵循其选择；用户明确确认继续但未单独选择此项时，才采用先前展示的具体建议。若建议只有一段解释、没有可执行的具体改动，不能将其当成默认写入。

### 人物与组织成员：多目标审阅

一次讨论拟将林岚的角色正文与青云宗成员职务分别改为外务负责人。系统展示两个目标各自的当前正文、候选、基线、检查依据和可能关联，允许逐项审阅；两份候选归不同模块，不能把一份保存或一份确认说成全部完成。用户是否能只提交其中一项、依赖未选项时如何处理，需要在实施前与用户确认；无论选择何种规则，都要如实报告每一项的实际结果，不承诺跨模块原子提交。

### 变化、未完成与取消

用户查看检查结果后，若另一操作修改了候选、当前资料，或在已检查的组织成员集合中新增了相关记录，即使原先读过的单个文件未变，旧确认也不能直接用于提交。检查失败、取消、资料不可读、结果不确定或仅完成部分页时，展示已检查与未完成范围；取消确认不产生提交。若写入已经开始，应区分未发布、已发布、部分完成及结果不确定，先核查再决定恢复，不能一概声称回滚或盲目重试。

## 检查、选择与提交契约设计

### 检查结果

可信应用生成检查标识并绑定世界、讨论、被检查候选 ID 和实际候选版本、目标及基线。每个检查项记录可定位的资料、实际读取版本或明确的版本不可用状态、检查方法和方向、发现的问题及可追溯依据。结果区分已检查未发现问题、发现问题、无法判断、检查失败 / 取消及未覆盖；支持分页时必须区分全部完成和部分完成。

检查范围需要同时记录单项版本和能够检测集合增删的查询条件、分页版本或其他可复核的范围凭据。只记录已命中的文件摘要无法发现新的关联记录；无法可靠重放查询或获得范围版本时，结果明确标记不能证明范围未变，不把它当成稳定检查。多个模块分别记录读取时点，不能声称形成全局快照。

建议应与具体检查项关联，说明处理内容、涉及目标、预期变更和依据，并明确哪些仍需用户判断。涉及修改的建议须能对应经所属模块校验的候选或明确的可审阅变更；推荐理由和模型输出不是授权。检查不产生当前方案写入；检查本身失败或范围不足时如何继续，列入下方业务讨论。

### 用户选择和确认

可信应用展示完整候选或可追溯的差异、检查项、建议、未覆盖范围及实际选项。用户可以明确选择某个方案、拒绝或取消；保留、暂缓和自定义方案的具体行为以用户确认的交互契约为准。单项选择和最终确认是不同动作；关闭界面、无回复、模型回答、工具成功或 Session 中出现“确认”等文本不构成可信确认。

确认记录至少绑定世界、检查结果的稳定标识 / 版本、每个候选 ID 和版本、目标基线、检查依赖及范围凭据、每项显式选择和适用的默认建议，以及被确认的实际变更清单。建议、选项、候选或依赖变化时使相关确认失效；不得按显示文字或列表位置重新匹配不同版本的检查项。明确取消或确认前中断不提交；已确认后请求失败也不自动产生新的授权。

### 受控提交与状态

可信应用核对调用身份、世界、候选归属和状态、已审阅候选版本、目标基线、检查与选择、依赖及范围凭据，再调用所属模块的受控发布接口。模型不得获得确认令牌或能自行提交的通用写工具。每个模块在发布点重新核验自身必要的版本、身份、格式、关系和旧候选限制；不同模块与普通文件分别使用其实际版本机制，不能混用文件版本、内容摘要和查询分页版本。

候选、检查、确认和提交结果是不同业务对象。提交后需要明确候选占用如何结束，以及已提交、已放弃、失败和结果不确定如何区分；不能把现有 `abandoned` 改作已提交。候选状态、提交记录及现有版本 1 的兼容方案在契约步骤确定：选择版本升级与显式迁移，或以独立版本化记录建立关联并拒绝不支持的组合；任何方案都保留已有文件，不静默误读或删除。

跨文件提交不假定原子事务。推荐先逐项准备可审阅的发布清单，并记录每项发布前后的可核查状态；若提交中途失败，停止后续依赖操作，展示已发布、未发布、失败和结果不确定的目标及目录状态。是否提供受控重试、补偿或回滚，以及部分提交是否可接受，须先结合样例确定；不得未经用户授权覆盖之后发生的变化。需要恢复的记录应带格式版本和严格身份校验，未知或损坏时保留原文件并拒绝自动推进。

单可信写入进程前提下，检查、候选更新 / 放弃、确认和提交必须有共同的协调边界，避免“检查通过后、发布前”被另一个应用入口修改。单个服务自己的队列、进程内身份占用或一次复查不能单独证明整个跨模块操作隔离；设计需说明所有写入口如何参与、资源释放和异常路径，以及不受支持的跨进程并发。无法保证时拒绝提交并报告范围。

## 分步开发与验收

第一步对实际读写、版本、查询范围及业务样例的走查见[现状盘点与样例决策](world-initialization-stage-8-inventory.md)。

第二步的检查、用户确认和受控发布契约见[第 8 阶段契约](world-initialization-stage-8-review-contract.md)。

1. **盘点与样例决策。** 复核第 7 阶段候选、各模块版本与查询覆盖、遗留候选、已有直接写入和恢复机制；用城门 / 人物、人物 / 成员及结果不确定样例走查。列出每种目标的当前读取、检查、提交和恢复能力，区分现有实现与缺口。向用户确认下节会影响近期行为的业务选择；工程上已有明确约束的问题自行处理。
2. **确定检查和确认契约。** 定义检查范围、依赖版本和集合变化凭据、检查项与建议、用户选择、确认范围、失效条件及版本化记录；以实际样例检查默认建议、取消、同名目标和资料变化。不把计划中的建议直接当成已确认契约。
3. **建立只读影响检查。** 装配主 Agent 与按需专用 Agent 的只读检查能力，优先复用现有查询；记录覆盖范围、来源、版本、失败及不确定性。验证跨世界和普通文件旁路、空结果 / 未知 / 错误区分、分页不完整和新增关联导致的范围变化；只读检查不得改变当前资料或候选。
4. **建立用户审阅与选择。** 由可信应用呈现可核对的当前正文、候选、差异、检查项及完整建议；实现明确选择、确认继续、采用已展示默认建议和取消。验证无选择与无确认的区别、缺失建议拒绝、选择覆盖默认、候选 / 检查变化使确认失效，以及模型无法伪造用户动作。
5. **实现首批受控提交与恢复。** 先以地点和人物纵向样例打通可信提交入口、基线及候选版本重验、模块不变量、候选占用结束与结果记录；处理旧人物候选及人物索引恢复。注入发布前后失败、重复请求、取消和结果不确定，证明不会误报成功、丢失候选或覆盖后续修改；未验证的目标明确拒绝。
6. **扩展多模块与部分结果。** 根据已确认的多目标规则接入组织 / 成员、人物关系、历史、局势、规划、专有内容及受控文件。逐项核验正文、引用、目录及状态同步，覆盖依赖变化、部分发布、失败恢复和不支持的新增 / 删除；不提供虚假的跨模块原子性。
7. **集成验证与交接。** 使用真实工作区和固定模型替身覆盖两个世界、城门冲突、显式选择、确认后默认建议、取消、版本及范围变化、部分失败与恢复；在隔离世界另做有记录的真实模型样例，报告实际调用和人工审阅范围。运行变更相关测试、类型检查、构建、文档链接和 Git 空白检查；按项目要求对照 DeepSeek Harness 的相关设计，记录适用差异与未覆盖事项，向第 9 阶段交接真实可恢复状态及限制。

每一步完成并验证后按仓库既有格式单独提交，然后继续下一步；不因提交自动暂停。真实模型结果仅证明运行过的样例，固定模型替身仅验证受测路径和状态。实际命令以项目现有脚本和测试入口为准，不把本计划的示例当作已经可运行的功能。

## 开发前需要讨论的业务问题

- **部分选择与依赖。** 林岚正文和成员职务相互关联时，用户只选一项是否允许提交？建议展示依赖并默认阻止造成已知不一致的部分提交；对是否允许用户明确保留不一致，需要用户决定。
- **检查不完整。** 城门规则检查时人物资料不可读或反向查询不支持，是否允许用户知情后继续？建议区分读取失败和未覆盖，失败先阻止提交；对明确未覆盖是否可由用户确认继续，需用户决定，不能由模型自行豁免。
- **默认建议的粒度。** 用户确认继续但未逐项选择时，总计划要求采用 Agent 建议。建议只使用确认前已展示且具有明确可审阅效果的逐项建议；没有可执行建议时重新询问，不生成新修改后自动提交。若默认建议会修改其他目标，是否需要额外逐项确认，需结合样例讨论。
- **多目标失败后的处理。** 地点已经发布但人物发布失败时，建议保留并展示真实结果，停止后续依赖写入；是允许在重新核验后继续剩余项，还是必须人工选择补偿，需用户决定。不能自动声称整组回滚。
- **候选及当前方案状态。** 提交一个局部候选是否意味着该目标整体 `confirmed`，还是只表示此项修改已接受？建议不将局部修改自动等同于第一版整体确认；人物既有 `commit` 的状态变化须结合业务明确处理。
- **重要冲突保留。** 用户明确知悉冲突后是否可以暂时保留并继续？总计划尚未确定最终交付是否允许重要冲突；本阶段不擅自决定，应将用户选择及未解决事项完整交给后续阶段。

## 与第 9 阶段的交接

第 9 阶段接收已验证的方案版本、候选和检查 / 确认 / 提交结果、未解决事项、结果不确定及恢复所需最小记录；Session 仍只负责对话。第 8 阶段不声称已完成整个初始化恢复、世界演化或最终交付，也不以一个成功文件代表整个多目标操作成功。

当前验证范围、真实模型样例限制及恢复交接见[第 8 阶段验证与交接](world-initialization-stage-8-handoff.md)。
