# 世界初始化内容模块逐项开发计划

本计划安排[十个内容模块与子 Agent 设计讨论稿](world-initialization-content-modules-design.md)的后续开发，位于[世界初始化开发计划](world-initialization-development-plan.md#6a-世界内容模块与专用子-agent-设计)第 6A 阶段。内容设计讨论稿负责模块职责、输入输出和待确认的业务边界；本文负责逐模块开发顺序、具体任务与验收。计划中的新模块、Agent、工具和接口均不表示已经实现。

## 目标与执行方式

按模块逐项完成设计、实现、验证和文档；每个模块先用具体世界构想说明输入、已有资料、输出、关联和失败结果，再确定最小实现。一个模块验收后再进入下一个；实际开发顺序可根据经用户确认的依赖调整，不为凑齐十个模块强制每个世界生成十份资料。十个内容模块是用户确定的范围，不新增顶层模块。

主 Agent 根据构想按需自行处理或委派。内容模块与 Agent 不是一一对应关系：是否为某模块创建专用 Agent、与其他职责共用 Agent，须结合独立任务、工具、持续身份和实际场景决定。每个新专用 Agent 既要能由可信应用独立运行，也要在需要时作为子 Agent；世界、身份、目录、Session 和权限由可信应用装配，不由模型通过任务参数授予。

## 当前基础与共同边界

- [世界入口与 Agent 装配](../../../src/app/README.md)提供主 Agent、只读通用子 Agent、可选角色创建 Agent、世界工作区、可选资料目录和 Session。生产装配的专用子 Agent 目前是角色创建；其他 Agent 不因写入本计划就视为已实现。
- [世界初始化模块](../../../src/world-init/README.md)提供世界范围、资料目录、角色资料和待审修改等能力。目录按文件和负责人登记，是导航线索；没有覆盖所有内容模块的统一对象存储、关联服务或路径无关查询接口。每步先核对实际代码，已有能力足够时直接复用。
- 世界规划、故事线和人物成长蓝图归属于世界。角色成长线供后续导演安排故事以引导发展；角色在故事中的具体选择和实际变化由角色自身决定。成长蓝图如何与成长线分工仍待用户确认，不把提案当成结论，也不在本阶段实现导演安排或角色自主行动。
- 用户构想、已有资料、Agent 建议、未来方向、明确留白与发现的矛盾需要可辨认。第一版、文件保存、目录登记或子 Agent 返回均不等于用户确认世界事实；不将后续局部讨论、影响检查和确认提交伪装成已完成。
- 已有角色资料、目录和 Session 有各自格式与生命周期。新增或修改持久化格式前明确版本、迁移或拒绝读取策略，保留原有用户数据。Session 恢复对话历史，不等于长期记忆或业务状态恢复。
- 工作区依赖单个可信写入进程，路径检查不是跨进程锁或系统级隔离。Windows 替换文件的 1175 已知问题见[本机文件后端说明](../../../src/agents/plugins/fs/fs-local/README.md)，按用户决定单独研究；本阶段如遇失败，报告实际结果，不擅自改造后端。

## 建议顺序与依赖

下表是推荐开发顺序，不是世界内容必须按此顺序产生的固定工作流。前置资料可以只有概况、引用线索或明确留白；模块不可用或尚未开发时，不把它当成不存在，也不自动伪造完整成果。每步开始时可根据真实场景调整，涉及业务边界的改变先与用户确认。

| 顺序 | 内容模块 | 推荐先做的原因及已有基础 |
| --- | --- | --- |
| 0 | 对齐业务边界与选取样例 | 先解决影响数据归属和 Agent 分工的问题，避免为十个模块预建统一框架。 |
| 1 | 世界基础信息 | 建立其他模块可引用的整体背景；先核对主 Agent 和现有草稿能力。 |
| 2 | 地图与空间 | 建立按需引用的地点及空间关系，为地区、组织和历史提供线索。 |
| 3 | 组织 | 在可用的世界及地点线索上设计组织；人物和历史可先留待关联。 |
| 4 | 人物与关系 | 在现有角色创建、资料及待审修改的基础上补足实际需要的关系能力，保留已有数据。 |
| 5 | 历史设定 | 引用已有或待定的地点、组织、人物，区分过去发生的事和公开说法。 |
| 6 | 初始局势 | 整合世界、地点、组织、人物和历史在起始时点的关联。 |
| 7 | 宏观发展蓝图 | 以初始局势和用户方向为依据，表达可能的重大变化及条件。 |
| 8 | 故事线组织 | 区分世界重大事件构想和持续叙事线路，设计角色成长线的规划内容。 |
| 9 | 人物成长蓝图 | 在用户确认其与成长线的分工后，设计人物长期和阶段性成长规划的组织。 |
| 10 | 世界专有模块 | 用至少两个不同世界检验按需扩展，按实际需要决定专用内容和 Agent。 |
| 11 | 跨模块整合与交付 | 将实际完成的模块接入第一版协作并验证关联、隔离与失败处理。 |

## 每个模块的共同开发步骤

以下步骤用于每个模块，模块小节只列出该领域额外需要解决的问题，不表示必须先建通用对象框架。

1. **核对与场景。** 阅读本计划、内容设计讨论稿、已有实现和测试，梳理本模块可复用能力。用至少一个具体输入走查新建、读取、修改建议与跨模块引用；相关业务边界有歧义时先提出建议并与用户确认。
2. **确定资料契约。** 明确归属、最小输入输出、定位与引用、来源、待审和留白如何表达；只对确需机器判断的数据定结构。按实际需要确定大小限制、无匹配、多个候选、缺失、无权、损坏和版本变化的区别。
3. **确定职责与装配。** 判断主 Agent 自行处理、通用只读委派或专用 Agent 的适用条件。确需专用 Agent 时设计 Preset、职责提示词、必要工具、可信身份及独立和委派入口；不存在对应实现时不得宣称已装配。
4. **实现和数据保护。** 沿既有扩展点实现本模块确认范围内的最小能力；区分自身建议与其他负责人的成果，不直接改写其他 Agent 目录或已确认资料。变更持久化格式前明确版本和旧数据策略。
5. **验证与交付。** 使用固定模型替身和真实工具验证输入、结果、实际文件、引用和未确认状态；按风险覆盖身份忙、启动失败、取消、资源释放、会话重建、保存失败及结果不确定。补充模块文档、必要的架构说明与 Agent Note；报告真实模型与平台验证范围。完成本模块后等待用户指示再进入下一模块。

## 0. 对齐边界与选取样例

1. 阅读[第一阶段计划](world-initialization-stage-1-plan.md)、[第六阶段计划](world-initialization-stage-6-first-world-plan.md)和内容设计讨论稿，区分已有能力、用户已确认方向与仍待讨论的建议。
2. 至少使用开放式修仙世界和资源有限的城邦群两种构想，标出十模块中实际需要细化、只需概况、明确留白或暂不使用的内容；示例不成为固定题材模板。
3. 优先讨论成长蓝图与成长线的具体职责、秘密与历史真相的可见范围、组织成员关系的权威归属，以及模块可选程度。每个问题先提出具体场景与推荐方案；用户尚未确认时，依赖该决定的实现不启动。
4. 确认第一批模块的实施顺序与首个模块；为将要实现的模块确定可复验的输入、已有资料、目标成果和拒绝路径。只记录已确认的业务结论，未决事项保持明确标注。

**验收**：两个世界形成不同的规划重点；首个模块有明确边界、输入输出和验收场景，影响其实现的业务歧义已有结论。

两个世界的规划重点、内容归属与待确认问题见[样例走查和业务边界](world-initialization-content-modules-design.md#边界示例)。建议首个模块为世界基础信息；它的候选范围与验收场景见下一节。模块可选程度等业务问题尚待用户确认，第 0 步验收不能因此视为已完成。

## 1. 世界基础信息

### 首个模块候选范围与场景（待确认）

建议由主 Agent 处理世界整体概念、基本构成、文明和时代背景；修炼规则或水利体系的深入内容按需归世界专有模块，基础信息只保留理解世界所需的概述与引用。现有草稿写入和第一版总览保存可供评估复用，但不等于已经有独立的基础信息存储或路径无关读取接口。当前样例不足以证明需要新增专用 Agent。

输入是用户构想与明确约束，以及授权范围内的已有世界资料；输出是可供审阅、来源可辨的基础信息建议，包括必要的引用和明确留白。用户要求、已有资料和 Agent 建议应可区分；保存或登记不代表用户确认。具体文件形式、定位方式和版本策略需在实现前结合现有能力确定。

| 场景 | 输入与已有资料 | 目标成果与检查 |
| --- | --- | --- |
| 修仙世界新建 | 用户要求开放世界、角色各有目标及法无好坏；没有既有世界资料。 | 形成世界性质和文明背景建议，区分用户要求与新增建议；修炼体系细节按需留待专有内容，远方范围可明确留白。 |
| 城邦群及已有资料 | 用户要求资源有限、多个城邦各有利益；已有一份授权可读的水源概况。 | 基础信息突出资源约束和城邦社会，引用实际水源资料而非复制全文；对缺失或未定内容保留说明。 |
| 重复生成和其他模块读取 | 已有一份基础信息成果；另一个获授权的任务需要世界背景。 | 新成果不覆盖旧成果；读取实际正文并保留来源线索，目录简介不替代正文，两份成果均不因保存而确认。 |
| 拒绝与失败 | 请求读取越权资料，或保存时发生失败、结果不确定。 | 越权读取被拒绝且不推断正文；保存失败时报告结果并保留已有成果，不确定时先核实再决定是否重试。 |

以上是待确认的最小场景，不预设其他模块已经实现或其读取接口已经存在。用户确认首个模块及影响实现的边界后，再按指示进入开发。

1. 核对主 Agent 的构想理解、待审总览及草稿写入，确定世界名称、整体概念、文明和时代背景等信息的归属；不同构想允许不同详略。
2. 确定如何引用用户明确要求与已有资料，区分用户要求、Agent 建议和留白；明确基础信息与世界专有内容的边界。
3. 评估主 Agent 是否足以维护基础信息。只有场景证明需要独立任务、工具或身份时才设计专用 Agent；确定结果如何被其他模块读取和引用。
4. 按共同步骤实现最小保存与读取，确保重复生成不覆盖已有成果；不把目录简介当正文或用户确认。

**验收**：两个构想能形成详略不同、来源可辨的基础信息；其他模块能在授权范围读取实际内容，生成和保存均不确认事实。

## 2. 地图与空间

1. 用多层地点、跨区域通行和特殊空间的具体例子确定地点身份、包含、空间关联及可选的距离、坐标和尺度表达；不假定所有关系是一棵行政树。
2. 确定同名地点、位置未知、明确留白、多个候选及地图尚未展开时的定位和读取结果；确定是否需要结构化关系以及最小版本规则。
3. 评估地图与空间 Agent 的独立职责和工具；若实现，可信配置限定其目录和世界，任务不决定权限。已有角色、组织和历史通过引用地点关联。
4. 实现经确认的地点与关联能力，验证跨世界隔离、越权拒绝、关系不完整和地点变化后的引用处理。

**验收**：可表示示例中的层级与空间关联，保留未知和留白；调用方能区分同名候选，不必一次填满世界地图。

## 3. 组织

1. 使用宗门和城邦联盟两个例子确定组织资料、组织关系、活动范围及成员关联；成员人物正文归人物模块，不重复维护完整角色资料。
2. 先与用户确认组织成员关系由哪一方维护及另一方如何读取；组织历史与历史事件的正文归属依内容边界确定，避免双份权威记录。
3. 评估组织 Agent；确定其读取世界、地点及已有角色线索和保存本人成果的权限，明确数据不足时的返回方式。
4. 验证同名组织、多种组织关系、未确定成员、跨负责人修改拒绝及已登记成果变化；不假定每个世界都存在宗门或固定组织类型。

**验收**：组织及其关系可单独定位并引用实际地点、人物线索；成员关系归属清晰，组织建议不成为已确认事实。

## 4. 人物与关系

1. 核对现有[角色资料与工具](../../../src/world-init/README.md)和[角色创建入口](../../../src/app/agents/character-creator.ts)，梳理当前角色身份、查询、待审修改、Session 和关系的实际表达能力。
2. 用朋友与敌对、师徒和组织成员等例子确定关系的权威归属、方向、描述和按需多重关系；明确如何引用组织、地点和历史，避免重复存储完整资料。
3. 保留角色创建 Agent 的独立运行与专用委派；用户指定数量优先，默认数量由可信配置提供。重要角色可按需深入，其他角色按近期需要创建。
4. 对已存在的角色文件和索引评估兼容策略；如需要格式变化，先确定版本、迁移或拒绝读取，验证同名人物、现有数据保留、待审修改和失败恢复。

**验收**：现有角色能力继续可用，示例关系可定位并区分方向和内容；角色建议与当前资料分开，创建和准备修改不代表用户确认。

## 5. 历史设定

1. 用两组织战争及其影响为例，区分历史事件、传闻、公开叙述和隐藏真相；说明时间顺序、因果、地点、人物和组织的关联。
2. 确定历史与初始局势的边界及世界资料不足时的留白；隐藏真相的可见范围先与用户确认，不预设所有角色 Agent 可见。
3. 评估历史设定 Agent 的输入、输出、可信装配和独立 / 委派运行；只在授权范围维护历史建议，其他内容使用引用。
4. 验证时间未知、顺序不确定、资料缺失、多个版本和跨模块引用；历史建议与未来规划不能混同。

**验收**：用户能从事件追溯相关背景和当前影响，公开说法、隐藏内容与待定内容按确认的读取范围区分。

## 6. 初始局势

1. 用战争之后仍然敌对的城邦为例，确认起始时点与当前世界局势、关系、危机、正在发生的事件如何组织；过去事件引用历史，未来变化引用发展蓝图。
2. 评估由主 Agent 整合还是配置独立职责；明确读取哪些已有成果、怎样表达未覆盖范围以及无法核实的矛盾。
3. 设计初始局势的保存、读取及与人物、组织、地点的关联，不复制完整资料；缺少其他模块成果时保留未定内容。
4. 验证世界背景相同但起始局势不同的场景，以及历史与当前资料冲突、文件过期和权限不足。

**验收**：初始时点的实际局势与历史和未来规划可区分，用户能看到支撑资料及未解决事项。

## 7. 宏观发展蓝图

1. 以城邦矛盾可能升级为例，区分已经存在的冲突与可能发生的重大事件；确定事件条件、关联、预期影响及确定程度的表达方式。
2. 以整个世界为规划范围，不将重大事件默认当作已经发生的事实，也不预先固定人物行动、所有剧情或结局。
3. 结合实际需求确定世界发展规划 Agent 的职责；若与故事线等共用 Agent，明确三类内容仍有独立归属及引用。
4. 验证不同确定程度、条件未满足、资料变化与未来留白；引用实际局势和相关资料而非复制另一模块正文。

**验收**：重大事件构想可与初始局势和故事线区分，条件与不确定性可见，规划不限制角色的具体选择。

## 8. 故事线组织

1. 明确核心故事线、长期角色成长线、阶段性核心线和阶段性角色成长线的实际使用示例；区分持续发展方向与重大事件列表。
2. 设计故事线与人物、组织、事件构想的关联，以及按需表达分支与合流；同一事件可关联多条线，不将关联视为事件已发生。
3. 与第 9 步一起确认角色成长线和成长蓝图的内容归属与引用；成长线为后续导演安排故事提供引导，实际发展由角色自行决定。
4. 确定主 Agent 与世界发展规划 Agent 的任务及成果边界，验证多条线、阶段性变化、无分支与留白；不实现故事级工作流。

**验收**：故事线可独立于事件清单定位和审阅；成长线方向与角色实际行动和结果不混淆。

## 9. 人物成长蓝图

1. 在用户确认成长蓝图与成长线的独立职责之后，选取一个角色的长期和阶段性规划，说明各自维护的内容及关联方式；不得将待确认方案视作定论。
2. 区分角色当前性格、已有经历、成长规划和故事中的实际变化；支持未来方向、可选转折与留白，不预先规定角色必须作出的选择或最终状态。
3. 确定如何引用角色资料及成长线，避免复制同一成长内容；评估与故事线共用 Agent 或独立职责的实际需求。
4. 验证规划与当前资料冲突、角色资料变化、成长线未提供及多个阶段不完整；实际演化结果不在本阶段模拟。

**验收**：用户能分别阅读人物当前设定与未来规划，蓝图与成长线各自职责明确，规划不会自动改写角色当前资料。

## 10. 世界专有模块

1. 使用修炼体系和科技 / 航行体系两个不同例子，确定专有主题如何按世界需要提出、定位和关联，不预设所有世界都需要相同主题。
2. 评估自由文本与少量可机读结构各自适用条件；按具体需要决定主题数据校验，避免预建无限制的动态 Schema 或插件市场。
3. 确定世界专有内容 Agent 的职责：由可信应用按实际主题装配可用能力和读写范围，主题名称和模型参数不能授予权限；是否拆成不同专用 Agent 由实际需求决定。
4. 验证不同世界主题隔离、同名主题、未知主题、格式版本、引用和权限拒绝；新增主题不增加第十个模块之外的顶层业务分类。

**验收**：两个不同世界能按需组织各自专有内容并关联基础资料，不要求其他世界使用同样主题或字段。

## 11. 跨模块整合与交付

1. 使用真实主 Agent、已完成的专用 Agent、既有工具和固定模型替身，分别走查修仙世界与城邦群：按需读取、委派或自行处理、整合关联并保存待审总览。
2. 验证资料只由所属模块维护，跨模块引用可定位，明确用户要求、Agent 建议、未来方向、留白和发现的矛盾；检查未配置能力、缺失、越权、资料变化和保存结果不确定。
3. 验证取消、子 Agent 失败、身份占用和重建；用户在恢复的同一会话输入“继续”后，主 Agent 依据历史及实际成果自行排查，不预建独立任务进度系统，也不盲目重复创建。
4. 更新相关模块、应用入口、架构与工作流文档，按实际新增能力运行聚焦测试、类型检查和正式构建；注明真实模型、跨平台、已知 Windows 问题及任何未覆盖的行为。
5. 对照[第 7 阶段](world-initialization-development-plan.md#7-局部讨论与待审修改)列明待审建议、局部讨论、影响检查和确认提交的剩余工作；不把本阶段完成描述为整个世界初始化或世界演化已经实现。

**验收**：实际完成的模块可以按可信装配和授权协作，用户能审阅来源可辨、未被冒充确认的第一版；失败保留成果并报告真实限制，下一阶段的入口和未完成项清楚。
