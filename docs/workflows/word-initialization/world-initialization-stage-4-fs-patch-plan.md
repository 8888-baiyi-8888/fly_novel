# 文件能力第一包：`dsh-fs-patch` 开发计划

本文细化[第四阶段的 `dsh-fs-patch` 步骤](world-initialization-stage-4-file-tools-plan.md#1-dsh-fs-patch补丁基础库)。目标是复用 DeepSeek Harness 的纯补丁处理能力，为后续文件系统契约、本地后端和模型工具提供基础。本计划描述开发任务，不表示代码已经引入。

## 范围和产出

本包负责补丁文本的解析和文本修改片段（hunk）的应用；文件读取、写入、删除、移动、路径授权、Agent 工具注册和多文件提交由后续组件负责。补丁中包含删除或移动指令，不代表本包直接操作磁盘。实际导出、输入输出及错误语义以选定上游源码为准。

完成后应有一个可独立构建和消费的包，保留选定上游版本需要的公开接口、实现和适用测试；记录来源、许可证、固定提交、本地修改及更新方法，并能在干净工作区验证。暂不引入文件系统服务或让 Agent 调用补丁工具。

## 1. 固定上游和核对包内容

1. 从 [DeepSeek Harness 仓库](https://github.com/deepseek-ai/deepseek-harness)选择并记录完整提交号，读取该提交的 `packages/fs/fs-patch` 源码、包清单、构建配置、测试和许可证；确认目录与包名在该提交存在。
2. 列出源码文件、公共导出、直接依赖与 peer dependencies，并递归核查运行时依赖；测试及构建依赖单独列出。核对 `dsh-fs`、`dsh-fs-local` 和 `dsh-tool-fs` 在同一提交中具体使用哪些导出，不凭当前分支文档推测接口。
3. 检查官方发布包可用性、Node.js、模块格式及本项目 CommonJS 构建兼容性。比较直接依赖发布包与同步源码的可行性，优先选择能保留官方实现且维护量较小的方式；不能直接使用时说明具体原因。
4. 记录实际补丁格式、解析与应用的行为、错误类型、换行和文件末尾处理，以及上游测试覆盖。当前未完成固定提交源码核对，这些细节在该步骤确认，不预先当作既定契约。

**完成条件**：得到固定提交、接口与依赖清单，以及引入方式的明确结论；若必需依赖不能取得或无法兼容，先解决或报告阻塞，不凭猜测实现替代品。

## 2. 建立包与来源记录

- 按选定方案引入官方包或源码。若复制源码，按仓库第三方源码管理规则保存许可证、来源、固定提交、更新步骤和本地修改清单；区分上游文件与项目适配文件。
- 如建立本地工作区包，依据包的实际职责选择位置和名称，更新 `pnpm-workspace.yaml`、相关 `package.json`、锁文件、TypeScript 构建配置和根 `AGENTS.md` 结构说明；公共导出对齐选定上游消费者的需要。
- 解决模块格式和导入路径差异，优先保持官方算法及外部行为；不得靠关闭类型检查、大范围断言或静默改变错误行为消除兼容问题。记录每处必要改动和理由。
- 包的导入不产生文件操作或启动副作用；构建产物与源码分离，消费构建产物的检查明确先构建。

**完成条件**：依赖安装、包构建和类型检查可从干净工作区执行，源码来源和实际修改可追溯；不得将本地生成产物误记为上游源码。

## 3. 保留并验证补丁解析

对照固定版本的公开接口和上游测试，复用官方解析实现，验证其接受的补丁边界、文件操作标记、路径和修改片段的解析结果。至少使用固定样例覆盖新增、更新、删除及移动指令；对不完整、格式错误和不受支持的输入检查上游规定的拒绝方式。具体支持范围及错误断言以该版本实际行为为准，不因预期不符而放宽有效检查。

此处只验证补丁结构的解析，不读取或修改目标文件，也不把路径解析结果视为已经授权。

**完成条件**：有效样例产生与上游契约一致的结构；无效样例按上游契约失败；适配后的导出可由独立调用方使用。

## 4. 保留并验证 hunk 应用

复用上游文本修改片段应用逻辑，在内存字符串上验证匹配、插入和删除等固定版本支持的行为。依据上游实际规则选择测试：包括多处修改、上下文不匹配及换行和文件末尾边界；记录上游是否支持模糊匹配和对应失败结果，不自行扩大或收紧规则。

检查解析结果与应用接口的衔接，但不将内存计算的成功等同于磁盘写入成功。文件写入原子性、并发保护和多文件部分成功属于后续后端及工具阶段。

**完成条件**：代表性样例的结果与上游一致；不可应用的修改明确失败，错误没有被吞掉；测试覆盖适配可能改变的行为。

## 5. 构建与消费验证

- 在相关测试位置运行移植的必要上游测试和针对本项目适配的聚焦测试；保留有意义的拒绝路径，测试描述行为而非复制实现细节。
- 执行本包类型检查和构建；从构建产物的公开入口做最小消费验证，调用实际导出完成解析与 hunk 应用。验证命令以实现后的项目配置为准，不预写尚不存在的脚本。
- 检查根项目的工作区构建及类型检查是否包含新包；仅运行受本次变化影响的检查。检查新增文件空白及已跟踪修改的 `git diff --check`。
- 更新包 README、上游来源和本地修改记录；如引入第三方源码、目录或依赖，同步仓库结构及锁文件。

**完成条件**：上述实际运行的检查通过并记录结果；无法执行的检查及原因明确列出。

## 交付和后续衔接

交付包、必要测试、构建配置与来源记录，并列明固定提交、引入方式、公开接口、依赖和本地修改。`dsh-fs` 阶段再按同一提交确认其消费方式；`dsh-fs-local` 阶段验证实际文件操作；`dsh-tool-fs` 阶段验证模型工具和删除权限。本包完成不代表这些后续能力已经实现。
