# 第 6A 阶段：世界专有模块详细开发计划

本文细化[内容模块逐项开发计划的世界专有模块步骤](world-initialization-stage-6a-content-modules-plan.md#10-世界专有模块)。世界专有模块是用户确定的十个内容模块之一；具体主题、字段、文件和工具不增加新的顶层模块。除明确列出的用户决定外，存储格式、工具名称及实现细节均为设计提案，不表示已经实现或形成最终契约。

## 已确认的业务方向

1. 先使用一个**世界专有内容 Agent**开发世界专有模块。它可以独立运行，也可以由世界初始化主 Agent 按需要委派；后续是否针对某些主题增加专用 Agent，依据实际需要再讨论，不在本阶段预建多个主题 Agent。
2. 专有内容 Agent 应结合用户构想、主题，以及世界基础信息、历史、地图、组织、人物、初始局势和世界发展规划等其他 Agent 已形成的相关成果，**自主识别需要补充的专有主题和内容并逐步完善**。它应按实际世界与任务确定重点、范围、详略和留白，不等待用户逐条列出设定，也不要求每个世界生成固定的修炼、科技或其他主题。
3. 主 Agent 负责理解构想、协调委派、核对和整合；世界专有模块内的信息由专有 Agent 开发。主 Agent 仍可主动补充十个模块之外的必要内容；专有 Agent 发现属于地图、组织或人物等其他模块的问题，应报告或提出补充需求，不直接代写那些模块的权威资料。
4. 用户确认使用 JSON 存储主题和按需拆分的内容项。同一内容维护一份正文，可以同时关联多个主题；从任一关联主题查询时应显示该内容的全部主题归属，不根据名称自动合并。

已保存的第一版及 Agent 自主补充内容供用户整体审阅；创建、更新、目录登记和 Agent 返回不等于用户确认世界事实。用户明确要求、已有资料和新补充的设定要能在讨论与成果核查时辨认；不强制为每个内容项增加未决定的来源标签。

## 目标和内容边界

世界专有模块维护某个世界需要深入表达、且不由其他九个模块负责的特殊设定，例如修仙世界的修炼原理、特殊资源规律，或航海世界的特殊航行技术与环境规则。不同世界可能具有多个主题，也可能只需要简短概况、暂时留白或没有专有主题；Agent 应依据现有构想判断，而非从题材名称机械套用模板。

| 内容 | 权威归属和协作 |
| --- | --- |
| 世界整体性质、文明与时代背景 | 世界基础信息维护整体概念；专有模块按需深入特定规则，并引用实际基础信息成果。 |
| 灵脉如何形成、功法适用条件、突破限制 | 专有模块维护规则或体系；地图维护灵脉的具体地点和空间关系。 |
| 青云宗修炼资源、宗门制度和具体成员 | 组织及其成员关系由组织模块维护；专有模块维护各方可引用的修炼体系规则，不重复维护整份组织资料。 |
| 林岚当前能力、认知与个人经历 | 人物资料维护；专有模块可以定义可引用的规则，不能因规则存在就自动赋予人物能力或知识。 |
| 过去发生的灵脉灾变、起点时的资源争议 | 分别归历史和初始局势；专有模块可解释相关规则并引用事件或局势。 |
| 未来可能出现的新修炼方式或技术扩散方向 | 未来发展方向归世界发展规划；专有模块维护起点已有或第一版设定中的规则，不将可能发生的变化写成已经完成。 |

规则、传闻和角色认知要区分。比如“传说服用灵草必定突破”可以是一种说法；若真实效果未知，不能自动写成确定的世界规则，更不能推断每个角色都知道它。专有 Agent 与世界规划者可读取其授权范围内的资料，角色知道什么仍来自角色自身初始化资料与后续经历；本模块不提前建立角色自主行动或通用秘密授权系统。

## 已有能力与限制

- [世界基础信息 Agent](../../../src/app/README.md)保存待审 Markdown 成果，按需供其他 Agent 读取。它提供整体背景，但目前不存在可对所有基础信息按路径无关 ID 读取的统一对象服务。
- [地图](../../../src/agents/plugins/map/README.md)、[组织](../../../src/agents/plugins/organization/README.md)、[人物](../../../src/agents/plugins/character/README.md)、[历史](../../../src/agents/plugins/history/README.md)、[初始局势](../../../src/agents/plugins/initial-situation/README.md)和[世界发展规划](../../../src/agents/plugins/world-development/README.md)各自维护自己的格式、工具、身份与版本；不能假定跨模块自动关联或统一存储已经存在。
- [世界工作区及资料目录](../../../src/world-init/README.md)提供世界、负责人和资料登记；目录简介是导航线索，不能代替成果正文或用户确认。现有专用 Agent 的 Preset、SystemPrompt、Tools、Session、受控文件和可信委派可复用，实际权限以[应用说明](../../../src/app/README.md)及具体装配为准。
- 当前没有世界专有内容的专用插件、数据格式、查询工具或专用 Agent；主 Agent Skill 中提出的修炼体系等观察方向，不代表这些专有内容的存储和自动开发能力已经实现。

## 示例走查

### 开放式修仙世界

已有基础信息指出“力量本身无善恶”，地图中有青云山与灵脉地点，组织资料中有青云宗；历史记载灵脉变化引发迁徙。专有 Agent 阅读这些实际资料后，可以自主识别出“修炼体系”和“灵脉及特殊资源”等需要设计的主题，并按近期需要补充：

- 修炼体系可先阐明力量来源、适用条件、限制和明确未知；只有故事与世界设定确实需要时再独立细化境界或功法。远古境界、稀有功法等可以留白。
- 灵脉主题可说明灵气形成、资源恢复或衰减的规则，并引用地图中的真实地点；具体坐标仍由地图维护。历史迁徙原因若尚未确定，规则本身不能把推测改写成历史事实。
- 青云宗如何使用修炼资源由组织资料负责；林岚掌握什么功法、知道哪些规则由人物资料或后续角色经历负责。专有 Agent 可以报告需核实的关联或冲突，不自动改写这些资料。

### 资源有限的城邦群

已有基础资料说明水资源紧缺，地图记录水源与水渠，组织记录城邦及供水联盟，初始局势记录起点时的供水问题。专有 Agent 可以根据已设计内容判断是否需要单独开发“水利技术”或“资源循环规则”：例如说明提水设施的条件和限制、维护所需资源及未知故障因素；如果现有世界无需这些细节，也可以暂不创建主题。

供水联盟的成员关系和具体协约归组织；水渠实际位置及连通归地图；起点时哪座城缺水归初始局势；未来可能建立的新设施属于世界发展规划。专有技术规则与这些资料通过实际 ID 或授权文档关联，不复制各方正文。

### 特殊航海 / 科技世界

用户设想船只能在特殊潮汐期间穿越迷雾海域。专有 Agent 可自主识别“潮汐航行规则”和“航行技术限制”；地图维护海域与航线，组织维护航运公会，历史维护已经发生的航行事故。规则可以存在尚未解释的原因和例外，不要求先定义修炼境界或复用城邦水利字段。

上述例子用于验证适应不同世界，不是固定主题清单；世界可以有不同数量的主题，或在缺少依据时明确未定。

## 主题、内容与自主补充

建议以“主题”组织同一世界的专有内容：主题用于表达一个世界内相对独立的设定范围，例如修炼体系或航行技术；内容项用于按需维护可单独定位、查询和完善的规则、概念、材料或机制。主题不是固定类型，名称可以由 Agent 根据资料提出或调整；同名主题应列出候选，不根据名称自动合并，主题 ID 与名称分离。

Agent 的工作方式建议如下：

1. 读取用户构想和实际可访问的其他模块成果，先区分已存在的专有主题、相关已有设定与明确留白。
2. 根据世界特征和近期需要判断哪些专有设定值得补充；查找现有主题或条目、核对同名候选，提出并创建所需的新主题或内容项。
3. 对需要继续细化的部分按需展开；内容不足时保留未知、待核实或未展开说明，不因为某个主题已建立就假设其所有规则已完整。
4. 检查新增内容与已读资料的关联及可见矛盾；不能验证时报告依据和未检查范围，不能为追求一致性自动修改其他 Agent 文件。
5. 返回实际成果路径、主题和内容范围、引用依据、未知、待核实事项及目录登记结果，供主 Agent 核对并供用户整体审阅。

主题和内容项是否使用固定层级、是否允许一个内容项关联多个主题、复杂规则是否需单独的结构化字段，均应根据修炼与航行等实际样例在契约步骤确定；不因某个示意目录自动要求所有主题具有相同结构。用户尚未指定某细节时，Agent 可合理补充，但不能将新增内容冒充用户原话，也不能擅自覆盖用户明确留白。

## 存储、版本与提取方案（建议）

参考当前地图、组织、历史和世界发展规划，建议使用版本化 JSON：一个主题有独立的主题资料，专有内容按需拆成可独立定位的文件。这样可以分别读取和更新境界、功法或航行限制，也允许主题只有简短说明而不预先创建全部子项。字段以名称、身份、正文、引用和确需程序判断的状态为主；长篇规则可使用正文文本，不为不同题材预建通用动态 Schema 引擎。

建议为世界专有模块建立 `src/agents/plugins/world-specific/` 专用插件，格式、受控存储、查询、工具定义和 Cordis 注册集中在该插件中。可信应用配置实际负责人的世界目录，以下为可讨论的文件示意：

```text
<世界专有内容负责人目录>/
  topics/<主题ID>.json            # 主题自身说明、覆盖范围与留白
  items/<内容项ID>.json           # 按需建立的独立设定或规则
  candidates/                     # 已确认资料的待审修改候选
```

主题与内容项使用程序生成、与名称分离的稳定 ID；不同世界和不同类型不因名称相同就视为同一对象。建议内容项维护自身主题归属及必要关联，按实际文件反向查询；不要求每次增删或更新内容都手动同步另一份列举所有条目的总表。主题文件可以维护它自身的概况及明确留白，不能用过时概况替代条目正文，也不能因为没有条目就推断世界没有该设定。

JSON 和一份内容关联多个主题已由用户确认；具体总览文件、主题层级及字段仍是实施提案。一个内容项在多个主题中出现时维护同一份正文及 ID；主题自身是否拥有上级、是否需要独立规则条目仍以实际场景决定，不为了实现方便固定单一树形结构。

### 格式、状态与更新

建议新格式从明确版本开始（如版本 1），严格校验世界、类型、ID 与必要关联；未知版本、损坏、重复字段、非法 ID 和跨世界数据明确拒绝并保留原文件。现有基础信息 Markdown、其他 Agent 的正文及目录记录不自动解析、迁移、覆盖或删除。以后若变更用户数据格式，先确定版本和迁移或拒绝读取策略。

主题和内容项可各自表达展开程度与明确留白；可参考其他模块的“未展开、概况、详细”三个等级，但是否采用、是否需要机器枚举待契约步骤确认。展开程度、用户审核状态、秘密 / 公开的世界设定及角色是否知道分别处理：某条内容“详细”不代表其子项或全世界都已规划完整，也不意味着用户已经确认。

初始化期间建议未确认资料按读取版本直接更新；版本变化拒绝覆盖。对已确认资料的修改参考历史 / 局势的待审候选与基线检查，具体流程以契约与后续确认能力为准。世界开始演化后，如果专有规则因实际事件变化，历史状态、变更依据和世界内时间应留存；初始化覆盖、文件修改时间和 Session 不能冒充世界历史。确认提交与演化历史留存不在本阶段预先宣称实现。

### 查询、关联与来源变化

建议支持按主题名称 / 别名查找主题，按主题、关键词、关联对象和展开情况查询内容项，并按 ID 读取正文及版本；同名返回多个候选。按主题查找条目应直接基于权威内容文件或可重建的索引；索引损坏不能伪装成资料不存在，查询结果需说明已记录范围、分页和未展开内容，不自动推断世界中其他内容不存在。

已建档的地点、组织、人物、历史、局势和世界发展规划等关联应使用对应模块实际存在的类型和 ID；基础信息若为 Markdown 则通过授权文件或目录读取，不创造虚构 ID。未建档对象保留文字线索，不按同名自动关联。某规则被多个主题或对象引用时，优先引用同一份权威规则，不能复制多份正文再要求同步；具体多主题归属方式留待契约步骤。

可信应用显式绑定已有只读句柄或授权的原文读取能力，验证世界、负责人及实际目标。缺少句柄、目标不存在、无权、读取错误、资料损坏、来源版本未知和来源已变化分别报告；来源版本或目录摘要不能证明内容语义已复核。对已读资料发现潜在矛盾时，列出依据和未覆盖范围；不能宣称全世界自动一致或自动更改其他模块。跨文件读取不是原子快照。

写入结果不确定时返回可核查目标，先检查实际文件与版本，再决定是否补做；内容保存和目录登记分别报告。沿用单可信写入进程和现有路径检查，不声称跨进程锁、跨文件事务或系统级隔离。Session 只能恢复对话，不证明任务或保存已经完成。

## 专用插件与工具（提案）

所有专有内容工具的定义、执行和注册集中在专用插件中。下列名称和参数是开发提案，实际契约在实现前结合场景确定；不提供模型按名称直接加载新代码或自行授予权限的机制。

| 工具 | 用途与边界 |
| --- | --- |
| `world_specific_topic_create` / `world_specific_topic_read` / `world_specific_topic_update` | 按需建立、读取和按版本修改主题资料；ID 由系统生成，未确认与已确认的修改路径分开。 |
| `world_specific_topic_search` | 按名称或关键词查找当前世界已记录的主题，列出同名候选、展开情况及查询范围。 |
| `world_specific_item_create` / `world_specific_item_read` / `world_specific_item_update` | 按需保存、读取或按版本更新独立规则 / 内容；不写入地图、组织、人物等其他模块。 |
| `world_specific_item_search` | 按主题、关键词或关联对象查询已有内容，返回文件版本、分页及未展开 / 未覆盖说明。 |
| `world_specific_related_read` | 查询内容项之间及主题相关的已记录关联，保留记录方向与上下文，不自动推断因果或归属。 |
| `world_specific_reference_check` | 核验同世界的外部对象或授权原文及可用版本，区分未配置、未找到、无权、变更和无法核验。 |
| `world_specific_consistency_check` | 核验可机械检查的身份、文件和引用；报告发现、依据及未检查范围，不自动裁决复杂规则矛盾。 |
| `world_specific_candidate_prepare` / `world_specific_candidate_read` | 为已确认主题或条目准备和读取待审候选，检查基线；不提供确认提交。 |
| `delegate_world_specific` | 主 Agent 提供用户构想、任务和必要背景，委派专有 Agent 自主识别并完善内容；世界、身份、目录和工具权限由可信应用绑定。 |

主题名称、内容正文和模型提供的路径只能描述业务内容，不能让 Agent 获得额外文件权限、创建其他 Agent、加载可执行代码或注册任意新工具。Agent 发现现有插件无法表达的需求时，报告缺口并保留资料；不把动态内容自动变成动态代码。

## 专用 Agent 和可信装配

建议参照已完成的地图、历史与世界发展规划 Agent，创建世界专有内容 Agent 的 Preset、SystemPrompt、独立应用入口和 `src/tools/subagent-world-specific/` 中的专用委派工具；其业务工具仍集中在上述插件中。名称仅为提案，具体导出和目录在实施时与现有项目惯例核对。

独立运行或主 Agent 委派时，可信应用绑定当前世界、稳定 Agent 身份、负责人工作目录、持久 Session、模型与已有资料的只读能力；内容 Agent 自己的目录可写，其他模块仅按授权读取。若目录服务已由主 Agent 持有，应使用该 Agent 自己的可信身份绑定；借用的地图、组织、人物、历史、局势及规划句柄由提供方负责保持有效和关闭，不能假定会自动共享或重复打开被占用的同世界存储。

主 Agent 根据世界构想和已有成果判断是否委派，不强制每个世界都调用或产生同样数量的主题。专有 Agent 在授权范围内自主识别、补充和完善，主 Agent 读取实际成果后整合，必要时再委派其他负责人处理其领域内容。专用 Agent 的提示词指导任务但不能取代读写边界和实际验证，也不能保证真实模型一定遵守留白或自主发现所有需要的主题。

同一世界的稳定身份并发启动应拒绝；启动失败、取消和父 Agent 关闭时等待已受理操作、释放注册及资源。失败后保留已经保存的成果；同一 Session 恢复时先读取实际文件与目录，核对已存在主题和版本，不能因为会话恢复就认定业务完成或盲目重复创建。面向故事角色的读取隔离、普通文件 / 搜索和目录旁路应由后续角色运行装配整体设计，不把规划者完整视图直接当成角色认知。

## 开发步骤与验收

第一步的实际能力、三世界自主补充与边界验收见[现状与场景走查](world-initialization-stage-6a-world-specific-content-scenarios.md)。

1. **核对现状与样例。** 对照世界基础、地图、组织、人物、历史、局势和规划的实际文件、读取能力及测试；用修仙、城邦和航海样例核对 Agent 自主发现主题、内容归属、关联与留白。涉及主题 / 条目归属或文件拆分的业务歧义先举例并商议，不将提案当作已确认。
2. **资料契约与存储。** 在用户确认的 JSON 和内容可关联多个主题的基础上，确定主题与内容的身份及必要关联、展开程度、状态、引用、版本及旧资料策略；按结果实现专用插件内格式与受控存储。验证不同世界同名主题、按需拆分、未知版本、损坏、权限拒绝、版本冲突、候选与写入结果不确定。
3. **查询与工具。** 在插件内实现主题和内容的定位、查询、按需关联、来源核验与可检查的一致性报告；按可信应用提供的句柄或原文能力读取其他模块。验证无结果与未覆盖、未配置 / 无权 / 缺失 / 读取错误、同名候选、多主题关联、引用变化、分页失效和跨世界拒绝；结果不依赖手工维护全量总表。
4. **专用 Agent 与主 Agent 接入。** 实现独立 Preset、职责提示、可信装配、Session 和专用委派；允许 Agent 根据已有世界资料自主提出并补充主题，写入仅限自身目录。验证与既有各专用 Agent 共存、身份与路径隔离、资料目录绑定、启动失败、取消、资源释放及同一会话恢复。
5. **双世界端到端验证与交付。** 用固定模型替身及实际文件走查修仙世界和另一不同世界，让专有 Agent 读取已有成果、自主补充适用主题并报告留白；覆盖没有必要新增主题、现有主题继续完善、跨模块引用、来源变化、冲突提示、重复创建防护、目录登记、越权、失败恢复和结果不确定。另用真实模型检查所选样例的工具选择、自主补充与内容质量，报告人工审阅范围；替身不证明模型会正确规划。更新插件、应用和架构说明及必要 Agent Note，完成后等待用户指示，不自动进入跨模块交付或世界运行。

**验收：** 专有 Agent 能依据不同世界和已授权的已有成果，按需识别、创建、读取和完善世界专有主题；用户能定位权威内容、关联与留白，多个主题不要求相同模板。其他模块事实与专有规则职责清楚，无法核验和未覆盖内容如实报告，生成与保存不等于用户确认。

## 近期需要结合示例细化

1. **主题与条目如何归属。** 用户确认“灵石”只维护一份正文，可关联多个主题；从任一主题查询都需显示全部归属。是否需要主归属、主题自身层级和其他关系，以实际查询需求确定，不预设必须是单父级。
2. **文件粒度。** 用户确认使用 JSON 存储主题及按需拆分的内容项，不要求每个主题产生相同数量的文件；具体字段和文件层级结合长篇规则、逐项更新和检索需求确定。
3. **规则分歧与细化程度。** 例如不同地区修炼规则不同、规则尚属传闻，或水利技术只有某组织掌握；需要分别表达适用范围、未定和真实关联，不能简单用一条无条件全世界规则覆盖。具体枚举和可计算约束依场景确定。
