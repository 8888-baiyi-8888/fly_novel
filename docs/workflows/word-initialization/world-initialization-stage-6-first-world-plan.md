# 世界初始化第六阶段：主、子 Agent 协作生成第一版详细开发计划

本计划细化[世界初始化开发计划第 6 阶段](world-initialization-development-plan.md#6-主子-agent-协作生成第一版)。目标是依据用户确认的构想和可信工作区中的资料，由主 Agent 识别本世界的重点，按需委派已装配的子 Agent，整合一份可供用户整体审阅的世界方案。计划中的方案、示例和步骤是开发设计，不代表新工具或业务状态已经实现，也不把待确认的选择当成既定契约。

## 目标、边界与现状

- 世界具有独立于单一主角和小说情节的发展；角色有自己的目标、认知和关系，规划为世界演化提供方向，不预先固定所有行动和结局。项目背景见[项目愿景](../../PROJECT_VISON.md)。
- 第一版应体现用户构想与重点，允许各部分详略不同；区分用户提供的要求、Agent 建议、未来方向和待定内容，呈现已发现的矛盾与无法判断的事项。地区、势力、规则和角色均按实际需要规划，不组成所有世界必须填写的固定清单。
- 第一版用于审阅；生成、登记、委派成功或文件写入都不等于用户确认世界事实。局部讨论、整体冲突修复、用户选择后的受控提交和最终完成初始化分别属于后续阶段，不能由本阶段伪装完成。
- [世界入口](../../../src/app/agents/world-initialization.ts)可由可信应用选择世界并装配共享读取、主 Agent 草稿目录、只读通用子 Agent、可选角色创建 Agent 和资料目录服务。现有生产入口只提供角色创建这一专用子 Agent；其他职责不能因配置里存在某个身份就视为已实现。
- [主 Agent 提示词](../../../src/agents/world-initialization-main-agent/plugins/system-prompt/plugin.ts)已有构想理解、规划与留白的职责；[角色委派工具](../../../src/tools/character/delegate-character-creator.ts)只接收任务文本，结果是建议，子 Agent 不继承父会话。角色 Agent 有独立 Session，角色资料与待审修改按[应用说明](../../../src/app/README.md)维护。
- [资料目录](../../../src/world-init/README.md)按世界和负责人登记成果及版本，`catalog_check_page` 检查已登记文件，不自动发现所有文件。普通文件读取及角色资料工具可供获授权 Agent 使用，但目前不存在统一的、与文件路径无关的世界资料查询与读取业务接口；明确留白目前可作为原文保存和读取，不等于已有结构化留白状态。
- 特殊 Agent 的身份、目录和 Session 由可信应用装配，模型不通过任务参数获得权限。当前依赖单个可信写入进程；路径检查不是系统级隔离。Session 恢复对话历史，不代表长期记忆恢复。
- Windows 替换已有文件可能出现的 1175 错误已列为[本机文件后端已知问题](../../../src/agents/plugins/fs/fs-local/README.md)，按用户决定留待单独研究。本阶段遇到保存失败或结果不确定时必须报告实际状态，不借本阶段擅自改造文件后端。

## 首版协作方案（待第 1 步结合示例确认）

1. **理解输入。** 主 Agent 接收用户构想和已有讨论，整理明确要求、创作方向、用户指定的约束及需要澄清的矛盾。按现有理解阶段的约定，涉及理解结果确认时遵循调用方提供的确认结果，不因模型说“已理解”就替用户确认。用户补充或修正时使用最新有效要求。
2. **读取已有资料。** 主 Agent 在可信世界范围内查看与任务有关的资料和目录记录，区分文件不存在、未登记、读取失败和文件中明确写出的留白；目录简介只作定位线索，具体内容以对应成果为准。资料过长、受限、过期或无法读取时说明未覆盖范围，不把未发现当成不存在。
3. **确定任务。** 主 Agent 根据世界构想决定自己处理哪些内容、是否需要委派，以及每部分的规划深度。需要角色创建且专用工具已装配时，可向角色 Agent 提供目标、世界背景、用户明确要求、近期故事、数量要求及相关资料线索；用户指定数量优先，未指定时遵循角色 Agent 的可信默认配置。角色关系由角色 Agent 主动设计；第二、第三梯队只按近期故事需要创建。是否需要通用只读子 Agent 由实际任务决定，不强制每次委派。
4. **处理返回。** 子 Agent 可以在授权范围内读取相关资料并维护本人负责的成果，向主 Agent 说明建议、资料线索、假设、未解决事项或失败。主 Agent 核对所需资料及结果，不把自由文本中的成功声明替代文件状态或用户确认。子 Agent 未配置、身份忙、失败、取消或资料不足时，保留已完成部分并说明未完成范围；是否继续交付部分方案由第 1 步结合场景确定。
5. **整合与交付。** 主 Agent 汇总世界规划和子 Agent 提出的角色设定，呈现重要内容及相互关系，明确用户来源、Agent 补充、未来方向、留白和已发现的矛盾。可审阅的具体形式、方案与分散成果的关联、是否保存总览文档及覆盖策略均须在第 1 步确定；不预先强制结构化字段、固定角色清单或单一存储布局。

上述步骤描述职责而不是固定编排引擎；实现优先使用已有 Agent Loop、工具、Session 和工作区装配。若现有能力不足，以具体场景证明缺口，再确定最小业务接口、提示词或受控工具；不先假定必须新增 LangGraph、自动重试或持久任务系统。

## 两个贯穿场景

**场景一：开放式修仙世界。** 用户提出修仙世界、人有善恶而力量本身无善恶，希望角色有独立动机，并对某个地区和近期故事有额外要求。主 Agent 先整理并按现有流程取得理解结果，再识别规则、人物关系和近期故事中真正需要细化的部分。角色工具已装配时委派创建所需角色，任务包含用户约束、相关世界背景和数量要求；角色建议及关系返回后由主 Agent 整合。遥远地区和以后才需要的角色可保留概况或留白。展示时不能把 Agent 推测标成用户原话，也不能把未来故事方向说成已经发生的事件。

**场景二：资源有限的城邦群。** 用户关心多个城邦的能源、贸易关系和群体选择，尚未指定主要人物，并明确某片外海暂不设定。主 Agent 应先识别资源及城邦关系是主要规划重点，不因为已有角色工具就强制大量创建人物；确有近期故事所需人物时再考虑委派。读取资料遇到明确留白时保留其原意；目录无匹配、文件缺失或读取失败分别报告，不能把任何一种误判为“外海不存在”。如果已有资料与用户要求冲突，应展示冲突和未覆盖范围，不自行宣称已修复。

以上是比较场景而非固定世界分类或输出模板。实现和测试还须覆盖用户明确指定或禁止某项内容、未装配角色 Agent、子任务失败与已有资料变化。

## 开发步骤

### 1. 核对现状、细化输入输出与交付契约

1. 阅读[第一阶段业务计划](world-initialization-stage-1-plan.md)、[第五阶段工作区计划](world-initialization-stage-5-workspace-plan.md)、[资料共享与读取设计](../../modules/world-information-access.md)，以及主 Agent、角色 Agent、委派工具、目录服务与现有集成测试。列出当前可实际调用的工具、会话与文件流转，标明提示词指导、程序保证和尚未实现的能力。
2. 用上述两个场景走查从构想、理解结果、资料读取、任务选择、委派到整合交付的过程。分别写出用户输入、已有资料、主 Agent 操作、子 Agent 任务与回复、用户看到的结果；补充不委派和资料不足的分支。说明建议的来源、留白和未来方向如何在结果中可辨认，不将示例固定为所有世界的字段。
3. 提出可审阅的首版方案：用户如何收到整体结果；主 Agent 输出与角色独立成果如何互相引用；任务中断、某个子任务失败或资料无法读取时如何呈现部分结果；是否需要保存总览以及重复生成时如何避免覆盖已有成果。为每个选择列出推荐方案、实际影响和与后续阶段的关系，按业务依赖与用户确认；用户尚未确认的选项保持待定。
4. 按场景检查是否必须补充路径无关的资料读取、结构化来源或留白表示、第一版业务状态、结果长度处理及版本绑定。只确定本阶段确实需要的能力和可观察错误；目录摘要、Session 和提示词不能被当作这些能力自动存在的证明。已有数据若需改变格式，先确定版本及迁移或明确拒绝读取策略。
5. 给出可信装配及生命周期图：世界与身份由应用固定，模型只提供任务；区分主 Agent 自行处理、通用只读委派和角色专用委派。列出每个入口的任务输入、结果、取消与释放责任，以及部分成果的保留边界。固定模型替身只验证执行路径和状态，不证明真实模型的内容质量。

**验收**：至少两个不同构想形成具体的输入、操作与可审阅结果示例；需要用户决定的交付和失败语义有明确结论；后续步骤使用的接口和保证均能对应真实能力或明确的实现任务。

### 2. 建立第一版需要的最小资料与成果访问

1. 根据第 1 步确认的交付方案，核对世界入口现有文件、目录和角色工具能否支撑主子 Agent 定位资料、读取内容和回溯来源；能满足时直接复用。不能满足时在所属模块设计并实现最小受控能力，明确世界、身份、读取范围、结果大小及错误语义。
2. 若确需路径无关定位或结构化状态，只实现确认场景需要的查找、引用和状态；区分未登记、无匹配、明确留白、缺失、无权、损坏、读取失败和范围不完整，避免仅用空数组或空文本混淆。允许资料原文表达留白时，不把文件内容自动升级为用户确认的结构化状态。
3. 若确需保存第一版总览或引用，定义写入归属、版本和覆盖策略，复用世界工作区的可信授权与已有成果；不修改其他 Agent 目录或已确认资料。明确读取和保存失败、取消及发布结果未知的行为，不把目录登记作为事实确认。
4. 验证不同世界隔离、主子 Agent 的同世界读取、相同名称或多候选项、读取截断、留白与失败、旧版本或资料变化、拒绝越权，以及原数据与已完成成果保留。仅对实际新增的业务接口增加相应测试，不预建通用索引系统。

**验收**：第一版场景所需资料可在正确范围内定位并读取，来源、状态和不足之处按确认的契约呈现；缺失能力和错误不被伪装成空结果。

### 3. 完善主 Agent 职责与可信协作装配

1. 沿现有系统提示词插件和世界入口补充第一版所需工作指引：理解构想、识别重点、读取资料、选择自行处理或委派、整合和说明未完成项。提示词只表达职责，不充当授权、用户确认或程序状态的保证。
2. 明确角色创建工具与通用只读工具的适用范围。只向主 Agent 展示可信应用实际注册的能力；角色工具固定调用现有角色创建职责，不能接收世界、身份、目录或 Session 授权参数。未配置角色工具时不伪造已完成委派。
3. 按场景决定任务需要哪些用户约束、世界资料、数量与近期故事背景，并说明子 Agent 可自行读取的范围。保留角色 Agent 对默认数量、重要性层级和主动设计人物关系的现有职责，不以主 Agent 的固定字段限制不同世界。
4. 复用现有运行驱动和 Session；核对身份忙、启动失败、执行失败、取消、重复释放与清理失败的实际传播。需要调整时在已有扩展点实施，并验证不丢失既有成果，不把失败子任务的回复当作成功建议。
5. 验证至少一个无需委派的场景和一个角色委派场景，覆盖未配置、错误身份或跨世界参数、任务取消和实例重建。主 Agent 能获取有效回复或明确失败，并保留已完成的其他部分。

**验收**：可信装配决定可调用能力和权限；主 Agent 能按实际任务组织工作，子 Agent 能获得足够背景并返回可供整合的建议或明确缺口。

### 4. 整合第一版并提供审阅结果

1. 按第 1 步确认的结果形式实现最小交付，结合用户构想、已有资料和子 Agent 结果组织整体方案。保留可追溯的资料线索及必要的结果状态，区分用户要求、建议、未来方向和待定内容。
2. 对已发现的内部矛盾、资料缺失、过期、失败或未检查范围作明确展示；发现矛盾不等于已完成后续整体修复，未发现矛盾也不表示不存在冲突。
3. 根据第 1 步确定的部分结果规则处理子 Agent 不可用、输出不完整、保存失败或用户取消。已保存成果、尚未完成的部分和结果不确定的操作须可区分；任何成功回复不能代替实际文件或目录结果。
4. 用户审阅前不写入受保护的已确认资料，不把初稿生成视为用户确认；如发生多次生成，遵循已确认的成果保存和覆盖策略。不要提前实现后续阶段的局部选择、自动冲突修复或最终提交。
5. 验证两种不同构想各自形成重点不同的方案；验证来源、留白、矛盾和未来方向的展示，以及无角色委派、角色委派和部分失败时的可观察结果。

**验收**：用户能整体审阅本次方案，区分要求与建议并看到主要待定和失败范围；结果不冒充已确认世界事实。

### 5. 集成与失败路径验证

1. 使用真实主子 Agent、现有工具和 Session，以及可控模型替身跑通两个贯穿场景；覆盖先读取已有资料、至少一次角色委派与一次不委派、主 Agent 整合结果、生成后实际内容及授权边界。断言工具请求、返回结果和最终交付，而不只断言预设文本。
2. 使用受控门闩或真实后端测试资料在读取或整合期间变化、角色实例销毁与重建、同身份忙、世界隔离、目录过期或损坏、权限不足、保存失败、任务取消以及执行与清理同时失败。逐项检查已完成、未完成和不确定范围，保留原有成果和用户数据。
3. 对角色 Agent 重新实例化验证原有目录及已配置 Session 继续使用；验证旧实例的目录读取凭据失效。不得将对话历史恢复描述为长期记忆恢复。
4. 对照[文件后端说明](../../../src/agents/plugins/fs/fs-local/README.md)报告 Windows 已知问题；不将测试替身或测试跳过包装成真实模型验证。若用户提供可用配置并要求真实模型演示，单独评估生成质量与失败结果；否则明确未运行及原因。

**验收**：从用户构想到可审阅结果的主子 Agent 协作路径可复验；异常、并发和取消结果不误报完整成功，也不丢失原有成果。

### 6. 文档与交付

1. 更新受影响的主子 Agent、工作区、工具、应用入口和业务说明；如涉及架构、持久化格式、生命周期或重要取舍，同步架构说明、目录登记和 Agent Note。明确方案文件与角色成果、目录简介、Session 和用户确认状态的职责。
2. 运行与变更相符的聚焦测试、类型检查和正式构建；新增或调整构建入口时先构建，再验证相应产物。检查相关文档链接和 Git 空白，并记录平台、跳过项、失败及已知限制。
3. 记录第一版交付能力与仍未覆盖的局部讨论、影响检查、确认提交、长期记忆及跨进程保护；不把第六阶段完成描述为整个世界初始化或后续演化已经完成。

**交付验收**：可信应用能按照已验证方式组织第一版协作并交付可审阅结果；实际能力、未确认内容和未完成事项对用户可见。
