# 第 6A 阶段：组织模块详细开发计划

本文细化[内容模块逐项开发计划的组织步骤](world-initialization-stage-6a-content-modules-plan.md#3-组织)，为后续设计、实现和验收提供依据。组织 JSON 与初始化存储的实际格式见[组织数据契约](world-initialization-stage-6a-organization-contract.md)和[组织包说明](../../../src/agents/plugins/organization/README.md)；组织 Agent 的独立运行与主 Agent 委派见[应用说明](../../../src/app/README.md)。本文不实现人物关系、历史或世界运行工作流。

## 目标与边界

组织模块按世界需要建立和维护宗门、城邦政体、联盟、商会、军队等组织资料及其关联。组织有自己的目标、资源、结构、规则、约束和相互关系；它可以服务多部小说，不以单个主角为中心。组织可只建立概况，也可详细规划，未建立的组织不能被推断为不存在。类型由具体世界决定，不要求每个世界都有国家、宗门或固定组织清单。

组织专用 Agent 负责组织内容开发，主 Agent 识别需要、委派和整合；专用 Agent 可以由可信应用独立运行或由主 Agent 委派。组织 Agent 按授权读取背景、地图和人物资料，维护自己的组织成果，不直接修改地图、人物、历史或其他负责人的文件。

| 内容 | 归属及处理 |
| --- | --- |
| 组织自身的定位、目标、规则、结构、资源、重要岗位、活动方式 | 组织模块按实际需要维护；组织可以只有部分信息。 |
| 组织与组织的合作、竞争、统属、联盟参与等 | 组织模块维护关系及其依据；不把所有组织关系强行变成父子树。 |
| 人物与组织的成员、任职等关系 | **用户已确认：由组织模块维护，人物侧查询和展示。** 关系只维护一份权威记录；人物正文仍归人物模块。具体文件与工具方案见下文。 |
| 世界中的地点、空间范围和地图坐标 | 地图模块维护地点及空间；组织引用地点表达总部、据点或活动线索，不复制地点坐标作为权威数据，也不因空间重叠推断控制权。 |
| 往事的事件经过与时间线 | 历史模块负责历史事件正文；组织可概述与自身有关的背景并引用事件，历史模块未建成时保留线索，不伪造事件 ID。 |
| 起始时点的跨组织危机和整体局势 | 初始局势模块负责整体局势；组织资料可记录自身当前处境或关系，并引用局势，不复制一套完整世界局势。 |
| 人物的性格、经历、目标及人物之间的关系 | 人物与关系模块维护；组织只能引用人物并说明其组织角色，不覆盖人物正文或替人物决定行动。 |

组织模块的第一版供用户整体审阅。**用户已确认：世界初始化期间，组织自身资料、组织间关系和成员关系的修改均按版本直接覆盖当前资料；世界开始向前演化后，更新时还要保留此前信息。** 初始化时直接写入是资料更新方式，不表示用户已确认整个世界或其他模块的事实；文件保存、目录登记、工具返回或 Agent 回复不等于用户确认。审核状态、资料展开程度、世界内时间关系和保密范围是不同维度。后续世界演化的留存机制及第 7 阶段的局部讨论流程尚未实现。

## 样例：宗门与城邦联盟

### 开放式修仙世界

青云宗是一个修行组织，下设传功堂与外务堂。传功堂是否需要单独建档由实际任务决定：只需要说明内部职能时，先写在青云宗资料中；需要独立目标、负责人或与其他组织关联时，再为其建立独立组织，并记录它与青云宗的实际关系。一个分支可以与多个组织有不同关系，不能只因组织结构画成一张单一父子树。

林岚是青云宗长老，同时秘密属于另一组织。人物资料由人物模块维护，两条成员关系各有独立记录；人物侧按授权读取后可展示两个组织，但不把组织档案全文和另一份成员权威数据复制到人物资料。若尚未建立林岚的角色档案，可以暂存“待关联的长老”线索；这不是已确认的角色 ID，也不代表已经查遍全部角色。青云宗总部引用已存在的山门地点；总部、活动范围、控制权和势力影响分别描述，不能因为山门位于某地就断言宗门控制整片地区。

组织可以概述曾发生的迁徙，但迁徙事件的详细经过、时间与各方说法由历史模块维护。历史事件尚未建档时写明线索和未核实范围，不构造一个不存在的事件引用。

### 资源有限的城邦群

曲水城可以同时有两种资料：地图中的曲水城是地点，组织中的曲水城政体是政治实体，两者名称可以相同，但 ID 和职责不同。曲水城政体、上游城政体和供水联盟各有组织资料；水源地点和水道由地图维护，供水规则及联盟内部约定由组织资料表达，水利技术的深入内容按需引用世界专有模块。

供水联盟包含多个城邦，成员城邦也可能就水量竞争。联盟参与、合作和竞争是不同关系，可以并存；联盟关系不自动赋予联盟对城邦的统治权，也不自动意味着城邦之间友好。只知道“下游还有城邦希望参加”时保留未确定的组织线索，不创建虚假的组织 ID 或假设申请已经获准。其他城邦或联盟部门不必在第一版全部建档。

## 当前实现与复用范围

- [世界工作区和资料目录](../../../src/world-init/README.md)提供可信世界及负责人目录校验、进程内身份占用、目录登记和按登记记录读取正文。目录简介用于导航，不是成果正文或用户确认；它不自动发现未登记文件，也不是组织对象或关系服务。
- [地图包](../../../src/agents/plugins/map/README.md)提供世界地图、地点与空间查询，地点有稳定 ID；可信应用可复用已打开的地图服务核验同世界地点引用，具体边界见[应用说明](../../../src/app/README.md)。`MapStore` 在同进程对世界和根目录占用，不能假设组织 Agent 随时再打开同世界地图存储；通用路径无关资料读取服务尚未建立。
- [角色资料与工具](../../../src/world-init/README.md)提供角色 ID、资料、分类、查询和角色待审修改。当前 `categories` 中的 `faction` 只是可查询分类：实现不校验其 ID 是否指向组织，不提供组织成员关系的统一写入、双向读取或自动同步。既有分类可能存在用户数据，不能直接当作权威成员关系或静默覆盖。
- 地图和组织专用 Agent 均由可信应用按需装配委派、Session 和目录绑定，详见[应用说明](../../../src/app/README.md)。共享工作区依赖单个可信写入进程；当前路径检查不能替代跨进程锁或细粒度访问控制。

## 组织、层级和关系的表达

### 组织自身

每个需要被独立查找或引用的组织具有同世界内稳定的组织 ID、名称和一份自身资料。名称允许重复或更改，不能按名字自动合并；组织类型是可描述和查询的属性，不是预置的封闭题材枚举。同一政治实体与同名地点分属不同模块；资料可按 ID 引用地点，而不是共用或混用 ID。

建议组织资料包含可机读的身份、版本、名称、审核状态和展开程度，并按需表达别名、简介、目标、运作、结构、资源、已知范围和引用。世界 ID、负责人及可访问目录由可信应用绑定并校验，不由模型指定。具体长文本可以自由组织，不要求所有组织填写统一章节；缺失、未知、未调查和用户明确留白应能够区分。只在有明确业务需求时增加必须机器判断的字段。

用户已同意组织资料采用三个展开等级：

| 等级 | 标识 | 含义 |
| --- | --- | --- |
| 未展开 | `unexpanded` | 组织已建档，只有名称、线索或简要描述，尚未形成组织概况。 |
| 概况 | `overview` | 已有足以辨认组织及理解其主要性质的简要资料，细节可继续补充。 |
| 详细 | `detailed` | 根据当前世界与任务，已较深入描述组织的重要内容；不要求填写所有栏目，也不表示永远完成。 |

等级只描述该组织自身，不继承到下属组织、成员或关系；未创建文档的组织不算 `unexpanded`。审核状态与展开程度分开；`detailed` 不代表用户确认，初始化新建的组织方案仍供用户审阅。

组织拥有的岗位或部门描述并不必然代表一个已建档组织或已建档角色。建立独立内部组织有其自身 ID 和资料，再用组织关系表达其与其他组织的关联。对于尚不确定是否成立、是否隶属或是否独立的内部派系，保留线索和判断缺口，不自动生成实体或关系。

### 组织与组织

需要独立查询的组织间关系以独立 JSON 记录；建议每条有稳定关系 ID、同世界两端组织 ID、关系含义、方向性、适用时点或不确定说明和必要描述，只维护一份，从两端查询时返回同一条记录。初始化期间关系按版本直接覆盖；世界演化后的变更还要保留此前信息。联盟参与、合作、竞争、上下级、分支等是可按世界扩展的关系语义，不能用一种“父级”覆盖全部。类型命名与哪些类型需要专门校验，在格式契约步骤结合场景确定。

方向由记录明确表达。例如“外务堂隶属于青云宗”与“青云宗包含外务堂”是同一条有方向关系的两种读取视角；“曲水城政体与上游城政体竞争”可按该关系的实际语义表达对等或单向，不能由一方的敌视自动推断另一方也敌视。两组织之间允许多条不同关系，也可按背景存在不同阶段；同名或相同类型关系能否合并须看具体含义，不按名称自动覆盖。

层级相关关系允许按实际情况表达多个上级、多个层面或没有已知上级；是否存在循环取决于关系语义。若某个经明确定义的关系确为包含或统属，创建时按该关系规则拒绝自关联和循环；合作、联盟参与等一般关系不能机械套用树形无环限制。层级查询应返回命中路径和其他已记录关联；无结果不表示不存在其他关系。

### 人物与组织成员关系

**已确认的权威归属：组织模块维护成员关系，人物模块查询展示。** 组织和人物两侧都是同一记录的读取视角，不各自维护一份可能发生分歧的成员表。一个人物可属于多个组织，可同时具有多种职务；记录区分关系本身、岗位名称或职务、适用时期及说明。岗位是组织结构中的角色，不要求每个岗位都有已建档人物；个人档案未建立时可保留可读线索，不伪造角色 ID。

建议成员记录的两端分别为已建档组织和已解析角色引用，另可通过显式的“尚未关联角色”形式保存线索；已解析与未解析不得混用。未解析线索需要时可在读取角色候选并核对后关联真实角色 ID，同名返回多个候选时不自动选择。组织可以有岗位或成员线索但没有可解析成员记录；查询为空、未覆盖全部资料、成员未知和明确没有成员是不同结果。时间或是否仍任职未知应明确为未知，不默认当前任职或已经离任。

组织 Agent 只修改其获授权的成员关系资料。人物 Agent 或主 Agent 发现成员关系需要变化时，读取已有关系后向组织 Agent 提出任务或修改建议，不直接改写组织目录；初始化期间由组织负责人按版本直接更新。人物侧通过只读成员查询按角色 ID 展示关联及其状态和可见范围；当前人物 `faction` 分类不自动等于成员关系，也不由组织 Agent 直接改写。后续人物模块如需迁移或投影分类，须先定义与既有分类的差异、冲突处理、数据版本及迁移或拒绝读取策略；在此之前保留原数据并明确展示来源。

### 秘密与可见范围

**用户已确认：组织 Agent 和世界规划者可以读取秘密成员关系；故事中的角色按各自权限决定是否可读取，同一秘密对不同角色的可见性可以不同。** 例如林岚秘密加入另一组织，知道此事的接头人可以读取，其他未获权限的角色不能读取；不能把“秘密”统一处理为对所有角色不可见，也不能仅因角色属于某组织就推断其拥有全部秘密权限。角色查询由可信应用提供授权，独立授权管理服务尚未建立。

#### 角色查询权限等级

权限按**世界、角色和组织**分别授予；同一角色在不同组织可以有不同等级。资料项由组织负责人为所属组织设定所需最低等级；角色在该组织的有效等级达到要求时，才允许通过角色查询工具读取对应资料。等级控制访问资格，不代表角色自动知道已获权限的全部内容；角色认知、实际获得信息和记忆另行维护。

| 等级 | 名称 | 用途示例 |
| --- | --- | --- |
| 0 | 公开 | 世界内向普通人公开的组织名称、公开活动或广为人知的资料。 |
| 1 | 内部 | 向获授权的普通成员开放的一般内部规则和成员资料。 |
| 2 | 管理 | 向获授权的负责人开放的管理资料，例如负责区域的调配计划。 |
| 3 | 核心 | 向获授权的核心人员开放的敏感资料，例如核心决策与隐秘成员。 |
| 4 | 最高机密 | 仅向明确获得最高授权的角色开放的关键秘密。 |

这些名称表达访问等级，不强制世界使用相同的职位体系，也不由“长老”“盟主”或成员身份自动映射。等级按数字比较，高等级可访问同一组织中要求较低等级的资料；组织 Agent 和可信世界规划者使用各自的规划权限读取，不冒充故事角色，也不因为故事角色拥有等级 4 就获得全世界所有秘密。没有该组织的明确授权时，角色仅能访问该世界对其开放的 0 级资料；不同世界隔离。

一个角色可能是青云宗普通弟子（青云宗等级 1），又是另一组织的秘密接头人（该组织等级 3）；他可以读取另一组织设为等级 3 的秘密成员记录，但同为青云宗弟子的普通角色不能读取。每份秘密成员关系使用组织的实际安全范围及所需等级；跨组织关系的保护范围由可信负责人明确绑定，不能因为查询另一端或通过反向列表绕过权限。等级不表达组织关系的成立与否、审核状态或成员本人是否知情。

可信应用根据当前运行的角色身份和世界绑定只读查询视图，并从受保护的授权资料取得该角色在目标组织的等级；模型不得传入、选择或提高角色 ID、世界 ID、权限等级或授权目录。角色只能以自身身份查询获授权内容，不能借查询其他角色的参数冒充其身份。初始化时组织负责人可提出等级与授权建议，由可信应用或受授权管理流程绑定；运行中授权变更由可信业务流程执行并保存，不能由查询工具或模型自行提权。授权资料需保存角色 ID、组织 ID、等级及版本；未知等级、跨世界引用和无效授权拒绝使用，缺失授权不能默认授予成员或更高等级。

读取正文、搜索、反向成员列表、目录简介、计数、分页版本、报错和历史记录都必须在同一可信授权边界内过滤，先授权再输出；未授权角色不能从名称、ID、数量、错误或分页结果推断秘密关系存在。组织文件中若同时包含不同等级的内容，组织查询需按可授权的独立内容项投影，仅返回角色可读的部分；不能先返回整个 JSON 再依赖模型自行忽略秘密。无法可靠拆分和过滤的文件对角色视图整体拒绝，不能降级为全文读取。对于合法查询返回的空结果，应表示“在该角色获授权范围内未找到”，不能表示全世界没有记录；直接猜测无权读取的 ID 时不泄露是否存在。不同权限视图的分页版本按各自可见结果计算，权限或可见数据变化时拒绝继续使用旧分页版本。目录或普通文件工具不能绕过受控角色查询读取秘密正文。

真实关系、公开说法及角色所知需要区分；目录简介和全文搜索也可能暴露内容。组织查询工具提供受可信授权绑定的过滤，但世界读取根及资料目录没有按人物认知或单条关系提供完整权限隔离。将秘密资料提供给故事角色前，应用须隔离原始组织目录和可绕过授权的目录、搜索及其他读取工具，并验证整个装配的读取边界。

## 文件与存取方案（建议）

### 目录及格式

**用户已确定：组织模块需要独立的专用插件。** 组织资料、组织关系、成员关系、受控存取、查询和组织 Agent 使用的工具定义及 Cordis 注册集中在 `src/agents/plugins/organization/`。主 Agent 使用的组织专用委派工具定义放在 `src/tools/organization/`，与角色创建 Agent 的委派工具归属一致。专用 Agent 的 Preset、职责提示词和应用装配按现有 Agent 结构单独组织，由可信应用为 Agent 装配插件。

下图仅展示建议的文档布局，实际根目录由可信应用从组织负责人配置绑定：

```text
组织负责人目录/
├── organizations/
│   └── <组织ID>.json        组织自身资料
├── relations/
│   └── <组织关系ID>.json    组织与组织之间的一条关系
└── memberships/
    └── <成员关系ID>.json    人物与组织之间的一条成员关系
```

**用户已确认采用 JSON 文件**：每个组织和每条关系独立保存，组织长文本放在 JSON 中。建议使用格式化 UTF-8；具体字段、关系拆分粒度及查询结构在格式契约步骤确定。组织与两个类型的关系各自维护权威文件，反向列表从关系文件查询构建；不在组织、人物两端同时保存一份独立的权威成员清单。

下面是语义示意，不是最终 JSON Schema 或可直接落盘的文件。`person` 的已建档引用必须经可信人物读取能力核实；未建档示例仅保留线索，不把名称当作 ID。

```json
{
  "formatVersion": 1,
  "id": "程序生成的成员关系ID",
  "worldId": "可信绑定的世界ID",
  "organizationId": "已存在的组织ID",
  "person": { "kind": "unresolved", "description": "负责外务的长老，人物尚未建档" },
  "roles": ["长老"],
  "period": "任职时段待核实",
  "reviewStatus": "suggested"
}
```

如采用独立组织关系与成员关系文件，组织对象不另存权威关系 ID 清单；目录或缓存可重建，查询时说明实际扫描范围。关系随世界资料变化而需重新核实时，保留记录和旧依据，报告缺失、版本变化或未核实，不静默删除关联或把变化自动解释成成员退出。成员关系是组织模块内的资料类型，不是新增顶层内容模块或预建全项目通用关系引擎。

### 引用、查询和一致性

可信应用为组织 Agent 装配本世界组织根、地图和人物的只读能力；模型不能传入其他世界 ID、任意磁盘根或授权配置。不同实体类型分别使用自身 ID；先搜索候选，再读取正文核实名称、世界及版本或可用摘要，不能依靠同名文本自动关联。对无法验证的外部引用，不报告为有效链接；可返回未核实线索，不能杜撰 ID 或凭目录简介视为已读正文。

组织 Agent 和世界规划者读取获授权的已登记成果时，首版优先采用目录搜索和 `catalog_read_shared_source` 完整读取，并报告登记状态、来源路径、实际摘要及目录过期状态。这能读取已登记文件，但不提供按地点 ID 或角色 ID 的通用解析，且不能发现未登记内容；原始目录工具不可直接向受角色等级约束的故事角色开放。可信应用可复用已打开的地图与人物存储核验引用，不将存储写句柄交给组织 Agent；接口和生命周期见[应用说明](../../../src/app/README.md)。

组织内部可通过扫描受控文档建立可重建内存索引，按 ID、名称、别名、类型、组织关系、地点线索和成员关系查询；同名返回候选及可辨认上下文。关系查询从任一端定位单份关系并标明方向；成员查询同时支持组织 ID 和角色 ID。分页绑定查询条件及所检查文档集合版本，后续页遇到相关文件变更则拒绝并要求重查；取消、扫描上限、未授权、损坏、外部引用无法验证应明确报告失败或不完整，不返回貌似完整的空列表。版本检查不能承诺跨文件原子快照。

同一地点可被多个组织以不同语义引用，例如总部、活动地点或声称控制的区域。组织控制或影响的含义由组织关系事实表达，不从地图包含、坐标相交或总部位置自动推出；更不复制地图多矩形作为组织领地的第二份权威空间数据。若某个控制范围无法由现有地点引用准确表达，记录为待细化的区域线索，不擅自修改地图或虚构坐标。

### 版本、写入与失败

组织模块首版格式建议显式 `formatVersion: 1`，文件名 ID、正文 ID 和可信世界绑定须核对；非法 JSON、重复键、未知字段 / 版本、无效 ID、跨世界引用或损坏记录明确拒绝，保留原文件。它是新格式，不自动将现有 Markdown、角色 `faction` 分类或目录简介迁入组织资料。将来格式变化先制定版本递增、迁移及备份，或明确拒绝旧版本的读取 / 修改策略；不得静默误读、覆盖或删除用户数据。

创建使用程序生成 ID 和独占写入；同名是候选，不自动覆盖。保存文件、登记目录及后续审阅分开报告，一次只承诺实际完成的单文件操作，不宣称跨文件或跨模块原子事务。

**初始化期间**，组织自身资料、组织间关系及成员关系均先读取当前完整记录与文件版本，再以完整新内容直接覆盖同一 ID 的文件。例如，修正青云宗宗旨或将林岚的职务由长老改为外务负责人，只更新相应组织文件或成员关系文件；组织间关系由合作改为敌对，只更新该关系文件。旧版本冲突时拒绝覆盖并重新读取；不自动改写人物资料、关系两端组织或其他关联文件。成功后新内容是当前初始化记录，但整个世界仍供用户审阅；结果不确定时先核实文件，不能假定已生效或回滚。

**世界向前演化后**，上述资料发生实际变化时，既要反映新的当前状态，也要保留此前信息，不能仅覆盖后丢失旧状态。采用下述拟实施的文档历史方案；它不属于本阶段的世界运行实现。

1. **当前资料与历史快照。** 每个组织、组织关系和成员关系继续有一份当前 JSON；世界演化触发变更时，在该组织负责人的历史目录中按资料类型和原 ID 保存不可覆盖的旧内容快照，并以独立变更 ID 关联新旧内容。当前文件负责当前读取，历史快照负责追溯；不把历史快照当成另一份当前权威资料。
2. **一项变更保存的依据。** 保存资料类型和 ID、变更 ID、旧内容快照、旧内容摘要、新内容摘要、世界内发生时点或明确的未知说明、变更原因 / 来源引用及记录顺序。世界内时点未知时不能用文件修改时间冒充；文件版本只用于并发检查，不等于历史事件或世界时间。跨资料的真实事件正文仍由历史 / 事件能力维护，组织变更记录只引用可核验的来源，不复制事件正文。
3. **安全提交与恢复。** 每次更新先核实当前版本并独占保存旧内容快照和操作记录，再以版本条件写入当前文件；确认新文件与预期摘要一致后标记该变更完成。中途失败或取消保留快照及操作记录；发布结果不确定时阻止该资料继续写入，先按操作记录及实际文件摘要恢复或报告冲突。操作记录、历史和当前文件属于多文件写入，不能宣称具有跨文件原子事务；恢复路径与单可信写入进程约束须在实现时验证。
4. **查询与授权。** 当前查询默认读取当前资料，历史查询按资料 ID、记录顺序或已知世界时点定位旧快照，明确未知时间和查询范围。历史内容按角色查询权限过滤，不因曾有权限或已知当前内容就自动暴露所有历史；权限在历史时点如何变化的业务语义由角色认知与世界运行具体设计决定。快照缺失、损坏、未知格式或恢复未完成时明确报错或不完整，不能伪装成没有历史。

例如林岚从长老转任外务负责人时，先保存长老时期的成员关系，再更新当前记录；城邦先合作后敌对时，同样保留合作关系的旧内容。该方案保留组织资料自身的变化依据，不预设组织事件会如何推动剧情，也不预定角色行动。初始化阶段按版本直接覆盖，不为每次草稿修正自动建立世界历史；从初始化切换到世界演化的可信触发及迁移边界须在世界运行入口实现前确定。当前不存在上述快照、恢复和权限服务。

失败或取消后保留已发布内容；提交结果不确定时返回可核查的目标和实际操作状态，由调用方先读取核实，不能盲目创建第二份。查询无法验证、索引损坏或目录不可用时分别报告原因和已完成范围；Session 只恢复对话，不证明组织任务已完成。组织插件按可信单写入进程、身份占用和路径校验工作，不声称提供跨进程锁、恶意并发替换防护或系统级隔离。

## 专用插件、工具与 Agent

组织专用插件负责格式校验、受控存储、查询和组织工具；工具使用 Cordis / Tools 按 Agent 身份注册和注销。插件按可信应用提供的身份和访问模式装配，不因模型参数获得权限。可信应用拥有存储及关联读取服务的生命周期，明确取消传播、并发占用、失败回滚与关闭等待。写能力只给组织负责人；主 Agent 和其他 Agent 按需要取得只读能力或使用已登记成果，不把组织写工具直接暴露给主 Agent。现有工具见[组织包说明](../../../src/agents/plugins/organization/README.md)；下表也包括尚待装配的 Agent 和历史能力。

| 拟议工具 | 主要用途与边界 |
| --- | --- |
| `organization_create` | 根据组织名称及必要概况创建独立组织建议，返回组织 ID、路径、文件版本和实际保存结果。 |
| `organization_search` / `organization_read` | 按名称、别名、类型或已授权筛选查找候选；按选定 ID 读取组织正文及版本，同名不自动选择。 |
| `organization_relation_create` / `organization_relations_read` | 保存一条组织与组织关系并按任一端查询；返回方向、关系含义、状态及不完整范围，不自动推断反向态度。 |
| `organization_relation_update` | 初始化期间根据实际读取版本以完整新内容覆盖同一组织间关系；过期版本拒绝，结果不确定时返回核查线索。 |
| `organization_membership_create` / `organization_memberships_read` | 保存成员或任职关系，并按组织 ID / 角色 ID 查询；报告未关联人物线索及可见范围，不虚构角色 ID。 |
| 角色身份绑定的组织查询 | 查询和读取当前角色获授权的组织资料及成员关系；身份与等级由可信应用绑定，输入不能选择其他角色或自报权限。 |
| 授权管理与历史查询 | 授权管理由可信应用或受授权管理流程执行；历史查询读取对应资料的过往快照，同样按角色视图过滤。具体接口在后续权限及世界演化实现时确定。 |
| 组织自身和成员关系的修改工具 | 初始化期间按读取版本直接覆盖各自文件；精确工具名、输入及错误结果在格式契约步骤确定。世界演化后的历史保留另行设计。 |
| 外部资料查找 / 正文读取 | 复用获授权的目录工具；可信应用可复用地图和人物存储进行引用核验，见[应用说明](../../../src/app/README.md)。 |
| `delegate_organization` | 主 Agent 向组织 Agent 提供任务、用户要求、所需上下文及资料线索；不接受世界、身份、目录、Session 或权限参数。 |

组织 Agent 的职责提示词需指导它先读取现有资料、核对同名候选、识别组织与地点的不同身份、根据需要建立组织或保留线索，并说明所读依据、未覆盖范围和待审状态。它可以提出新增角色、组织关系或地点需求，但不替其他模块直接落盘。只读成员工具是否向人物 Agent 暴露由可信装配决定，不能仅靠提示词实现保密或权限控制。

独立入口和主 Agent 委派均由可信配置决定世界、稳定组织 Agent 身份、专属工作目录、Session 根、模型与权限。独立运行可以按配置打开目录服务；主 Agent 已持有世界目录服务时应复用该服务并建立独立身份绑定，避免重复打开。停止时取消并等待子运行和已受理文件操作，清理失败保留必要占用并报告；相同世界身份的并发启动须拒绝。与角色创建、世界基础信息和地图 Agent 同时装配时保持身份与目录隔离。

## 开发步骤与验收

第一步的宗门、城邦联盟、身份引用及角色权限走查见[组织模块场景与业务边界](world-initialization-stage-6a-organization-scenarios.md)。

1. **核对业务决策。** 依据宗门及城邦联盟样例细化组织间关系、内部部门、未建档人物线索和权限。成员由组织模块维护、人物侧查询展示，组织及关系采用独立 JSON；初始化期间各类组织资料按版本直接覆盖；组织展开程度采用三个等级。世界演化历史和授权管理服务尚未实现。
2. **组织数据与受控存储。** 在用户确认的格式下设计版本、身份、组织自身资料、组织关系和成员关系的精确 Schema 与工具输入；实现独占创建、校验、受限读取和基于实际版本的写入。先以真实目录和文件测试无效格式、旧版本、同名、重复 ID、越权及数据保留，再确定后续查询。
3. **查询、引用与工具。** 实现组织及关系查询、双向读取成员关系和按需分页；先确定地图 / 人物 ID 读取授权与服务生命周期，再装配只读引用能力。实现由可信应用绑定的角色只读查询视图，按本文五级授权过滤，不实现故事运行或角色自动获取知识。验证多关系、多组织成员、尚未关联人物、同名候选、引用缺失或过期、扫描限额、取消、身份隔离和其他负责人目录写入拒绝。分别验证等级 0、1、3、4 的允许和拒绝、同一角色在不同组织等级不同、角色身份和等级参数伪造、正反向查询及搜索 / 目录 / 分页旁路、权限变更后的旧分页失效；保护范围无法可靠过滤时拒绝读取。
4. **专用 Agent 与主 Agent 接入。** 建立 Preset、职责提示词、组织插件装配、独立入口、Session 和 `delegate_organization`；启用目录时使用可信绑定并单独报告登记结果。验证与地图、角色创建和基础信息专用 Agent 共存，失败或取消后可恢复，不将 Session 或子 Agent 回复当作业务完成证明。
5. **端到端及交付。** 用固定模型替身与真实工具走查宗门和城邦群，核查实际文档、关系、双向成员查询、引用和待审状态；覆盖来源更新、版本冲突、保存结果不确定、目录不可用、跨世界隔离、Session 恢复和资源释放。单独用真实模型检查组织规划、工具使用和来源表述；报告实际结果和未验证范围，模型替身不证明规划质量。完善模块说明、应用入口、架构和必要 Agent Note，验收后等待用户指示，不自动进入人物模块。

**本模块验收**：用户可以定位和审阅不同详略的组织、组织间多种关系和组织成员；人物侧能按绑定身份及组织权限查询同一份成员关系，已建档与未关联的人物可区分。初始化阶段对各类组织资料的版本覆盖符合已确认规则；组织、地点、人物的身份及权威资料不会混同，缺失、未覆盖、无权和未确认状态如实显示。受控角色查询须通过等级过滤和绕过拒绝测试；该局部能力不等于完整角色认知和世界运行已经实现。世界演化后的历史留存须另行实现与验证，不能因本模块验收而声称已实现。

## 实施范围与后续设计

组织展开等级、初始化修改方式、世界演化后的历史留存方案及角色查询等级已在本文给出。具体 JSON Schema、权限授权记录格式和历史恢复流程在各自实现前细化；组织模块内的角色绑定和权限过滤属于本模块，世界推进、权限随剧情的自动变化和角色认知不提前实现。组织关系类型的机器校验和未建档人物线索如何解析可结合首个实现样例继续确定。
