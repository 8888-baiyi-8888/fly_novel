# 影响检查、确认与受控提交契约

本文定义第 8 阶段拟实现的业务契约；现有能力和用户确认的业务选择见[现状盘点](world-initialization-stage-8-inventory.md)。本文件不是已经实现的 API；各步骤以[详细计划](world-initialization-stage-8-impact-review-plan.md)为准。

## 身份、数据与所有权

可信应用固定世界、业务身份、讨论、候选和允许读取 / 提交的目标。目标沿用第 7 阶段的模块、类型和真实标识；文件成果使用可信负责人及规范真实路径。同名结果须先由用户选择，模型不能通过参数扩大目标、权限或世界。检查 Agent 可以读取和提出建议，不能确认、发布或取得能绕过确认的文件 / 存储句柄。

检查报告、用户决定、发布操作记录是独立业务对象，标识由程序生成；Session 只保留对话。记录必须绑定世界和讨论身份，不能以名称、模型自述、列表位置或目录简介代替身份、正文和版本。检查输出、建议和发布结果各自可追溯；报告、决定和发布记录由可信应用持有，释放资源时不能删除用户资料。

## 检查报告

报告至少包括：世界、讨论、报告 ID、生成版本、实际检查的候选 ID / 版本 / 目标 / 基线、每项当前正文版本、检查时间或顺序线索、逐项检查结果、建议及未覆盖范围。候选须为当前有效版本；报告读取完整候选，且提供用户可核对的正文或完整差异及来源。若候选不存在、已放弃、基线过期或身份不符，不能生成可确认报告。

每个检查项使用程序生成的稳定项 ID，并记录检查对象、条件、方向、实际依据、实际读取的版本、发现、状态和建议。状态至少区分：已检查无发现、发现问题、无法判断、失败 / 取消和未覆盖；模型推测与已核实引用分别呈现。当前只能按已记录引用、可重放的查询和明确的文件范围检查；无命中、未关联线索、读取失败和范围未展开不能混同。报告必须写出实际覆盖和未覆盖；不能报告“世界没有冲突”。

检查记录除每份读取资料的版本，还要保存查询条件、分页完成状态和能在提交前重放并比较的范围版本 / 清单凭据，以发现新增、删除和更改的关联。分页未全部完成、版本无法核验或数据读取失败不得伪装成完整检查。各模块读取发生在各自时点，不能把聚合结果称为跨模块原子快照。

建议绑定所属检查项，包含用户能理解的选项、实际变更、受影响目标、对应候选 ID / 版本或明确的不写入处理，以及可能的后果。需要修改其他资料时，先形成所属模块的独立候选并展示；解释文本或未经验证的模型输出不能成为自动发布内容。建议版本、候选或关联证据变化后，旧报告及其选择不得用于发布。

## 选择与确认

可信应用展示当前正文、候选、变化、逐项发现、建议、已覆盖及未覆盖范围，并取得用户明确动作。每个检查项可保存显式选择；显式选择优先。用户明确确认继续，但某项没有单独选择时，仅采用确认前已经展示、仍有效且可执行的该项建议；没有建议、建议缺少具体可审阅效果或不能执行时拒绝确认并请求选择。建议涉及其他目标时，先逐项目标展示并取得用户确认，不因确认原目标而默认确认隐藏改动。

用户已确认：已知重要冲突或部分目标提交将造成已知不一致时，先处理冲突，不能用默认建议或模型判断静默豁免。检查读取失败、取消、部分分页或无可靠版本的已检查依赖阻止提交。明确未覆盖范围可以在向用户逐项展示后，由用户明确确认知悉并继续；不能把未覆盖项改标成已检查，也不能把失败改标成未覆盖来绕过阻止。

确认记录绑定报告 ID / 版本、每个候选 ID / 版本及基线、全部实际读取依赖和范围凭据、用户明确选择、所采用的每项默认建议、未覆盖范围的明确知悉动作及最终发布清单。确认必须来自可信应用明确接收的用户动作；对话文字、等待超时、模型或工具输出不是确认。缺失、取消、跨世界、篡改、重复使用或与当前状态不匹配的确认不能授权写入。

## 提交与最小恢复

只提供可信应用调用的受控提交；模型工具不可持有确认凭据或提交入口。提交受理前重验报告、确认、候选状态和版本、当前正文基线、所有已读取依赖以及完整查询范围凭据；发现变化、无法读取或无法可靠比较时停止，重新检查并要求用户审阅。检查到发布期间必须使用所有本进程相关写入口共同参与的协调机制，并在每个所属模块的发布点执行条件版本写入；如果无法覆盖某个入口，不为该目标开放提交。既有身份占用、独立服务队列和单独一次复查不足以证明这一关系。

发布清单按用户确认的目标逐项记录目标、候选及版本、基线、预期发布内容的可校验摘要、所属模块和前后状态。每项至少区分未开始、发布中 / 结果不确定、已核实发布和已知失败；一次多目标操作可以部分完成，不能报为全部成功或自动回滚。用户已确认：中途失败或结果不确定时停止后续写入，核查实际正文、候选、模块索引和目录状态，展示逐项结果；需要继续时重新检查，由用户明确选择后形成新的授权。重复请求或重启不能二次应用同一发布，也不能覆盖之后出现的版本。

发布操作记录采用独立严格版本化记录，持久化发布前检查所需身份、版本、预期结果及恢复阶段；发布前必须能核查该记录。用户确认、发布记录、目标文件及候选文件不是跨文件事务：任一写入的响应丢失或进程中断都须按实际文件和记录重新核查，无法区分时保留文件并阻止自动推进。只承诺经过测试的进程中断恢复；不把文件重命名推断为跨文件事务或断电持久性保证。目录刷新与正文发布分开记录，目录失败不能抹去已发布正文或伪装成正文未发布。

当前讨论候选版本 1 没有已提交状态。拟在实施时为提交成功的候选引入版本 2 `committed` 状态：保留候选 ID、正文、基线和发布记录引用；版本 1 的 `active` / `abandoned` 保持可读取，旧数据不批量改写。发布完成后以条件写入升级单份候选；旧读取器遇到版本 2 必须拒绝而不是将其解释为 `active`。若正文已发布但候选升级未完成，恢复记录阻止再次发布及释放占用，先按实际内容和记录核查，再完成或报告不确定。未知版本、损坏或身份不一致保留原文件并拒绝自动迁移。版本 2 格式、升级及拒绝路径须在代码和测试中明确；不同版本程序同时写入同一世界不受支持。

局部修改接受不等同于整个第一版完成。地图地点仍为其模块定义的建议状态；人物既有 `commit` 会将人物标记为 `confirmed` 且使用另一套候选，不能未经适配直接用于本流程。首批人物发布须明确保留原有状态的策略、索引和恢复日志如何绑定此次审阅；不覆盖已有旧候选，不因为复用旧代码而改变用户尚未确认的状态。

## 样例与拒绝路径

- 曲水城候选由昼夜开放改为夜间关闭。历史查询中已关联地点的事件作为线索，人物正文中未结构化引用地点的范围明确列为未覆盖；用户明确知悉未覆盖后才能继续。若读取历史失败或分页未完成，阻止确认和提交。
- 林岚正文与成员职务各自形成候选。用户只选择正文且已知会造成成员信息不一致时，阻止部分发布；两项的用户选择、候选版本和发布结果分别记录。若地点已发布而人物发布失败，保留地点实际结果并停止，不能把整个操作标记为成功或回滚。
- 用户确认后，新增一个符合已检查条件的成员记录，或更新一个原本未命中的关联：即便旧命中项版本未变，也必须通过范围凭据重查发现变化，使旧报告和确认失效。缺少能重放的范围凭据时不得声称范围仍有效。
- 对某项未显式选择，只有用户明确确认继续且已看到完整可执行建议时使用该建议；仅有“建议以后处理”或建议需修改但没有已审阅候选时拒绝默认执行。取消确认、关闭界面和 Agent 输出“已确认”均不触发发布。

这些场景是实现前契约走查。具体文件布局、协调机制和模块适配以接下来的代码设计及测试验证为准；第 8 阶段不承诺完整初始化恢复或最终交付。
