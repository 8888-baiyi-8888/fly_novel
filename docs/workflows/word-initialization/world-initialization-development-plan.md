# 世界初始化工作流开发计划

本文记录已确认的世界初始化方向和待讨论的问题，作为后续详细设计与分阶段开发的依据。项目背景参考 [PROJECT_VISON.md](../../PROJECT_VISON.md)；其中的历史方案不自动视为本计划的既定契约。

整体业务流程见[世界初始化工作流方案](world-initialization.md)；本计划按功能依赖安排实施阶段，具体接口在各阶段开始时讨论。

## 目标与边界

世界初始化根据用户构想建立世界观、重要角色的信息和世界未来发展的总体规划，为后续世界演化与具体故事的产生提供基础。规划可以包括世界的性质、地图大致分布、当前时间、角色的发展方向及未来重大故事，不要求预先确定所有事件的过程和结果。

世界有自己的发展，写手从世界中发生的事情中提取和组织故事。一部小说可以包含多个故事，同一个世界也可以为多部小说提供故事。世界中的事实、角色认知和小说呈现需要区分。

初始化允许内容详略不同。例如，地图可以先确定几个洲，重点规划亚洲、中国和安徽，而其他地区仅有名称或概况。角色、地区和未来发展不必全部固定；留白供后续事件推演和世界演化时继续探索。第一版的完整指形成可整体审阅的世界方案，不要求所有内容都详细或确定。

已确定的事实和规则、未来的发展规划、粗略设想与尚未确定的空白在讨论和交付时应能区分。发展规划为后续演化提供方向，具体约束程度及调整方式仍待讨论。

## 预期使用流程

1. 用户提供初始构想，输入可以内容繁杂、篇幅较长，也可以混合不同主题和详细程度的信息。
2. 系统理解并整理用户输入，生成世界方案的第一个完整版本；根据用户关注的重点决定各部分的规划深度，保留必要空白。
3. 用户审阅第一版，可选择某个部分与 Agent 单独讨论和优化。用户可以重复选择不同部分进行优化。
4. 每次局部优化后，Agent 检查对其他内容的影响，列出冲突与处理建议，供用户选择和确认。
5. 用户对冲突作出选择时，以用户选择为主；用户确认继续处理但未对某项作出选择时，采用 Agent 的处理建议。处理后向用户展示调整结果。
6. 用户完成所需的优化后，交付世界初始化结果，供后续世界演化使用。完成不意味着世界设定永远不可修改。

## 与后续演化的关系

后续演化需要专门的 Agent 能力。导演 Agent 从全局关注世界发展，主动发现和推动变化，并协调相关能力参与；角色的具体行动由角色根据自身情况作出。导演与负责地区、角色或其他内容的专门 Agent 如何分工，及其与初始化阶段 Agent 的关系，尚待具体设计。

初始化结果需要让后续演化能够理解世界现状、发展方向和可继续探索的空间。世界如何持续演化、故事如何提取和组织，不在本阶段预先确定具体实现。

世界资料共享和按需读取的整体方案见[世界资料共享与读取设计](../../modules/world-information-access.md)。

## 第一版内容与交付标准（讨论稿）

本节提出第一版内容的组织方式和交付判断，具体交互规则待用户确认。不同世界的设定重点不能预先穷举，Agent 根据用户输入和当前世界构想自行识别需要规划的内容，组织第一版的结构与细化程度。用户可以审阅、调整或补充 Agent 识别出的重点。

Agent 需要理解用户的创作方向，识别世界的基本性质、当前处境、重要参与者、未来发展方向和主要待定问题；这些是帮助理解构想的观察方向，不是必须逐项填满的固定栏目。地图、时代、角色、组织等内容根据构想的实际需要确定深度。修仙世界的境界体系只是可能由 Agent 识别出的重点示例，不是预设的题材模板或强制字段。

第一版应形成可整体审阅的方案，并体现用户明确提出的重点。对 Agent 识别出的重要内容，可以依据已有构想提出初步建议，或说明暂时留白；其他不必要的细节可以粗略或完全不写。不得为了填满栏目虚构用户未确认的细节或封死未来发展，也不要求穷举所有尚未设定的内容。

用户明确提供的内容与 Agent 补充的建议需要在审阅时可区分；Agent 补充的内容不能仅因出现在初稿中就视为用户指定。内容不要求用户按固定表格逐项输入，也不要求每个方面对应一个独立 Agent。

### 交付判断

建议将“生成第一版供审阅”和“完成初始化并交付后续演化”区分。第一版呈现 Agent 识别出的重点、方案、主要待定内容和建议来源后即可供用户审阅；存在疑问或冲突不妨碍展示，但不得隐藏。

建议完成初始化前检查以下条件：

1. 用户能理解世界的基本性质、当前时代和创作重点，重点内容已达到用户认可的细化程度。
2. Agent 根据当前构想识别的重要设定得到适当规划，或明确列为待定；重点内容足以支持后续讨论或演化，不要求补齐全部细节。
3. 已确定事实、发展规划和留白可以区分，后续使用者能够知道哪些内容应遵守、哪些仍可探索。
4. 已发现的冲突和处理结果对用户可见；重要冲突是否允许留待后续处理，仍需用户决定。
5. 用户审阅当前版本并选择完成初始化。交付包含当前方案和主要待定问题，而不是将未确定内容包装成事实。

实际交付形式、如何判断内容足以支持后续演化，以及空白被补充后何时成为正式事实，留待结合使用示例继续设计。

## 实施方向

采用受约束的主 Agent 主导方案：主 Agent 根据用户构想识别重点、组织任务并与用户协作，按需直接处理或委派子 Agent，不预设地图、角色等固定节点或固定 Agent 分类。用户确认、资料提交和访问范围由程序保证；是否需要独立工作流引擎或 LangGraph 节点，根据实际交互、恢复和可靠性需求决定。

现有 Harness 提供 Agent 装配、Loop、工具执行和 Session 等基础能力，子 Agent 委派与世界资料共享需要另行实现。Session 保存对话和执行记录，不代替世界方案、待审修改和确认状态的业务管理。现有能力和装配方式见 [Agent 包说明](../../../src/agents/README.md)。

按[学习型开发要求](../../development-plan.md#学习型开发要求)逐步推进：每阶段先说明问题、实际使用示例、输入输出和预期行为，再确认接口并实现最小功能；完成后验证并按项目要求对照 DeepSeek Harness 对应设计，等待明确指示再进入下一阶段。以下顺序是实施计划，不代表接口或具体目录已经确定。

## 功能与依赖

| 功能 | 职责 | 主要依赖 |
| --- | --- | --- |
| 主 Agent | 理解构想、识别重点、组织任务、整合方案并与用户交流 | Harness、提示词和运行入口 |
| 子 Agent 委派 | 创建受托 Agent，交付任务并回传结果，管理取消、失败和清理 | 主 Agent 工具调用、Harness 生命周期 |
| 方案表达与工作区 | 管理可审阅方案、来源、状态和待审修改 | 最小业务数据契约，初期可在内存中运行 |
| 世界资料读取 | 按线索查找、按标识读取和查看已记录的关联 | 方案资料组织、世界和可见视图边界 |
| 第一版生成 | 根据构想确定重点，直接处理或委派，再整合可整体审阅的方案 | 主 Agent、委派机制、最小工作区和资料读取 |
| 局部讨论 | 选定内容，多轮讨论并形成待审修改 | 当前方案定位、会话和待审修改 |
| 影响与冲突检查 | 检查修改可能影响的资料，列出检查范围、问题和建议 | 待审修改和资料读取，可按需委派 |
| 确认与提交 | 根据用户选择或经确认的建议更新方案并展示结果 | 待审修改、检查结果和程序控制的提交边界 |
| 持久化与恢复 | 保存和恢复方案、未完成工作及必要的确认状态 | 业务数据契约和版本策略 |
| 最终交付 | 用户选择完成后交付方案和待定事项 | 当前方案、冲突处理和用户确认 |

第一版供用户审阅，不因生成成功就成为已确认世界事实。局部调整的提交和最终完成初始化分别需要程序控制的确认边界；用户要求、Agent 建议、已确定事实、发展规划和留白需要能够区分。

## 开发阶段

### 1. 使用场景与最小业务契约

- 详细讨论顺序和示例见[第一阶段计划](world-initialization-stage-1-plan.md)。
- **问题与示例**：用户只提供零散的小说构想，例如“想写非常规修仙小说，角色智商在线。且法无好坏，人有好坏，故而有好坏”。说明 Agent 如何识别需要规划的内容、生成第一版，用户如何选择某个部分继续讨论，以及如何确认冲突处理。
- **范围**：明确第一版展示、局部选择、待审修改和确认前后的行为，确定世界、方案内容、来源、状态和确认动作等最小概念。Agent 根据构想判断是否需要规划地区、境界等内容及其深度；示例不作为所有世界的固定字段，也不预先设计完整世界模型。
- **验收**：能用示例走通从输入到确认的预期交互，说明信息在生成、讨论和确认前后的状态，并列出仍未确定的交付条件。

### 2. 基础世界初始化主 Agent

- **问题与示例**：用户输入构想，主 Agent 识别重点并组织初步方案，验证其理解和规划职责。
- **范围**：复用现有 Harness，建立主 Agent 的 Preset、职责提示词和最小运行入口。此阶段的输出用于验证主 Agent，不作为完整的多 Agent 第一版。
- **验收**：使用固定模型替身验证装配、输入、输出、失败和清理；通过实际使用示例检查重点识别与留白，真实模型需要配置时明确报告是否执行。

### 3. 子 Agent 委派机制

- **问题与示例**：主 Agent 将一项需要独立分析的任务交给子 Agent，获得结果并决定如何整合。
- **范围**：提供最小委派能力，明确任务、必要上下文、可见范围、结果回传和资源所有权；处理创建与执行失败、父任务取消及清理。子 Agent 按任务创建，不预建题材分类；初期可串行执行。
- **验收**：验证主 Agent 通过工具完成委派与结果回传，并覆盖创建失败、执行失败、取消和资源释放。

### 4. 最小方案工作区与资料读取

- **问题与示例**：主 Agent 和子 Agent 在同一世界的工作视图中查找并读取用户要求、已有建议和留白。
- **范围**：依据实际示例建立最小方案工作区和按需读取能力，可先使用内存及固定测试数据；调用方不依赖底层文件路径。写入由受控应用代码管理，子 Agent 不直接改写已确认资料。资料读取方向见[世界资料共享与读取设计](../../modules/world-information-access.md)。
- **验收**：验证不同 Agent 在授权范围内读取同一份资料及世界隔离；区分查询无结果、明确留白和读取失败。

### 5. 主、子 Agent 协作生成第一版

- **问题与示例**：主 Agent 理解构想并识别重点，按需委派分析，整合结果形成可整体审阅的世界方案。
- **范围**：组合主 Agent、委派与资料读取能力，让不同部分详略不同；展示用户要求、Agent 建议、发展方向和主要留白，不将未来规划包装成已发生事实。
- **验收**：使用不同构想验证规划重点不依赖固定清单，检查委派结果的整合以及矛盾和不确定内容的展示；固定模型替身验证协作行为，真实模型示例单独评估生成质量并说明是否执行。

### 6. 局部讨论与待审修改

- **问题与示例**：用户选择安徽的某个城市或一个角色进行多轮讨论，再切换到其他内容；主 Agent 可按需委派分析。
- **范围**：明确会话、当前方案和待审修改的关系。讨论形成的建议进入待审工作区，当前方案保持可辨认，未确认的修改不覆盖当前方案。
- **验收**：验证同一部分的多轮讨论和不同部分的切换；取消、Agent 失败或尚未确认时，不将待审修改当作已提交结果。

### 7. 影响检查、用户选择与受控提交

- **问题与示例**：局部修改地区封闭规则后，与角色已有的往返经历发生冲突；系统展示影响、冲突和建议，等待用户选择。
- **范围**：查找相关资料并展示检查范围；用户选择优先，用户确认继续但未对某项选择时采用对应的 Agent 建议。提交绑定用户审阅的修改和检查结果；方案在此期间变化时重新检查或重新审阅，确认后展示实际结果。
- **验收**：覆盖明确选择、确认后采用默认建议、取消、检查或保存失败及方案版本变化；不把未发现冲突表述为不存在冲突，失败时明确实际提交结果。

### 8. 持久化、恢复与最终交付

- **问题与示例**：用户中断后恢复未完成的初始化，审阅当前方案和待定事项，并选择完成初始化。
- **范围**：依据前述阶段验证的业务对象和确认行为确定持久化格式、版本和恢复策略；Session 管理会话，业务数据管理方案与确认状态。组装完整入口并明确后续世界演化的交接；已有数据的格式变化采用迁移或明确拒绝读取策略，保留原数据。
- **验收**：验证从新建、第一版、局部优化和确认到完成的完整过程，以及中断后的恢复、新入口和必要的构建产物；后续演化尚未接入时明确限制，不声称已经贯通。

### 阶段安排说明

资料访问分为最小工作区与长期持久化两个阶段：第一版协作前需要共享读取；长期格式在局部讨论与确认行为经过示例验证后确定。如果第一版实际需要跨进程恢复，可提前实现满足该需求的最小持久化，并明确版本与数据处理策略。

确认边界随能力逐步建立：第一版区分建议与已确认内容；局部讨论隔离待审修改；影响检查阶段完善用户选择和受控提交。子 Agent 委派作为独立阶段验证，第一版生成时由主 Agent 按任务决定是否使用，不强制每次委派。

## 既有数据

没有需要兼容的外部调用方，不为旧接口增加兼容层。已有持久化数据与代码兼容性分开处理：格式变化时明确版本和迁移或拒绝读取策略，不删除用户数据。

## 待讨论

- 第一版内容范围与交付标准的讨论稿见上节，待用户确认和调整。
- 重大故事规划是否允许用户指定必须发生的节点，以及规划随演化变化的规则。
- 冲突选择、确认与未选择时的具体交互；是否允许带未解决冲突完成初始化。
- 局部优化的边界、跨模块影响的识别方式，以及 Agent 建议的审阅和修改方式。
- 导演的主动推进方式、专门 Agent 的职责划分和世界演化与初始化之间的接口。
- 世界方案的持久化格式、版本管理、已有产物处理和对现有章节流程的影响。
