# 世界初始化工作流开发计划

本文记录已确认的世界初始化方向和待讨论的问题，作为后续详细设计与分阶段开发的依据。项目背景参考 [PROJECT_VISON.md](../../PROJECT_VISON.md)；其中的历史方案不自动视为本计划的既定契约。现有小说级工作流的实际行为见[工作流模块说明](../../../src/workflow/README.md)。

整体业务流程见[世界初始化工作流方案](world-initialization.md)；流程确定后再细化支撑能力和实施阶段。

## 目标与边界

世界初始化根据用户构想建立世界观、重要角色的信息和世界未来发展的总体规划，为后续世界演化与具体故事的产生提供基础。规划可以包括世界的性质、地图大致分布、当前时间、角色的发展方向及未来重大故事，不要求预先确定所有事件的过程和结果。

世界有自己的发展，写手从世界中发生的事情中提取和组织故事。一部小说可以包含多个故事，同一个世界也可以为多部小说提供故事。世界中的事实、角色认知和小说呈现需要区分。

初始化允许内容详略不同。例如，地图可以先确定几个洲，重点规划亚洲、中国和安徽，而其他地区仅有名称或概况。角色、地区和未来发展不必全部固定；留白供后续事件推演和世界演化时继续探索。第一版的完整指形成可整体审阅的世界方案，不要求所有内容都详细或确定。

已确定的事实和规则、未来的发展规划、粗略设想与尚未确定的空白在讨论和交付时应能区分。发展规划为后续演化提供方向，具体约束程度及调整方式仍待讨论。

## 预期使用流程

1. 用户提供初始构想，输入可以内容繁杂、篇幅较长，也可以混合不同主题和详细程度的信息。
2. 系统理解并整理用户输入，生成世界方案的第一个完整版本；根据用户关注的重点决定各部分的规划深度，保留必要空白。
3. 用户审阅第一版，可选择某个部分与 Agent 单独讨论和优化。用户可以重复选择不同部分进行优化。
4. 每次局部优化后，Agent 检查对其他内容的影响，列出冲突与处理建议，供用户选择和确认。
5. 用户对冲突作出选择时，以用户选择为主；用户确认继续处理但未对某项作出选择时，采用 Agent 的处理建议。处理后向用户展示调整结果。
6. 用户完成所需的优化后，交付世界初始化结果，供后续世界演化使用。完成不意味着世界设定永远不可修改。

## 与后续演化的关系

后续演化需要专门的 Agent 能力。导演 Agent 从全局关注世界发展，主动发现和推动变化，并协调相关能力参与；角色的具体行动由角色根据自身情况作出。导演与负责地区、角色或其他内容的专门 Agent 如何分工，及其与初始化阶段 Agent 的关系，尚待具体设计。

初始化结果需要让后续演化能够理解世界现状、发展方向和可继续探索的空间。世界如何持续演化、故事如何提取和组织，不在本阶段预先确定具体实现。

世界资料共享和按需读取的整体方案见[世界资料共享与读取设计](../../modules/world-information-access.md)。

## 第一版内容与交付标准（讨论稿）

本节提出第一版内容的组织方式和交付判断，具体交互规则待用户确认。不同世界的设定重点不能预先穷举，Agent 根据用户输入和当前世界构想自行识别需要规划的内容，组织第一版的结构与细化程度。用户可以审阅、调整或补充 Agent 识别出的重点。

Agent 需要理解用户的创作方向，识别世界的基本性质、当前处境、重要参与者、未来发展方向和主要待定问题；这些是帮助理解构想的观察方向，不是必须逐项填满的固定栏目。地图、时代、角色、组织等内容根据构想的实际需要确定深度。修仙世界的境界体系只是可能由 Agent 识别出的重点示例，不是预设的题材模板或强制字段。

第一版应形成可整体审阅的方案，并体现用户明确提出的重点。对 Agent 识别出的重要内容，可以依据已有构想提出初步建议，或说明暂时留白；其他不必要的细节可以粗略或完全不写。不得为了填满栏目虚构用户未确认的细节或封死未来发展，也不要求穷举所有尚未设定的内容。

用户明确提供的内容与 Agent 补充的建议需要在审阅时可区分；Agent 补充的内容不能仅因出现在初稿中就视为用户指定。内容不要求用户按固定表格逐项输入，也不要求每个方面对应一个独立 Agent。

### 交付判断

建议将“生成第一版供审阅”和“完成初始化并交付后续演化”区分。第一版呈现 Agent 识别出的重点、方案、主要待定内容和建议来源后即可供用户审阅；存在疑问或冲突不妨碍展示，但不得隐藏。

建议完成初始化前检查以下条件：

1. 用户能理解世界的基本性质、当前时代和创作重点，重点内容已达到用户认可的细化程度。
2. Agent 根据当前构想识别的重要设定得到适当规划，或明确列为待定；重点内容足以支持后续讨论或演化，不要求补齐全部细节。
3. 已确定事实、发展规划和留白可以区分，后续使用者能够知道哪些内容应遵守、哪些仍可探索。
4. 已发现的冲突和处理结果对用户可见；重要冲突是否允许留待后续处理，仍需用户决定。
5. 用户审阅当前版本并选择完成初始化。交付包含当前方案和主要待定问题，而不是将未确定内容包装成事实。

实际交付形式、如何判断内容足以支持后续演化，以及空白被补充后何时成为正式事实，留待结合使用示例继续设计。

## 实施方向

采用受约束的主 Agent 主导方案作为开发方向：主 Agent 根据用户构想识别重点、组织任务并与用户协作，不预设地图、角色等固定节点。用户确认、资料提交和访问范围由程序保证；是否需要独立工作流引擎或 LangGraph 节点，根据实际交互、恢复和可靠性需求决定。子 Agent 是按需引入的候选能力，不作为第一个闭环的前置条件。

按[学习型开发要求](../../development-plan.md#学习型开发要求)逐步推进：每阶段先说明问题、实际使用示例、输入输出和预期行为，再确认接口并实现最小功能；完成后验证并按项目要求对照 DeepSeek Harness 对应设计，等待明确指示再进入下一阶段。以下顺序是实施计划，不代表接口或具体目录已经确定。

## 开发阶段

### 1. 使用场景与最小契约

- **问题与示例**：用一个输入混杂、地区详略不一的修仙世界示例，说明用户给出构想后看到什么，如何继续讨论某个角色或地区，以及如何确认冲突处理。
- **确定内容**：明确第一版和局部优化的输入、用户可见输出、留白与建议的区分；界定确认前后的行为。示例中的境界或地区不作为所有世界的固定字段。
- **验收**：能用示例走通从输入到确认的预期交互，列出仍未确定的交付条件；不实现世界数据的完整模型。

### 2. 单主 Agent 生成第一版

- **问题与示例**：用户输入一段构想，主 Agent 识别规划重点，返回可审阅的世界方案，并标明用户要求、建议和留白。
- **范围**：复用现有 Harness 的 Agent、Loop 和 Session 能力，按实际需要装配最小入口；不预设具体世界类型的节点或子 Agent。
- **验收**：通过固定模型替身验证输入传递、结果返回和失败传播，并以实际使用示例检查结果是否支持审阅；真实模型验证需要配置时明确报告是否执行。

### 3. 多轮讨论与局部优化

- **问题与示例**：用户在第一版后选择安徽的某个城市或一个角色，继续多轮讨论并获得修改建议。
- **范围**：明确会话、当前方案与待审修改的关系；用户可以反复选择不同内容，尚未确认的建议不覆盖确认方案。先使用完成示例所需的最小资料访问方式。
- **验收**：验证多轮对话能定位用户选择的部分，待审建议与当前方案可区分；验证取消或失败时不会将建议当作已确认结果。

### 4. 冲突检查与确认

- **问题与示例**：局部修改地区封闭规则后，与角色已有的往返经历发生冲突；系统展示冲突和处理建议，等待用户决定。
- **范围**：确定检查范围和结果表达；用户选择优先，用户确认继续但未指定某项时采用 Agent 建议。程序保证确认前不提交相关修改，确认后展示实际结果。
- **验收**：覆盖明确选择、未逐项选择而确认、取消、检查或保存失败；展示检查范围，不把未发现冲突表述为不存在冲突。

### 5. 资料保存与按需读取

- **问题与示例**：保存一个世界方案，重新打开后按名称或线索找到安徽及有关角色，并继续局部优化。
- **范围**：根据前面示例确定最小数据、版本和读取契约，区分世界、正式方案和待审修改；调用方通过工具获取资料，不依赖预设题材或固定文件布局。设计参考[世界资料共享与读取](../../modules/world-information-access.md)。
- **验收**：验证世界隔离、保存与恢复、来源和状态、无结果与留白的区分，以及无效或不支持版本的明确处理；不能静默误读或删除既有数据。

### 6. 按实际问题评估子 Agent

- **触发条件**：前述闭环暴露上下文过大、任务隔离不足或独立分析确有价值等具体问题时，选择一个任务尝试委派；没有实际问题时不强制开发子 Agent。
- **范围**：明确任务、可见资料、结果及依据、取消与失败传播和资源归属；委派结果仍经过主 Agent 整合与必要的用户确认。
- **验收**：用同一实例验证直接处理与委派的区别，并覆盖失败、取消和清理；不预建按题材分类的固定子 Agent 清单。

### 7. 交付与旧流程清理

- **问题与示例**：用户确认当前世界方案达到初始化要求，系统交付方案和待定事项；明确与后续世界演化的交接，不把现有章节流程兼容性当作已解决。
- **范围**：核对旧入口、脚本、测试和仓库内引用，逐项决定替换或删除；格式变化明确版本和数据迁移或拒绝读取策略，保留用户数据。
- **验收**：验证新入口、交付结果及必要的构建产物；清理过时代码和文档时同步更新仓库内引用。若章节接入尚未完成，明确其限制，不声称端到端已贯通。

## 现有代码处理

当前没有需要兼容的外部调用方，可以按照新设计删除旧实现，不为旧入口或接口保留兼容层。现有 [小说级工作流](../../../src/workflow/novel_workflow/workflow.ts)及[应用入口](../../../src/app/novel-workflow/workflow.ts)仍被仓库内代码和脚本引用；[章节入口](../../../src/app/run-chapters.ts)引用其产物路径，小说运行时也引用旧模块中的角色 ID 生成逻辑。删除时同步处理这些源码引用、入口、测试和文档，使保留的代码能够构建。

可以在新实现前清理旧流程，但应先确定删除边界与仓库内依赖的处理方式；共享能力按实际需要保留或迁移，不为保留旧流程而保留。已有持久化数据与代码兼容性分开处理：格式变化时明确版本和迁移或拒绝读取策略，不删除用户数据。

## 待讨论

- 第一版内容范围与交付标准的讨论稿见上节，待用户确认和调整。
- 重大故事规划是否允许用户指定必须发生的节点，以及规划随演化变化的规则。
- 冲突选择、确认与未选择时的具体交互；是否允许带未解决冲突完成初始化。
- 局部优化的边界、跨模块影响的识别方式，以及 Agent 建议的审阅和修改方式。
- 导演的主动推进方式、专门 Agent 的职责划分和世界演化与初始化之间的接口。
- 世界方案的持久化格式、版本管理、已有产物处理和对现有章节流程的影响。
