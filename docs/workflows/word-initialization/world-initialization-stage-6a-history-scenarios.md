# 历史设定第一步：现状与场景走查

本文执行[历史设定详细计划](world-initialization-stage-6a-history-plan.md#开发步骤与验收)的第一步，以已有代码为起点走查两类世界、首版输入输出和验收边界。示例中的名称和内容只用于说明，不是固定世界模板；格式字段和工具仍需在后续契约步骤设计。

## 一、实际能力与缺口

| 已有能力 | 历史模块可复用的部分 | 当前限制 |
| --- | --- | --- |
| [世界工作区和资料目录](../../../src/world-init/README.md) | 可信世界与负责人目录校验、进程内身份占用、按路径登记和读取成果正文，目录状态和版本核对。 | 尚无历史专属目录或事件服务；目录简介不能替代正文，也不代表用户确认。 |
| [世界基础信息 Agent](../../../src/app/agents/world-basics.ts) | 已授权世界背景可保存为独立待审 Markdown 并按现有资料读取路径查阅。 | 没有统一的机器可比较世界纪年或初始化时点服务；不能从自由正文或文件时间自动推出事件日期。 |
| [地图插件](../../../src/agents/plugins/map/README.md) | 地点 ID、名称和层级查询、世界绑定、未知与未展开范围。 | 引用历史参与地点需另行装配只读句柄及核验；同名、未建档或地图未覆盖不能自动视为不存在。 |
| [组织插件](../../../src/agents/plugins/organization/README.md) | 组织 ID、组织与成员关系、初始化版本更新，以及规划者读取能力。 | 历史事件不是组织关系；组织角色的等级不自动变成角色对历史的认知。 |
| [人物插件](../../../src/agents/plugins/character/README.md)与[角色创建入口](../../../src/app/agents/character-creator.ts) | 角色 ID、自由正文、人物关系、未确认资料版本更新和待审能力。 | 人物正文可记录本人已知或误认的往事，但没有历史事实与角色认知的自动同步或长期记忆恢复。 |
| [跨模块引用装配](../../../src/world-init/storage/organization-references.ts) | 组织通过可信应用复用同世界地图和人物存储，验证世界与负责人；可借鉴引用核验和资源归属。 | 专用 Agent 内部打开的句柄不会自动共享；没有覆盖所有模块的统一 ID 解析或路径无关读取服务。 |

[地图 Agent 测试](../../../src/app/tests/map-agent.test.ts)、[组织引用测试](../../../src/app/tests/organization-references.test.ts)、[人物关系装配测试](../../../src/app/tests/character-relationships-assembly.test.ts)和[世界工作区测试](../../../src/world-init/tests/world-workspace-config.test.ts)提供可借鉴的真实目录、跨世界、取消或生命周期验证；它们不证明历史存储、时间线或历史 Agent 已存在。固定模型替身只验证其预设执行路径。没有历史事件的格式、专用插件、专用 Agent、委派工具、时间线服务或角色历史记忆接口。

## 二、已确认的职责和修改边界

历史记录初始化起始时点之前发生的事情；初始化时仍持续的整体处境归初始局势，未来可能发生的变化归宏观发展蓝图。历史可说明对当时世界的已知影响，但不维护另一份完整当前局势，不预定未来角色行动或故事结局。

重要子事件按需独立建档，一个子事件在需要时可以有多个上级，每条上级关系表达实际含义；主题相关、先后和因果不是自动成立的上级关系。同一事件中分别记录公开说法、隐藏内容及未知或留白；多个有分歧的说法可并存，不能因为有叙述就判定其中一个为世界真相。

时间可相对于初始化起始时点或已知纪年表达，两种参考可共存；缺少可靠基准或换算关系时保留原表述。未确认历史在初始化期间按读取版本直接更新，已确认历史的修改形成待审候选；世界演化造成变化时保留原状态及世界时间依据。候选提交流程及演化留存尚不能视为已有实现。

历史 Agent 和世界规划者可以读取完整历史。初始化人物资料记录角色当时已知或误认的内容；以后由实际经历、交流或发现形成新认知。历史模块不维护角色知情权限表或预设未来谁会知道什么；在角色运行信息隔离真正设计并实现前，不把完整历史直接当成角色认知。

## 三、开放式修仙世界

假设世界起始时点只确定为“现在”，并无统一纪年。公开传说称灵脉变动导致青云宗约三百年前迁徙；另一份记载只说迁徙发生在山门修建之前，幕后原因没有确定。地图中可能只有青云山区域概况，青云宗有组织资料，一位参与迁徙的散修尚未建档。

| 输入或问题 | 首版应处理的内容 | 不应推断的内容 |
| --- | --- | --- |
| 宗门迁徙约在起始时点三百年前 | 建立迁徙事件，保留约略时间和“相对于初始化起始时点”的参考；没有可信换算就不生成精确年份。 | 文件创建日期、用户当前日期或其他世界的纪年就是事件日期。 |
| 山门修建有独立资料需求 | 按需建立山门迁建子事件，明确与迁徙之间是组成或先后等哪种关系。 | 所有迁徙阶段都必须独立建档；只有一个关系就能推导所有因果。 |
| 公开说法称灵脉自然变动，幕后原因未知 | 同一事件保留公开说法和“隐藏原因未知”；需要时可再记另一份有分歧的说法及其依据。 | 把未知内容补成 Agent 虚构的阴谋，或把一方说法自动确认为事实。 |
| 宗门和地区已有资料，散修没有档案 | 引用已核验的组织、地点 ID；散修保留可辨认线索。读取失败与未建档分别说明。 | 用同名文本冒充 ID，或把一名参与者自动加入某组织。 |
| 角色资料写有与迁徙年代可能冲突的经历 | 读取实际人物资料及参考时间，报告需核实的冲突和依据；如果寿命或时间不详则说明不能判断。 | 自动修改角色年龄、历史经过或将冲突归因于错误认知。 |

在此例中，历史可以只覆盖宗门迁徙及近期需要的山门；其他宗门和远古历史留白，不因缺少文件推断不存在。

## 四、资源有限的城邦群

假设青河战争与北岸冲突在时间上部分重叠，停战谈判同时结束两场冲突。曲水城在地图中是地点，曲水议会在组织模块中是政治组织。战争公开说法是水源争夺，但幕后原因尚无确定结论；起始时各城仍有供水压力，未来是否再次开战尚未决定。

| 输入或问题 | 首版应处理的内容 | 不应推断的内容 |
| --- | --- | --- |
| 青河战争和北岸冲突部分重叠 | 记录已知的时间范围或相对关系；若年份不足，将不可比较部分保留未知。 | 将重叠事件强行排成先后，或因时间相近就断定一方导致另一方。 |
| 停战谈判同时属于两场冲突 | 在需要独立查询时建立一份谈判事件，分别关联两个上级，并说明两条组成关系。 | 为两场冲突各复制一份权威谈判正文，或将普通主题关联自动识别成上级关系。 |
| 停水损失、现在仍缺水、未来可能开战 | 停水损失作为历史影响线索；现在的供水处境交由初始局势；未来变化交由发展蓝图。 | 把未来战争保存为已发生，或让历史文件替代当前局势的完整资料。 |
| 曲水城和曲水议会参与 | 分别引用地图地点与组织 ID；缺失或无法核验时保留线索。 | 因为名称相近就把地点与政体当成同一对象。 |
| 林岚初始化时只知道公开记载，顾青可能有不同看法 | 各自人物资料记录当时认知；历史保存公开说法与未知原因。 | 在历史里为角色配置秘密权限或知情名单，也不预写未来会发现的内容。 |

两场冲突的远方战线、各城内部经历及未关联人物可以留白。独立子事件是否详细，不由某个上级事件的展开程度自动决定。

## 五、首版输入、输出与验收

**输入：** 可信应用绑定的世界、历史负责人、专属目录与授权；用户对初始化历史的要求；实际可读取的世界基础、人物、地图、组织与已有历史资料。缺少其他模块或只读到目录简介时，保留缺口并按实际能力报告。

**输出：** 供用户整体审阅的历史事件及必要子事件，包含已知经过、世界时间或其未定说明、公开与隐藏内容、明确留白、真实引用或待关联线索，以及可核查的已知影响和未解决问题。保存、登记和 Agent 返回不等于用户确认世界事实；本步骤不决定最终 JSON 字段或提前生成完整世界历史。

| 验收场景 | 下阶段应能验证的结果 |
| --- | --- |
| 时间与事件 | 区分约略、未知、可比较与不可比较；先后、重叠和因果不互相冒充，展示实际查询覆盖范围。 |
| 多级和多上级 | 一份子事件可关联多个上级；沿不同路径找到同一 ID，缺失上级、重复关联、循环及遍历截断有明确处理。具体约束在下一步契约确定。 |
| 事实、说法与角色 | 公开说法、隐藏内容和未知不混同；人物已有认知由人物自身资料表达，不生成角色历史权限表或自动补全角色知识。 |
| 跨模块引用 | 地点、组织、人物 ID 经可信世界与负责人核验；没有服务、目标缺失、无权读取、同名和未建档线索不混同。 |
| 修改和保留 | 初始化未确认资料按版本更新；已确认内容的候选与后续演化保留是分别需要实现的能力。旧文件、候选及失败时成果不被静默删除。 |
| 故障与恢复 | 取消、版本冲突、损坏、未知版本和发布结果不确定分别报告；恢复先核实实际文件，不能仅凭 Session 推断完成。 |

## 六、下一步契约需要解决的技术细节

时间的具体表达、纪年参考标识和不确定区间如何校验；多上级关系的持有位置、环检测、层级深度和遍历限制；已关联 ID 与未建档线索如何表达；历史 JSON 版本、读取拒绝和已确认资料候选的实际存储，均属于下一步数据契约的设计工作。按已确认的业务方向及现有项目约定自行细化；若遇到会改变上述业务含义的具体例外，再向用户说明并讨论，不将一般字段选择逐项交给用户决定。
