# 角色资料与分类读取设计

本文描述角色资料和分类读取的业务设计；当前实现及限制以[角色资料模块说明](../../../src/world-init/README.md)为准。世界隔离、授权和用户确认遵循[共享工作区计划](world-initialization-stage-5-workspace-plan.md)及[初始化业务流程](world-initialization-stage-1-plan.md)。

## 整体工作制度

角色创建 Agent 负责角色规划、资料创建和局部修改。它围绕世界背景及近期故事主动发现人物需求、检索已有角色、规划缺口和人物关系，并维护角色资料；不替代故事规划或整体冲突修复。它可以独立工作，也可以通过专用工具接受委派。以下均为待实现的目标流程，具体运行入口由可信应用装配。

| 时机 | Agent 的处理 | 结果 |
| --- | --- | --- |
| 世界第一版规划 | 读取世界背景、重要局势与近期故事，梳理第一梯队及近期故事需要的其他角色；查找已有资料，主动设计关系与各自目标。 | 形成角色需求、创建建议和逐角色资料；不要求规划全部未来角色。 |
| 新的近期故事进入规划 | 读取该故事及相关世界资料，识别参与者和支撑世界运行所需人物；检索已有角色及关联。 | 每项需求标明由已有角色承担、需要新建、需要判断或暂缓。 |
| 世界、故事或用户要求变化 | 对受影响的角色需求和已有资料重新检查，明确缺少或过时的依据。 | 提出新增角色或调整角色资料的建议；角色之间和世界资料之间的整体修复由后续流程处理。 |
| 用户选择现有角色修改 | 定位所选角色及必要上下文，多轮讨论并更新该角色的待审候选。 | 保留原资料和待审修改；后续整体检查及确认完成后由受控流程提交。 |
| 已确认的候选需要提交 | 核对确认对象与资料基线，受控更新当前资料与索引。 | 记录实际结果；失败保留可恢复数据，不将部分更新当作成功。 |

系统在上述业务时机显式向 Agent 发起工作，不依赖常驻进程或假定后台监听已经存在。每次分析都记录实际依据及未检查范围；世界和故事资料缺失时报告缺口，不伪称已经规划完整。一次任务创建多名角色时逐项记录结果，未完成的需求保留待处理状态。角色生成、需求登记、写入草稿或工具执行成功都不等于用户确认世界事实。

## 资料组织与身份

可信应用提供当前世界的角色根目录，不由模型指定或授权。每个角色使用一个稳定的 UUID 标识，同世界内唯一；名称可重复或更改。目录名使用小写 UUID 标准形式，拒绝路径分隔符和其他不符合格式的标识。生成标识由可信程序负责，遇到已存在的目录应重新生成或报错，不能覆盖已有角色。不同世界由各自的根目录隔离。

```text
角色根目录/
├── index.json
├── requirements.md
└── <角色ID>/
    ├── profile.md
    ├── pending.md
    ├── pending.json
    └── backup.md
```

每个角色的当前资料为一个 `profile.md`；`pending.md` 保存候选，`pending.json` 保存候选所基于的当前资料摘要，`backup.md` 和 `operation.json` 在提交或恢复时使用。它们仅在修改流程需要时存在，不作为其他角色进入索引。普通角色可以尚未建档，但一旦建档，也使用独立 ID 和资料文件。

## 角色需求与创建时机

`requirements.md` 是角色创建 Agent 的需求清单，记录从已提供的世界背景、近期故事、用户要求和已有角色中识别出的角色需求；它与 `index.json` 中的已建档角色不同。清单用于持续定位需要补充的角色，不假设初始化时已经发现未来所有故事的角色。它不是世界事实或已确认档案，也不是共享工作区的资料目录。

每条需求应有稳定的需求 ID、来源引用或描述、所需角色的职责和背景、与近期故事的关系、建议重要程度、当前处理状态及已关联的角色 ID。未确定的内容明确留白，不提前生成角色 ID；需求和角色并非一对一，多个需求可能对应同一角色，一个需求也可能需要多人。状态至少区分待判断、需要创建、已有角色可满足、已创建和暂缓；记录判断依据，避免将未调查当成没有合适角色。需求是否准确和角色设定是否确认仍遵循用户确认流程。

需求状态由实际处理结果决定：新发现或依据失效时为待判断；找到可承担的已建档角色时关联 ID 并标为已有角色可满足；没有合适角色且当前需要时标为需要创建；创建资料成功后关联 ID 并标为已创建；当前不需要处理时标为暂缓。状态反映工作进度，不表达角色内容是否已确认。用户改变需求或来源资料变化时重新判断，原有角色不因需求变更而自动删除。需要多人的需求记录所需人数或范围以及已关联角色；只有满足该需求的数量时才能标记为已满足，未完成部分仍须可见。

近期故事开始规划、故事需求变化、用户明确提出角色需求时，Agent 读取获授权的世界与故事资料以及现有角色索引，更新相关需求，先检查已有角色是否能承担，再提出需要创建或补充资料的角色；资料不足时记录缺口并反馈。对第二、第三梯队，仅为近期故事需要的需求创建角色；后续故事出现时再分析补充。第一梯队按世界和重要故事的整体需要规划。触发流程由调用方显式执行，不假设已有后台监控或自动发现能力。

例如，近期故事要求调查宗门失踪案：清单记录“需要能接触宗门档案并有调查动机的人物”，并引用故事资料。Agent 查询已有角色后，如果现有长老可以承担，就关联其 ID；如果没有合适角色，则标记需要创建并说明理由。创建完成后关联新 ID；用户改变故事需求时重新评估，而不自动删除已建档角色。对尚未读取或未提供的故事资料，清单不能声称已覆盖全部角色需求。

清单采用 Markdown，开头 YAML front matter 的 `formatVersion: 1` 标明格式；每条需求作为单独的二级标题，包含由程序生成的 UUID、状态、来源引用、来源内容版本、需要的人数或范围、关联角色 ID 和判断说明。来源引用由可信资料入口提供，不要求模型生成宿主绝对路径；无法取得稳定版本时标记未核验，每次相关任务重新读取判断。清单是工作成果，不由解析标题推断世界事实。未知版本拒绝修改；并发编辑时基于读取版本检查，发生变化则拒绝覆盖并重新读取。来源更新、缺失或读取失败时，标记需要重新检查或明确报告，不能保留过时结论并宣称最新。是否实现自动提醒属于后续流程设计。

首版建议用 front matter 中的 `requirements` 数组保存机器可读数据，正文供人阅读；二级标题与正文只供展示，不是解析依据。每项包含 `id`、`status`、`description`、`sources`、`minCount`、`maxCount`、`characterIds` 和 `reason`。`sources` 的每项为 `ref` 与 `version`，无法核验版本时使用 `version: null`；人数范围未知时 `minCount` 与 `maxCount` 均为 `null`。状态使用 `undetermined`、`needed`、`existing`、`created`、`deferred`，分别对应待判断、需要创建、已有角色可满足、已创建和暂缓。需求未达到人数下限时不得标记为 `existing` 或 `created`；未确定人数的需求由 Agent 在判断说明中说明满足依据。ID 重复、必填字段无效或状态未知时拒绝读取并保留原文件。

## Markdown 资料格式

文件使用 UTF-8，开头为 YAML front matter，正文为可审阅的 Markdown；下例只是虚构数据，不要求所有角色具有相同正文栏目。

```markdown
---
formatVersion: 1
id: 2e59b48c-2c7c-4abc-b232-97dc06111001
name: 林岚
summary: 负责调查失踪事件的宗门长老
contentStatus: suggested
categories:
  importance:
    - id: tier-2
      name: 第二梯队
  faction:
    - id: sect-01
      name: 青云宗
---

# 林岚

调查弟子失踪事件；她对宗门的信任和疑虑并存。
```

`formatVersion`、`id`、`name`、`summary`、`contentStatus` 和 `categories` 必须存在；名称非空，`summary` 可为空字符串。`contentStatus` 在当前资料中为 `suggested` 或 `confirmed`，候选文件为 `pending`；`confirmed` 只能由可信业务确认流程设置，索引登记和 Agent 调用不能改变该状态。正文明确区分用户要求、Agent 补充及留白；状态描述整份资料的处理状态，不冒充逐项确认。分类的键是稳定的小写 ASCII 标识，每个值为 `{ id, name }` 项的数组；`id` 在该分类维度内标识类别，`name` 是供展示的名称。每个维度允许零个或多个值，不存在的维度表示尚无可查询分类，不能推断世界中不存在对应关系；同维度同 ID 不可重复。分类可随世界需求增加，`importance` 和 `faction` 只是示例；势力等引用的标识来自相应资料的可信身份，不凭名称虚构。关系正文中引用已建档角色时携带角色 ID 与可读名称；未建档的人物不冒充已有 ID。

元数据是机器读取的唯一来源，正文不强制字段清单。读取器须校验元数据类型、目录 ID 与内容 ID 的一致性以及重复字段；未知格式版本拒绝读取并保留原文件。将来调整格式时递增版本并提供明确迁移或拒绝策略，不静默改写已有资料。正文和用户要求、建议、待定内容的表达仍遵守世界初始化确认边界。

## 分类索引与查询

`index.json` 是根据当前 `profile.md` 构建的可重建目录，不是角色资料的第二份权威副本。示例：

```json
{
  "formatVersion": 1,
  "characters": [
    {
      "formatVersion": 1,
      "id": "2e59b48c-2c7c-4abc-b232-97dc06111001",
      "name": "林岚",
      "summary": "负责调查失踪事件的宗门长老",
      "contentStatus": "suggested",
      "categories": {
        "importance": [{ "id": "tier-2", "name": "第二梯队" }],
        "faction": [{ "id": "sect-01", "name": "青云宗" }]
      }
    }
  ]
}
```

索引条目与对应文件元数据一致；数组中 ID 唯一。初版按名称去除首尾空白后进行精确匹配，不将同名角色合并，也不隐式将别名、模糊匹配或大小写变换当成精确匹配。名称查询返回所有匹配角色的 ID、名称、简介和分类供区分；零条表示在完整索引中无匹配。同名时调用方选择候选，不自动指定角色。

查询结果同时提供 `contentStatus`；普通查询只读取 `profile.md`，需要候选时由有权调用方明确请求 `pending.md`。名称相同时返回所有候选，不依赖显示名称映射到单一 ID。索引缺失、损坏或检测到不一致时不能返回完整的零结果；文件系统中未建档的潜在角色不属于索引覆盖范围。

分类查询按维度和类别 ID 精确匹配；同一维度提供多个类别时匹配任一类别，不同维度的条件同时满足。类别显示名称可用于列出候选，但不作为跨资料唯一标识；同名类别需先选定 ID。比如查询 `faction=sect-01` 找到该势力已登记的角色；再加 `importance=tier-2` 则只返回同时符合两项的角色。查不到与分类尚未登记不能混同，也不能以此宣称世界里没有其他角色。

查询返回稳定顺序、匹配总数、分页信息和索引状态。批量读取先查询 ID，再逐个读取 `profile.md`；结果逐项包含 ID、成功内容或明确错误，并注明分页、数量限制或无法读取的项目。只有查询完整且全部文件读取成功时，才可称已读完该查询范围内的角色；索引缺失、损坏、版本不支持或发现索引与文件不一致时返回错误或明确不完整状态，不伪装成零结果。

## 创建、修改与索引一致性

角色 ID、角色文件及索引由角色资料服务管理，模型不自行生成 ID 或直接修改当前资料与索引。服务为应用提供可调用的创建、查找、读取和受控修改能力；面向 Agent 的专用工具调用相同服务，并按角色职责和工作区授权分别装配。服务不绑定具体模型或某个 Agent，工具不自行维护另一份索引。

创建角色工具接收本次角色内容及分类，不接收调用方指定的角色 ID；服务生成 UUID，并通过独占创建角色目录防止极低概率的 ID 碰撞及覆盖。碰撞时重新生成；其他文件错误直接报告。成功结果返回生成的 ID 和保存状态；多角色创建应逐项报告结果，不能将部分成功表述为全部成功。受可信应用控制的导入与迁移若将来需要保留已有 ID，另行设计，不作为普通创建工具参数。

角色读取工具先按名称或分类查询索引，再按 ID 读取一个或多个角色；同名候选及部分失败按上节处理。修改工具以已选角色 ID 和修改内容为输入，形成或更新待审候选；确认后的提交由拥有相应权限的业务流程调用服务，普通修改工具不能自行确认或覆盖当前资料。角色创建 Agent 与其他获得读取权限的 Agent 可装配不同工具集合，访问范围由可信应用限定。

创建时先由可信程序分配 ID，在授权范围写入新角色资料，再登记索引；新角色的设定状态仍需区分建议和已确认内容。禁止以同名覆盖已有角色。修改入口先定位现存角色，保存当前文件的内容版本作为基线，并在 `pending.md` 写入完整候选；多轮讨论更新候选，不改当前文件和索引。取消时保留当前资料；清理候选的时机由流程控制。

提交前核对候选、用户确认的内容及基线版本；当前资料已变化则停止并要求重新检查，不静默覆盖。将原资料保存为 `backup.md` 后再更新 `profile.md`，并更新索引；保留备份，直到资料与索引均更新成功并确认结果。不得声称跨多个文件的更新天然具备原子性；发生中断或写入失败时报告实际阶段并保留候选、备份及可恢复信息，恢复前不能将不一致索引当作完整结果。具体崩溃恢复标记、并发互斥范围和备份历史保留规则在实现前确定和验证。

提交前如已存在未处理的备份或恢复状态，停止提交并先处理，不能覆盖旧备份。确认结果与实际候选必须绑定，候选在确认后变化时须重新确认；具体确认凭据和恢复接口由业务流程定义。

首版恢复方案由可信服务在角色目录内创建带版本的操作记录，保存角色 ID、原文件和提交后内容的 SHA-256 摘要及阶段。写入候选时记录基线摘要；提交前校验业务确认与当前候选、原文件摘要一致，先写入备份，再更新当前资料并更新索引。阶段依次为 `prepared`、`backup-ready`、`profile-written`、`index-written`；每步成功后再推进，任何一步失败停止并保留记录与文件。索引更新完成后移除操作记录，再清理候选、候选基线和备份；清理失败仍须报告。每个单文件更新使用同目录临时文件及替换，不能由此声称跨文件原子或断电后目录项持久化。

恢复时以实际文件摘要核对操作记录，不单凭阶段推断上一步是否完成：原文件仍为基线时保留候选并等待重试；当前文件与已确认候选一致时重建索引后完成；备份与原始摘要一致而当前文件缺失时停止自动提交，提供受控恢复备份的操作。文件内容与任何已记录摘要不匹配、备份缺失、操作记录损坏或未知版本时停止写入并报告，保留现场，不覆盖用户数据。操作未完成时查询不得将索引标为完整，新的修改或提交不得覆盖现有操作和备份。明确单进程持有前提，并在实现时验证异常中断与恢复；确认凭据的生成仍由外层业务流程定义。

索引缺失或损坏时可从有效 `profile.md` 重建；重建过程校验每项，发现无效资料、重复 ID 或无法读取的目录时报告并拒绝把部分结果发布为完整索引。未知版本不得自动迁移或覆盖；重建不能修改或删除角色资料。写入和重建由可信应用的受控入口负责，不能让普通文件操作绕开确认和索引维护。

## 验证场景

- 两个同名角色返回两个带不同 ID 的候选；更名后旧名称不再命中当前索引，ID 和其他角色保持不变。
- 一个角色属于多个势力或类别；按一个势力批量查询，返回所有已登记匹配角色，再叠加梯队筛选。
- 没有登记分类的角色不会出现在该分类结果中；结果说明仅覆盖已登记数据。
- 待审修改更改名称或分类时，普通查询仍看到当前资料；确认后资料与索引一致，取消时原资料保留。
- 缺失文件、损坏索引、未知版本、重复 ID、部分读取失败和写入中断均明确报告；重建不覆盖原资料。
- 创建时由服务分配 ID，模拟目录已存在时不覆盖原角色；Agent 工具不能指定 ID 或直接提交待审修改。
