# 第 6A 阶段：跨模块整合与交付详细计划

本文细化[内容模块开发计划的跨模块整合与交付步骤](world-initialization-stage-6a-content-modules-plan.md#11-跨模块整合与交付)，目标是在已有模块和专用 Agent 的基础上，形成可验证、可恢复、供用户整体审阅的世界初始化第一版。本文是开发计划；建议的装配、测试与接口不代表已经实现。局部讨论、确认提交与世界演化的阶段边界见[世界初始化总开发计划](world-initialization-development-plan.md)。

双世界固定替身验证及真实模型样例的运行方式见[整合验证指南](../../cookbook/world-initialization-integration-validation.md)。真实模型完整交付样例尚未通过，已保存的测试成果和后续核查范围见[整合验证记录](../../../.agents/notes/2026-11-20-world-integration-validation.md)；不得把固定替身结果当作真实模型验收通过。

## 已确定的业务边界

1. 内容范围仍是用户确定的十个模块。宏观发展蓝图、故事线组织和人物成长蓝图由同一个世界发展规划 Agent 负责；世界专有内容由专用 Agent 根据构想和其他成果自主识别、补充。模块是职责划分，不要求每次生成十份文件、填满所有主题或逐一调用所有 Agent。
2. 主 Agent 负责理解世界构想、判断重点、决定是否委派、核对实际成果并整合；已划分的十个模块由各自专用 Agent 开发。主 Agent 仍主动补充十模块之外的必要内容，不以此擅自增加顶层模块。
3. 世界独立于单一主角和小说；一个世界可以服务多部小说。未来规划、人物成长方向和可能事件不是已经发生的世界事实，角色在故事中的认知、选择和实际变化不由初始化计划预先锁定。
4. 第一版是供用户整体审阅的方案。用户明确要求、已有资料、新增建议、未来方向、未知 / 留白及已发现冲突应能够辨认；生成、保存、资料目录登记、工具或子 Agent 成功返回均不代表用户确认。
5. 第一版中途失败或取消时保留已完成成果；用户可恢复同一会话输入“继续”，由主 Agent 结合历史和实际成果核查并补做。结果不确定时先读取核实，不能盲目重复创建；完整第一版形成后才进入相关修改讨论。
6. 完整第一版总览保存在主 Agent 草稿目录；重新生成时创建独立文件并保留旧总览，不自动覆盖。总览保存成功本身不证明其完整或已确认，必须核对实际正文及依赖成果。

## 当前实现与需要补足的整合

### 已有入口

[世界工作区入口](../../../src/app/agents/world-initialization.ts)按可信应用提供的世界配置装配主 Agent、可选目录和主 Agent 持久 Session；当前可分别配置角色创建、世界基础信息、地图、组织、历史、初始局势、世界发展规划、世界专有内容八类专用 Agent。专用委派工具只在相应配置存在时注册，具体入口、目录和 Session 约定见[应用说明](../../../src/app/README.md)。

各模块已有各自存储与工具，详见[地图](../../../src/agents/plugins/map/README.md)、[组织](../../../src/agents/plugins/organization/README.md)、[人物](../../../src/agents/plugins/character/README.md)、[历史](../../../src/agents/plugins/history/README.md)、[初始局势](../../../src/agents/plugins/initial-situation/README.md)、[世界发展规划](../../../src/agents/plugins/world-development/README.md)和[世界专有内容](../../../src/agents/plugins/world-specific/README.md)插件。世界基础信息成果按现有入口保存为待审 Markdown。第一版总览通过主 Agent 的 `save_first_world_plan` 创建独立 Markdown 文件；该工具不负责判断正文完整性。

[资料目录服务](../../../src/world-init/workspace/catalog/service.ts)能按世界与负责人登记成果及检查正文变化，目录简介是导航，不是正文或用户确认。`mainSession` 可恢复主 Agent 对话；各专用 Agent 有自己的 Session。现有[目录对齐测试](../../../src/app/tests/catalog-alignment-e2e.test.ts)与[工作区生命周期测试](../../../src/app/tests/world-workspace-lifecycle.test.ts)覆盖部分目录协作、身份及恢复路径；各模块也有独立端到端与真实模型样例。这些测试不能代替所有已开发模块共同参与的第一版整合验证。

### 需要重点验证和解决的缺口

| 问题 | 当前事实 | 本步骤需要完成的工作 |
| --- | --- | --- |

| 跨模块结构化引用 | 世界入口通过共享存储所有者向配置的 Agent 绑定引用；独立入口仍可由可信应用显式提供引用。 | 核对读写依赖及失败清理，验证同世界、负责人和访问模式；检查读取失败不能伪装为不存在。不能由模型决定身份或路径。 |

| 第一版何时完整 | `save_first_world_plan` 保存调用方提供的正文，不检查是否覆盖实际任务或缺失成果。 | 结合真实案例定义主 Agent 交付前应核对的内容、依据和未完成范围；区分程序可机械判断的条件与依赖模型判断的内容，不仅依赖提示词或固定模块清单。 |

| 大任务与步数限制 | Agent Loop 默认 `maxSteps` 为 10；已有真实模块样例出现达到上限后在同一 Session 继续的情况。 | 针对真实调用链核对主子 Agent 的可配置性、任务规模、失败传播和恢复。若确需调整，沿现有配置与生命周期扩展，不以无限重试或丢弃上下文掩盖失败。 |

上述缺口需在第一步结合真实代码、测试和两个世界场景重新核实；实现时优先复用现有能力。不要为整合提前建立通用对象数据库、全自动冲突修复、独立任务进度平台或完整世界运行引擎。

### 第一步核对：实际装配与依赖

主 Agent 的世界入口绑定世界、主身份、可选目录及各专用 Agent 配置；八类专用 Agent 的身份必须属于同一世界且互不相同。专用 Agent 按委派创建并管理各自 Session；世界入口使用共享存储所有者管理业务存储，独立 Agent 入口自行管理存储。世界基础资料和主总览分别写入各自授权目录。目录绑定负责登记和发现成果，不提供这些存储句柄。

| 引用方 | 可由可信调用方提供的目标存储 | 当前约束 |
| --- | --- | --- |
| 人物 | 地图、组织 | 装配只读地图及组织工具；可信配置检查世界和负责人目录。 |
| 组织 | 地图、人物 | 地点与人物核验复用借用句柄；检查世界或负责人目录。 |
| 历史 | 地图、人物、组织 | 沿用组织的地点 / 人物核验，并核验组织世界及目录。 |
| 初始局势 | 地图、人物、人物关系、组织、历史 | 对存在的目标读取版本，缺失目标与未提供引用能力分别处理。 |
| 世界发展规划 | 初始局势可引用的各目标、局势 | 分别核验局势总览与条目所属关系；规划不自动选定待审局势。 |
| 世界专有内容 | 发展规划可引用的各目标、世界发展规划 | 可引用发展规划资料；借用句柄由调用方保持有效。 |

上述依赖来自世界存储目录内的 `*-references.ts` 类型；它们通过只读查询能力消费句柄，不转移关闭责任。世界入口按可信配置绑定共享引用，外部引用与同一目标的自动共享不能同时配置。主 Agent 的固定替身测试与各单模块测试不能证明八类 Agent 同时协作、所有生命周期路径或真实模型规划质量。

两个场景均从隔离的空测试世界和明确的用户构想开始，不假设测试前已有业务数据。修仙场景按任务建立青云山、宗门、人物、历史、局势和必要的修炼规则；远方地图与无关主题保持留白。城邦场景按任务建立河流、城邦、人物与旧战争，并分别建立封渠和通水的候选局势及其适用方向；无需补充的水利细节可以留白。测试夹具必须使用实际创建返回的 ID 建立引用，不能把示例名称当成 ID 或强制两个世界使用相同委派顺序。

第一步后续验收重点：复现共享句柄与目标 Agent 同时装配是否冲突及关闭顺序；验证代表性跨模块引用和未配置、缺失、越界的区分；读取实际正文核对候选局势、未来方向和留白；在部分成果已保存后恢复同一 Session，确认不重复创建。真实模型验证应另行记录，不能由固定模型替身代替。

## 两个端到端场景

### 开放式修仙世界

用户要求开放世界、力量本身无善恶、角色各有目标，远方区域暂留白。可用资料包括基础背景、重点地图、宗门和人物、灵脉变化历史及候选初始局势；世界专有 Agent 可根据这些资料按需完善修炼和灵脉规则，世界发展规划 Agent 可围绕资源压力提出未来方向和故事线。

整合时主 Agent 读取实际成果及必要正文，说明青云山的地点归地图、宗门和成员归组织、人物认知归人物、过去迁徙归历史、起点争议归局势、未来可能发展归规划、修炼规则归专有内容。不同模块通过可核查引用关联；远方留白不能被“补完整世界”的要求覆盖。最终总览应让用户定位依据和未覆盖内容，但不要求所有模块同样详细。

### 资源有限的城邦群

用户希望多座城邦围绕有限水源各自追求利益。可用资料包含河流地图、城邦组织和成员、人物、旧战争、两个待审起始局势（A 封渠、B 暂时通水）及各自可能的发展方向；若水利技术细节对当前构想有必要，可委派世界专有 Agent 补充，否则记录未使用或未展开的实际情况。

总览应分别展示 A、B 与其适用的发展规划，不把 A 的条件当成 B 的事实，也不自动选定方案。故事线可引用共同的未来谈判构想；人物成长蓝图引用各人物唯一成长线，不重复维护个人阶段。尚未建立的地点、人物或规则以线索 / 未定表达，不编造 ID。

### 贯穿失败与恢复

在任一场景中，某子 Agent 已保存部分主题或人物后出现失败，或目录登记、总览保存返回结果不确定。主 Agent 应区分实际已完成、失败、待核查及未覆盖内容；保留其他已完成成果。用户恢复同一会话输入“继续”后，主 Agent 先读取实际文件、目录和已有版本，再决定补做或报告阻塞；不能只根据历史工具回复推断完成，也不能重复创建同名成果。

如果某专用 Agent 未配置或资料读取无权，报告具体模块与范围，不将其自动替换为“无相关资料”。若用户构想本身不需要某专有主题，可以说明该范围未使用或无需展开；这与任务失败或模块尚未配置应可区分。

## 可信装配与资料流

跨模块存储共享的代码布局、生命周期和分步修复见[共享存储修复计划](world-initialization-stage-6a-shared-storage-fix-plan.md)。

建议在可信应用层建立明确的世界初始化装配过程，依据世界配置提供主 Agent、各专用 Agent、共享只读能力、目录绑定和独立 Session。以下是职责方向，不预设必须新增某个类、通用存储服务或独立调度器：

```text
用户构想 / 已有世界资料
        ↓
可信应用绑定世界、身份、读写目录、Session、模型与引用能力
        ↓
主 Agent 按需要读取、协调、委派专用 Agent
        ↓
专用 Agent 维护所属成果；跨模块读取由已授权能力完成
        ↓
主 Agent 读取实际正文、核对结果与未覆盖范围
        ↓
主 Agent 草稿目录中的独立待审第一版总览
```

各负责人只在自己的可信写入范围内维护权威正文；引用使用实际对象类型与 ID 或授权文档线索，不复制其他模块完整资料。目录用于发现已登记成果，读取时仍核对正文及状态；未登记不等于不存在。跨模块结构化工具未绑定时，应明确报告未配置或使用现有授权原文 / 待关联线索，不能伪造 ID、吞掉权限错误或声称引用已核验。

在实现句柄协作前，逐项列出：谁打开目标存储、何时被借用、借用方是只读还是写入、谁拥有关闭责任、Agent 运行取消或失败时谁等待未完成操作、哪个身份或目录仍被占用。调用方提供的句柄必须验证世界和负责人；子 Agent 的模型输入不能选择新的授权范围。若一个专用 Agent 自行打开写存储，同时其他 Agent 需要读取同一世界，应先实测现有占用规则，再设计同一可信所有者下的借用或清晰的顺序装配；不把“已配置 references”当作句柄始终有效的保证。

所有实体和跨模块读取都处于单可信写入进程假设下。路径检查、身份占用和目录能力不能抵御所有恶意并发替换或硬链接，不构成跨进程锁、系统级隔离或跨文件原子事务；共享只读能力也不能自动作为故事角色的知识权限视图。初始化期间角色认知来自角色自身资料，不因为规划者读取了完整资料就自动扩散给角色。

## 待审第一版的交付内容

主 Agent 根据具体世界及已完成成果组织总览，而不是套用必须填满的字段。至少应能让用户理解：

- 用户的关键构想和约束、世界最值得关注的特点及实际规划重点。
- 所用资料和已形成的专用成果，提供可核查的目录线索或实际路径；不只摘录目录简介，也不维护第二份需要同步的完整权威正文。
- 已发生的历史、初始时点的实际候选局势与未来可能方向分别表述；同一世界的多个待审局势及其适用规划不互相混用。
- 人物、组织、地点和专有规则之间已核验的引用、待核查线索、明确未知或用户留白；角色成长规划与实际选择分开。
- 已发现冲突、资料不可用或变化、未检查范围、失败或结果不确定的工作。没有发现冲突只表示在所读范围内未发现，不表示世界不存在冲突。

这里的“已形成”表示文件或资料确实存在，不代表用户已经确认。内容生成来源的表现形式应能支持用户辨认要求、已有资料和 Agent 补充，但不预设所有模块增加统一来源枚举。若某部分尚未完成，总览不得标成完整第一版；先保留部分成果并报告原因，恢复和补做后再形成完整总览。是否增加程序可验证的交付检查应以实际场景为依据，检查只能证明其覆盖的条件，不能证明模型理解正确或全部世界资料一致。

## Session、失败与“继续”

可信应用使用稳定世界、主 Agent 身份、Session ID 和 Session 根恢复同一个主会话；专用 Agent 的身份与 Session 也必须由应用稳定绑定。Session 记录对话，不是长期记忆、世界事实或业务完成证明；旧实例的临时目录凭据在释放后不能继续使用。

| 情况 | 预期处理与验收 |
| --- | --- |
| 子 Agent 中途失败，部分文件已保存 | 显示实际错误和可核查成果，其他已完成资料保留；不把部分回复或目录登记当成整个模块完成。 |
| 文件写入或目录登记结果不确定 | 按返回路径、实际文件、版本和目录分别核查；没有证据时报告不确定，不自动再次创建。 |
| 取消、步数上限或模型超时 | 取消后等待资源释放并保留已发布成果；恢复时在同一会话核对成果及未完成范围，不因为步数上限静默结束为成功。 |
| 主子会话恢复后输入“继续” | 主 Agent 基于会话及实际文件决定要查询、委派或补做什么；专用 Agent 以实际已有资料避免重复创建，失败继续报告。固定替身只能验证路径，真实模型的自主排查需单独观察。 |
| 目录过期、文件缺失或来源变化 | 读取实际正文及可用版本，区分变化、缺失、无权、未配置和失败；不能根据过期简介或历史回复覆盖原资料。 |
| 同身份重复启动、清理失败 | 拒绝不安全的重复占用；清理失败如实报告，确认实际资源状态后再恢复，不绕过占用或把系统当作已释放。 |

完整总览重新生成时使用新文件；旧总览和各模块已发布文件保留。新增文件或用户数据格式变化前须明确格式版本和迁移 / 拒绝读取策略。当前没有完整第一版状态机或长期记忆恢复，是否需要更小的程序状态、结果引用或校验应先根据第一步发现的真实缺口论证，不由本计划预设。

## 验证矩阵

| 维度 | 需要覆盖的可观察结果 |
| --- | --- |
| 两个世界及规划重点 | 修仙、城邦各有独立世界与身份；验证重点不同、按需委派、必要内容和留白，不要求固定模块调用顺序。 |
| 十个模块与八类专用 Agent | 在联合覆盖中实际验证每个已开发模块如何被定位与整合；同一世界发展 Agent 的三个模块分别核查。某个测试不必为每个世界强制调用全部 Agent。 |
| 跨模块引用 | 用真实存储建立并读取地点、组织、人物、历史、局势、规划和专有内容之间的代表性引用；检查世界、负责人、原文、版本和只读 / 写入边界。 |
| 共享句柄与生命周期 | 验证目标存储由专用 Agent 写入、其他 Agent 读取时的真实占用与借用；覆盖重复启动、同时任务、取消、关闭顺序及重建。 |
| 多个待审局势 | 城邦 A / B 及各自发展方向保持分离；没有实现用户选用流程时保持待审，不自动选择或合并。 |
| 失败与恢复 | 部分写入后子任务失败、目录或文件结果不确定、来源变化、步数上限和用户“继续”；检查保留成果、核查动作、不重复创建及最终总览。 |
| 用户可审阅输出 | 读取实际第一版总览并核查主要依据、留白、冲突和未覆盖范围；多次完整生成保留旧总览，不以工具返回成功代替文件检查。 |
| 权限与坏数据 | 不同世界隔离、跨负责人写入拒绝、未配置 / 无权 / 缺失、损坏和未知版本；不能把错误伪装成空结果。 |
| 真实模型与固定替身 | 固定替身验证预设路径和状态；单独运行有记录的真实模型样例，观察任务选择、内容质量、留白及恢复；真实调用可能失败或达到上限，不能用替身结果代替。 |

## 分步实施计划

1. **现状核对与联合场景。** 阅读主 / 子 Agent、工作区、目录、各模块存储、引用绑定和现有测试；绘制实际的模块、身份、存储所有者与引用依赖。用修仙和城邦场景确定哪些数据已存在、哪些需新建、哪些可以留白或不委派；列出不可运行的整合路径与明确验收，不把尚未决定的接口当成现状。
2. **可信装配与跨模块读取。** 在真实工作区复现多模块句柄借用、进程内占用和 Agent 生命周期；按需设计并实现最小可信共享 / 按序读取机制，核验同世界、负责人、只读与写入权限以及取消 / 关闭责任。保留未配置和错误的独立反馈；验证相关专用 Agent 能按需同时装配、读取和保存，不能为了测试绕过单进程约束。
3. **第一版整合与可审阅交付。** 结合用户构想、实际授权资料和专用成果完善主 Agent 的任务、资料读取、引用核对和总览提示；只在确有必要时增加最小程序校验。实现 / 验证完整与未完成范围、历史 / 当前 / 未来区分、多局势候选、来源变化和留白；总览按已确定规则独立保存，不改写专用 Agent 的正文或已确认目录。
4. **失败恢复与会话继续。** 在现有 Session 和文件机制上覆盖子任务部分成功后失败、调用取消、身份占用、目录变化、写入结果不确定与恢复同一会话。用户输入“继续”后由主 Agent 查询实际成果并决定补做；按真实需要处理 `maxSteps` 等配置与反馈，验证不会静默截断、盲目重试或重复创建。只有完成并核查第一版后才交付整体审阅。
5. **双世界端到端与真实模型验证。** 用真实主子 Agent、目录、Session、文件和固定模型替身走查上述两个世界，联合覆盖十模块与八类专用 Agent 的实际装配及代表性关联；覆盖不委派、部分未配置和失败恢复。单独使用可用的真实模型配置在隔离测试世界验证实际任务选择、跨模块读取、总览及恢复；若失败则保留成果、核对后按需恢复，报告模型、工具和平台的实际结果，不把样例表现扩展为质量保证。
6. **文档与阶段交付。** 更新应用入口、模块说明、架构及必要 Agent Note；运行与实际变更相符的聚焦测试、类型检查、正式构建、相关文档链接和 Git 空白检查。整理哪些能力已验证、真实模型 / Windows 与其他平台覆盖、已知错误和未完成项；完成本阶段后等待用户指示，不自动进入第 7 阶段或世界运行。

每完成一个步骤，先核对该步实际成果及对应验证，再按用户的开发节奏单独提交；若发现业务边界仍有实质歧义，先以具体例子和建议与用户商议，能依据现有决定解决的工程细节自行完成。

## 与后续阶段的交接

第 6A 阶段交付的是**供整体审阅的第一版建议及其实际来源**，不是整个世界初始化流程已经完成。以下能力按后续阶段设计和验证：

- **第 7 阶段：局部讨论与待审修改。** 用户选择某个地区、角色或其他内容进行多轮讨论；待审修改与当前方案区分，未经确认不提交。当前各模块的候选文件不等于已有统一的局部讨论流程。
- **第 8 阶段：影响检查、用户选择与受控提交。** 跨内容影响展示、选择与确认绑定实际版本，以及变化后的重新检查；不把当前有限的一致性检查称作全自动语义修复。
- **第 9 阶段：完整持久化、恢复与最终交付。** 用户完成初始化的业务状态、迁移和完整流程验收；Session 持久化与现有模块文件不足以单独证明这些能力已经完成。
- **世界运行与故事创作。** 世界时间推进、导演安排、角色自主行动、实际事件和演化历史留存另行设计；初始化蓝图不会自动生成这些实际行为。

**本阶段验收：** 可信应用能在不同世界按需装配并协调实际已完成模块，用户能整体审阅有实际依据、未冒充确认的第一版；失败保留成果并能在同一会话核查和继续，验证范围与未实现内容如实可见。
