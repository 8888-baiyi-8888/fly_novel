# 第 7 阶段：局部讨论与待审修改开发计划

本文细化[世界初始化总开发计划](world-initialization-development-plan.md#7-局部讨论与待审修改)的第 7 阶段。目标是在完整第一版供用户整体审阅后，让用户选择世界中的内容，与主 Agent 多轮讨论并形成可审阅的局部修改。本文是开发计划；计划中的目录、接口、状态和工具名称均不是现有实现或已经确认的最终契约。

## 阶段目标和边界

1. 用户可以通过名称、描述或已有成果线索选择地点、人物、组织、关系、历史、局势、世界发展规划、世界基础信息及世界专有内容等；同名或目标不明确时，展示候选并请用户选择，不猜测 ID。
2. 对同一个对象进行多轮讨论，可暂不形成修改；也可切换到其他对象，之后返回原对象继续。当前方案、对话和候选修改分别保存和读取，切换不自动提交或丢失已有候选。
3. 已建立的内容模块由对应专用 Agent 按需参与；主 Agent 负责理解用户意图、组织讨论、按需委派和呈现结果，并可补充十个模块之外的必要内容。独立专用 Agent 的现有用途不因此消失。
4. 讨论形成的建议进入待审工作区；无论当前方案本身是否已经过用户确认，待审修改均不直接覆盖它。用户、Agent、工具或目录对候选的保存成功不等于确认或提交。
5. 影响检查、用户选择和受控提交属于第 8 阶段；最终完成初始化及完整恢复属于第 9 阶段。本阶段只提供必要的候选、基线、版本和可审阅信息，不提供绕过检查的确认写入入口。
6. 第一版仍未完成时沿第 6A 阶段规则保留成果并继续补做；进入局部讨论需要完整第一版。现有总览文件成功保存并不能单独证明完整，可信应用需要明确如何接收完成判断，不凭文件存在、目录登记或 Session 自动切换阶段。

## 现有能力与缺口

| 能力 | 实际情况及本阶段需要处理的问题 |
| --- | --- |
| 世界入口与会话 | [世界初始化入口](../../../src/app/agents/world-initialization.ts)按可信配置装配主 Agent、各专用 Agent、共享存储、可选目录服务和持久化 Session。Session 保存对话，不能代替当前方案、候选或用户确认状态。 |
| 资料目录与总览 | [资料目录设计](../../modules/world-information-access.md)及[第 6A 整合计划](world-initialization-stage-6a-integration-delivery-plan.md)约定目录是查找线索，正文需实际读取；总览是独立 Markdown，不自动成为所有模块的权威副本。 |
| 人物资料 | [人物插件](../../../src/agents/plugins/character/README.md)已有 `character_prepare`、`character_pending_read`、基线摘要及可信应用提交能力；已有候选按角色独占，重复准备可以更新同一候选。角色初始化工具和人物关系工具还提供直接写入能力，需要按讨论阶段限制。既有提交会将角色标为 confirmed，不能直接当成跨模块的第 8 阶段确认流程。 |
| 地图与组织 | [地图](../../../src/agents/plugins/map/README.md)和[组织](../../../src/agents/plugins/organization/README.md)的初始化工具可以创建或按版本直接更新部分资料；地图地点、连通和组织、成员关系的接口并不完全相同。讨论时不能直接装配能改写当前成果的这些工具。 |
| 历史、局势、规划和专有内容 | 对应[历史](../../../src/agents/plugins/history/README.md)、[初始局势](../../../src/agents/plugins/initial-situation/README.md)、[世界发展规划](../../../src/agents/plugins/world-development/README.md)和[世界专有内容](../../../src/agents/plugins/world-specific/README.md)插件提供各自的初始化存储和候选能力；其候选范围、状态限制及更新语义需要逐项核实，不能假定已有统一候选工作区。 |
| 世界基础信息与主 Agent 补充 | 世界基础信息及第一版总览使用文件成果；主 Agent 的草稿目录有写能力。需要识别具体资料及版本，确保讨论候选与原文分离，也不能让普通文件写工具绕开这一边界。 |
| 跨模块存储 | [共享存储设计](world-initialization-stage-6a-shared-storage-fix-plan.md)使用可信所有者与借用句柄；单可信写入进程不意味着跨文件事务、原子快照或操作系统级隔离。讨论模式应继承相同的生命周期和信任边界。 |

## 示例与预期交互

### 地点：多轮讨论并切换

第一版已有曲水城和青河地区。用户选择曲水城，要求讨论城门夜间关闭规则。系统读取实际地点资料及其版本，说明现有内容；专用 Agent 根据用户要求提出候选。用户再要求给商队留出例外，系统更新同一讨论中的候选并展示变化。当前曲水城资料保持原样。

用户转去讨论青云宗，系统保留曲水城候选；之后用户返回曲水城，能够分别看到当前资料、候选及其基于的版本。如果当前资料在讨论期间发生变化，系统标记基线过期并要求重新读取、调整候选；不能静默覆盖当前资料或声称候选仍基于最新版本。

### 人物与关系：候选不能混为当前事实

用户选择林岚，讨论将其宗门职务改为外务负责人。人物 Agent 读取角色当前资料，必要时读取组织的成员关系；角色资料和组织成员关系分别归各自模块维护。若讨论同时涉及两处，候选应分别指出涉及的资料和变化，不能只改角色正文就声称成员关系已变更，也不能直接改写组织成员记录。第 7 阶段不实际提交这组变化，第 8 阶段再设计关联检查和提交。

### 未完成与失败

用户只询问“如果城门夜间关闭，会有什么好处”，Agent 可以回答并给出建议，不必创建候选。用户要求修改后，若子 Agent 失败、取消或保存结果不确定，展示已知结果与需核查事项；不把对话中的建议当作已保存候选，不盲目重复创建，现有资料和已保存候选保持可核查。

## 业务对象与状态设计建议

以下是第 7 阶段最小概念，字段和枚举待第一步结合已有格式确定：

| 对象 | 建议职责 |
| --- | --- |
| 讨论 | 可信应用绑定世界、讨论 ID、用户选择的目标或范围和会话线索；保存当前进度与候选引用。讨论不等同于对话 Session，也不证明修改已形成。 |
| 目标 | 使用所属模块、实体类型和真实 ID，或受控文件成果的可信标识定位；名称只用于展示。一个讨论可以提出多个关联资料的候选，但每个候选必须标明自己的真实目标和归属。尚不存在的内容应明确表示为新增意图，不能捏造已有 ID。 |
| 当前方案 | 由各模块既有权威文件维护；读取正文与版本，记录实际读取范围。第一版建议属于当前待用户整体审阅的方案，并不因为称为“当前”就变成已确认世界事实。 |
| 候选 | 独立保存建议内容、目标、创建或更新所依据的基线版本、候选版本、简要说明及必要的新增 / 修改 / 删除意图。正文仍遵循所属模块格式及验证，存放位置、具体载荷按第一步核实后的适配方案确定。删除仅表达待审意图，不删除当前文件。 |
| 展示 | 返回可读的当前内容、候选和变化说明，并标记未保存、已保存、基线过期、失败或结果不确定；允许查看完整候选，不能只依赖模型摘要或目录简介。对尚不支持的目标明确报告，不能退化成直接写入。 |

建议最初支持一个讨论对每个目标维护一份可继续编辑的候选；不同讨论如同时修改同一目标，必须在创建时明确处理冲突，不能互相覆盖。既有模块的独占候选限制是否足以支撑讨论之间切换，应通过第一步样例确认；不擅自承诺多分支、自动合并或候选历史。

建议取消分为两种明确动作：停止本轮生成时保留此前已保存的候选；用户明确放弃候选时将其标记为放弃或通过受控操作清理，具体留存方式先以样例核对。讨论切换、请求失败或进程退出均不隐式当作用户放弃。取消与候选保存并发时以实际发布结果为准，结果不确定需核查。

## 写入隔离与可信装配

讨论阶段需要程序控制的写入边界，不能仅依赖 SystemPrompt：

1. 可信应用决定世界、阶段、目标、实际存储及 Agent 身份；模型不能通过参数选择其他世界、负责人、路径、阶段或写入权限。
2. 第一版生成模式保持既有按需创建能力；讨论模式只装配读取当前资料、读取和准备候选所需能力。讨论模式下不得暴露当前资料的创建、覆盖、删除或提交能力，包括角色初始化更新、组织 / 关系更新、其他模块的直接写工具及可绕开的通用文件写工具。对间接委派、共享句柄和恢复会话同样适用。
3. 优先复用各模块现有读取、候选、版本和格式验证；针对不具备所需能力的对象，由所属插件增加明确的候选适配，业务格式与校验仍归原模块。跨模块讨论和候选索引可置于 `src/world-init/` 下独立目录，Agent 插件与委派工具保留在现有所属位置；具体文件随第一步盘点确定，不为计划预建空目录或另建通用存储框架。
4. 现有角色候选是按角色独占的 `pending.md` / `pending.json`，不可把它无条件复制到多个讨论；要先核对已有候选、基线变化、取消及失败恢复语义，明确如何关联讨论。不得为了统一格式丢弃或覆盖已有候选。
5. 创建候选前读取当前目标及版本；后续写入候选使用候选自身版本防止覆盖其他讨论更新。目标不存在、不可读、版本未知或发生变化时分别报告，不能把读取失败当成空内容。涉及多个目标时逐项记录基线和实际结果，不声称获得全局原子快照。
6. 新增资料先在隔离候选中描述或保存，正式 ID 的生成、候选内引用及提交后引用的转换必须在相应模块的实施设计中明确；不可把候选 ID 伪装成已存在的正式对象。跨目标引用尚未实现时明确限制，不直接创建正式记录。
7. 对普通文件和世界基础信息，可信应用基于已授权成果标识解析路径，检查归属并读取实际正文；不能由模型任意指定写入路径。第一版总览候选与原总览分离，目录登记不代表确认。
8. 只读或候选能力覆盖到应用装配、子 Agent 工具和底层存储访问；单元测试需实际尝试绕过路径。信任单个写入进程的既有限制继续适用，不宣称跨进程锁或文件系统级隔离。

## 存储、版本与恢复

计划采用世界级隔离的讨论记录和候选成果；讨论标识由程序生成，正文可以是模块原有 JSON / Markdown 或由模块支持的候选格式，不强制把所有资料转换成同一种业务正文。讨论记录只保存定位、状态和必要版本，不复制另一份需要持续同步的当前方案。候选文件属于待审工作区，不应通过普通世界资料查询冒充当前事实。

落地前需确定存储根、每种目标到候选的映射和可信所有者，限制目录穿越、同世界身份误用、损坏和超限输入。新记录格式带明确版本；未知版本拒绝读取并保留原文件。已有数据及已有候选不静默迁移或删除；需要改变既有格式时先制定迁移或拒绝读取方案并验证。目录与候选的部分写入或结果不确定应可核查，不能假定多文件原子提交。

本阶段需验证已保存讨论和候选在受控重启后可以被再次读取；Session 恢复负责对话历史，业务记录负责候选与目标的关联。完整初始化状态、最终交付以及第 8 阶段确认与提交的持久化策略留给后续阶段，不把这里的最小恢复声称为第 9 阶段完成。

## 分步开发与验收

1. **盘点现状和确定样例。** 核对全部专用 Agent 的创建 / 更新 / 候选工具、角色既有候选和确认实现、普通文件工具授权、共享存储与 Session；对地点、人物和成员关系做端到端走查，列出目标类型、版本来源及具体可用 / 缺失能力。确定第一版完成判断的可信交接方式以及讨论范围；遇到影响近期行为的业务歧义，使用具体例子和推荐方案与用户讨论。
2. **确定讨论和候选契约。** 明确目标标识、讨论 / 候选状态、基线与候选版本、切换、放弃、过期和多目标结果；规定目录布局、格式版本、旧数据及已有角色候选的处理。选择能代表既有差异的地点与人物纵向样例，先验证契约，不假定所有模块可直接复用同一实现。
3. **建立可信讨论装配与隔离。** 在世界入口增加受控的讨论模式，绑定世界、身份和生命周期；限制直接写工具、文件工具和委派子 Agent 的写入权限。测试普通入口、共享句柄、恢复、取消和失败清理，确认无法通过模型工具直接覆盖当前资料，同时不破坏第一版生成与独立 Agent。
4. **实现讨论记录和首批候选。** 实现可信讨论记录及地点、人物候选所需最小适配，复用人物既有能力或明确安全改造；支持读取当前版本、准备与更新候选、展示完整内容和过期状态。覆盖同名目标、独占候选、候选并发更新、目标变化、损坏、未知版本与不确定发布。
5. **接入其余已开发资料。** 按目标类型逐一核对并接入组织 / 成员、人物关系、历史、局势、世界发展规划、世界专有内容、世界基础信息及主 Agent 补充；对新增、删除、跨对象关联分别验证，确实不能支持时显式报告限制。每个模块仍拥有自身数据与校验，不能以直接更新冒充候选。
6. **多轮讨论、切换与失败恢复。** 主 Agent 结合真实读取和专用 Agent 结果组织讨论；验证无修改的问答、连续修改、跨对象切换、回到先前讨论、明确放弃、取消、子 Agent 失败和重启读取。保留已完成候选，结果不确定时核查，不自动提交。
7. **集成验证与交接。** 用真实工作区及固定模型替身覆盖地点、人物和跨模块候选，验证世界隔离与写入边界；另在隔离世界进行有记录的真实模型多轮样例，报告实际调用范围和结果。运行适当的聚焦测试、类型检查、构建、文档链接和 Git 空白检查；记录未支持事项，将候选、基线和已知限制交给第 8 阶段，不提前实现确认提交。

每一步完成并验证后按项目既有提交格式单独提交；遇到需改变计划的业务问题先说明并讨论。真实模型结果只证明所运行样例的表现，固定替身只证明受测路径和状态。

## 与第 8、9 阶段的接口

第 8 阶段应能读取用户审阅的候选及其版本、每个目标的基线、实际变更和已知未覆盖范围，另行设计影响检查、用户选择及受控提交；本阶段不承诺跨模块原子提交，也不把人物插件已有单对象 `commit` 当成完整解决方案。第 9 阶段基于实际验证过的业务状态设计完整恢复、完成初始化和演化交接。

## 需在第一步结合示例确认的事项

- 多个讨论同时涉及同一资料时，是拒绝新候选还是允许彼此独立；建议先保留独占候选并明确提示，确认不会覆盖用户已有修改后再决定是否扩展。
- 用户明确放弃候选时是保留可找回记录还是直接清理；建议先保留并标记放弃，避免误删。取消本轮生成与放弃候选应区分。
- 一次讨论产生多个模块的候选时，用户如何逐项审阅和选择；建议第 7 阶段允许逐项查看并保留所属关系，整体或部分提交规则留待第 8 阶段讨论。
- 对第一版完整性的判断如何由可信应用接收，及不完整时界面如何提示；不能将模型回复、总览文件或目录记录单独作为完成证明。
