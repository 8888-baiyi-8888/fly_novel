# 第 6A 阶段：初始局势详细开发计划

本文细化[内容模块逐项开发计划的初始局势步骤](world-initialization-stage-6a-content-modules-plan.md#6-初始局势)。它是开发方案，不表示局势插件、局势 Agent、所列工具或数据格式已经实现；除明确标注用户确认的业务方向外，具体字段、工具名称和实现方式在契约步骤结合现有代码确定。

## 目标与范围

初始局势描述世界开始演化时已经存在的整体处境，以及该时点正在持续的矛盾、危机和活动。重点由用户构想和近期需要决定，既可以覆盖一个地区，也可以连接多个地区；不要求每个世界都存在战争、危机或同样数量的局势。世界服务多部小说，局势属于世界，不以某个主角或单部小说为唯一中心。

| 内容 | 负责范围 |
| --- | --- |
| 起始时点以前已发生的战争、迁徙或停水 | 历史设定维护经过、已知影响和不确定信息；局势按需引用历史，不复制完整事件。 |
| 起始时仍然存在的缺水、利益冲突及正在进行的谈判 | 初始局势维护跨地点、组织和人物的整体处境与相互影响；持续活动只描述起始时已知状态。 |
| 两个组织之间的敌对、人物成员身份 | 分别由组织关系、成员关系维护；局势引用相关关系并描述其与整体处境的联系，不另建一份权威关系。 |
| 某个人的经历、想法、目标与认知 | 人物资料维护；局势可以引用人物及与局势有关的必要背景，不假定人物知道完整局势。 |
| 地点范围、通路及组织自身资料 | 地图和组织维护；局势通过可靠引用描述涉及范围，不替代原文。 |
| 未来可能爆发战争或达成协议 | 属于后续发展规划或故事线；局势可以说明尚未解决的问题，但不将推测写为已经发生的事实。 |

已保存的局势只是供用户审阅的第一版建议。保存、目录登记、子 Agent 返回、其他资料已有内容均不自动代表用户已确认；已有资料的待审或确认状态不能因引用而改变。起始时点之前尚在持续的战争，其已发生经过可由历史维护，起始时的持续处境归局势；后续过程和结果不能预先写成已发生。

## 已有能力与复用

- [世界工作区](../../../src/world-init/README.md)提供世界、负责人、目录和身份约束；[资料目录](../../modules/world-information-access.md)用于发现成果和读取授权正文，目录简介不是局势正文或事实确认。
- [历史插件](../../../src/agents/plugins/history/README.md)提供事件 JSON、事件层级、时间及查询，历史 Agent 支持可信绑定的地图、组织和人物只读工具；历史事件引用不自动成为局势影响，需要实际读取与判断。
- [组织插件](../../../src/agents/plugins/organization/README.md)维护组织、组织关系和成员关系，提供规划者查询。它的角色等级过滤只适用于组织查询，并不自动保护复制到局势中的内容。
- [地图插件](../../../src/agents/plugins/map/README.md)维护地点及空间关系；[人物插件](../../../src/agents/plugins/character/README.md)维护人物和人物关系。各模块有各自存储、身份和版本规则，不存在已经实现的统一跨模块对象或局势引用服务。
- 专用 Agent 可参考[历史 Agent 装配](../../../src/app/agents/history-agent.ts)和[历史引用绑定](../../../src/app/agents/history-references.ts)：可信应用绑定同世界负责人、目录、Session、模型和已授权存储句柄；模型提供任务和必要背景，不自报权限。
- 当前没有初始局势的专用插件、专用 Agent、持久数据格式或局势工具。现有主 Agent 提示词提出初始状态规划目标，不代表本模块已实现。宏观发展蓝图和完整世界演化能力尚待后续开发。

## 两个世界与边界走查

### 开放修仙世界

青云宗过去因灵脉变化迁徙，历史记录迁徙；起始时新山门附近灵气紧张，宗门和散修争用修炼资源。初始局势描述资源紧张、涉及区域、各方已知利益和未解决问题，引用山门地点、青云宗、相关组织关系及迁徙事件。远方灵脉尚未调查时明确保留未知，不推断全世界都缺灵气。

如果只有传闻称灵脉受人为破坏，局势应保留其说法性质；历史中的隐藏内容可供规划者参考，但不能因此认定散修或宗门成员知情。角色自身的观点按人物资料维护。未来灵脉是否恶化及各方如何行动留给后续规划和实际演化。

### 资源有限的城邦群

青河战争已结束，战争经过归历史；起始时各城供水紧张，上游城限制水渠流量，下游城对此提出抗议，两城之间已有的敌对关系归组织模块。局势说明这些当前处境如何相互影响，并引用已存在的战争、水渠地点及组织关系；若关系文件未建立，保留明确线索，不虚构关系 ID 或擅自写入组织目录。正在进行的谈判只记已知的当前情况，结果未知。

同样的城邦背景可以对应不同起始状态：一种是封渠且谈判尚未结束，另一种是暂时恢复供水但协议仍不稳定。用户确认同一世界使用一个初始化起点，允许多个待审局势方案；这些方案可以描述该起点的不同候选状态，分别审阅，不把某个方案视为已经采用。

### 缺失与冲突

历史说战争已停战，但组织关系仍敌对并不必然冲突；停战与敌对可以同时成立。若历史明确说水渠已毁且无修复记录，局势却写水渠正在正常通水，应展示各自资料、具体矛盾和未核查范围，等待讨论；不能自动判定谁正确，也不能直接修改其他模块。组织关系、人物资料或地点暂不可读取时，区分未配置、未找到、无权、读取失败和资料变化，不把它们解释为世界中不存在。

## 时间、资料与组织方案

### 起始时点

用户确认一个世界有一个初始化起始时点，可有多个待审局势方案；保存多个方案不等于存在多个正式世界起点或已经选定方案。建议记录明确的参考时点说明，可使用世界纪年、相对其他事件的表达或“具体时间未知”；不要求公历、精确日期或将不同纪年强行换算。历史中的 `initialization` 相对基准应指向同一世界起始概念，但现有历史格式并没有统一起点对象 ID、跨模块时间换算或校验服务，不能宣称已经建立。未来需要改变起点时须检查现有历史相对表达的含义；不能静默把旧的相对时间解释成新起点。

文件版本、Session 时间和目录更新时间均不是世界时间。当前只规划初始化时点的表达，不实现世界时钟、事件推进、历史快照或多个世界时间线的自动切换。

### 局势内容与粒度

用户确认按需将局势拆成多份可关联的条目，并保留总览；组织之间的关系仍由组织模块维护，局势引用并描述影响。例如“河谷供水紧张”可以单独表达概况、已知状态、涉及范围、影响和未定问题，也可关联封渠与下游抗议。文本可以表达复杂差异，只有定位、引用、版本等确需程序判断的内容才定义结构，不预设所有世界必须填写统一的危机模板。

每个待审方案有一份总览，记录所用起点说明、规划重点、覆盖范围及具体局势入口；总览是可更新的导航和整体说明，不复制每一条局势正文，也不能因未列出某条内容就推断世界没有该处境。建议每个条目明确所属方案，各方案独立维护自己的条目；不同方案即使都描述同一个水渠，也不共用会被一方编辑覆盖的局势正文。地图、组织等权威资料仍可由多个方案共同引用。总览和条目的精确关系、引用完整性与版本语义在契约步骤确定；方案的选择和确认留给后续确认流程。

### 与权威资料的关联

建议以类型加稳定 ID 引用实际存在的历史事件、地点、组织、组织关系、人物和人物关系；能否通过现有接口直接解析某一类型须逐项核对，不能假设所有模块接口一致。跨模块名称从原资料读取用于展示，不把姓名或名称作为 ID；重名列出候选，未建档内容保留可读线索，不编造 ID。

局势正文可保留理解影响所需的简短叙述，但对象完整资料和关系的权威内容只由原模块维护。关联意味着“与此处境相关”，不自动推断因果、角色知情、组织成员或未来行动。保存引用前核验同一世界和目标；读取时再次核实可用性，明确“以前核验成功”不保证现在仍存在或未改变。

建议记录实际读取来源的定位、版本或可靠摘要以及读取结果，用于判断资料是否改变；只对来源支持的版本做比较，不同接口没有版本时报告无法核验，不把目录摘要当作正文版本。发现变更只提示需要重新核对，不自动重写局势或其他模块。外部文件逐个读取不构成跨文件事务或原子世界快照。

### 未知、审核与角色认知

局势对未知原因、未调查地区、正在进行而结果未知的活动、待核实线索分别作可读说明；无结果、未覆盖、读取失败和角色不知道不能混为一谈。建议保留整体及条目展开程度，是否需要机器可判断的固定枚举在契约阶段结合实际查询确定，不为每个世界强制填满。

局势 Agent 与规划者可以读取其获授权的完整世界规划资料；角色知道什么来自人物初始化时自身资料及后续实际经历，不能因为局势可读就默认角色知情。组织的角色等级只约束其查询结果，不自动过滤局势、普通文件、搜索或目录。首版不将完整局势文件或工具直接装配给故事角色；角色视角和所有读取旁路由后续角色运行机制设计并验证。

## 文件与版本方案（建议）

参考历史和组织，建议建立 `src/agents/plugins/initial-situation/` 工作区包，插件内部集中格式校验、存储、查询和工具定义。由可信配置提供实际负责人目录，以下名称仅为示意：

```text
<局势负责人目录>/
  overviews/<方案ID>.json       # 该方案的起始时点说明、范围和局势入口
  situations/<局势ID>.json      # 按需建立的局势正文，记录所属方案
  candidates/<候选ID>.json      # 已确认资料的待审修改，是否采用由契约步骤确定
```

建议每份文档从格式版本 1 开始，使用程序生成的稳定 ID；名称与 ID 分离、允许同名。对于未来未知版本、重复 JSON 键、损坏内容、非法或跨世界 ID，明确拒绝并保留原文件。现有 Markdown、目录成果和其他模块文件不自动转换、覆盖或删除；如之后确需迁移，应另行明确版本、备份和迁移策略。

初始化期间未确认的局势建议可读取实际文件版本后整体更新；旧版本发生冲突时拒绝覆盖并重新读取。已确认内容的修改建议参考历史候选机制，保存待审候选、保留基线并标明过期；确认提交和世界演化后的历史留存不在首版实现，具体能否沿用现有基础能力在契约步骤验证。不要把初始化草稿修改当作世界内事件，也不能在世界演化后继续使用初始化覆盖入口冒充历史留存。

创建采用独占写入、更新采用版本条件写入；取消或结果不确定时报告可核查的目标，先查看实际文件，再决定是否补做。资料目录登记与文件保存独立，任何一方失败应分别报告。使用已有单可信写入进程及路径边界，不声称提供跨进程锁、跨文件原子事务或系统级隔离；发生 Windows 文件替换错误时报告实际情况，不在本模块擅自修改后端。

## 插件工具与专用 Agent（建议）

所有局势工具的定义和注册放在同一局势插件中。名称是提案，不代表已经存在：

| 工具 | 计划职责 |
| --- | --- |
| `situation_overview_create` / `situation_overview_read` | 创建或读取一个待审方案的起点说明、覆盖范围及局势入口；不通过保存选定方案。 |
| `situation_overview_update` | 读取版本后更新未确认总览；不自动覆盖独立条目或其他模块文件。 |
| `situation_create` / `situation_read` / `situation_update` | 建立、读取和按版本更新局势条目；返回 ID、实际路径、文件版本与写入结果。 |
| `situation_search` | 按名称、涉及对象或范围查找已记录局势；同名返回候选，明确分页和记录覆盖范围。 |
| `situation_related_read` | 查询已记录的局势关联及相关对象线索；不自动推断因果、反向关系或世界全部关联。 |
| `situation_reference_check` | 调用可信绑定的各模块只读能力核验同世界引用；分别报告缺失、无权、不可用、未配置和已变化。 |
| `situation_consistency_check` | 对实际读取到的来源、版本与可机械检查的约束报告发现、冲突及未覆盖范围；不宣称自动理解全部语义。 |
| `situation_candidate_prepare` / `situation_candidate_read` | 如契约确认采用候选，为已确认局势保存待审修改并核对基线；不执行确认提交。 |
| `delegate_initial_situation` | 主 Agent 提供任务、构想和资料线索；专用 Agent 负责开发局势，可信应用绑定世界、身份、目录、Session 和权限。 |

局势 Agent 首先读取用户构想及授权范围内的世界基础信息、历史、地图、组织和人物已有成果；按需查找、核对引用，识别当前处境及留白，保存自身结果并说明依据、覆盖范围、冲突、尚未核验内容和登记状态。找不到资料时可以继续保留线索或请求相关模块补充，不能冒充其他模块已创建资料。

主 Agent 根据世界构想选择是否委派，并整合、读取和核查成果；已划分的初始局势内容由专用 Agent 开发。主 Agent 仍可主动补充十个模块之外的必要内容。独立运行和委派应复用现有 Preset、SystemPrompt、Tools、Session、工作区和专用委派形式；目录服务在主 Agent 已持有时借用可信绑定，外部存储句柄由创建者管理并保持有效。

局势 Agent 仅写自身负责人目录；地图、组织、人物和历史通过可信应用配置的只读句柄或已授权文件读取，不因模型提供的世界 ID、路径或名称获得权限。相同身份并发启动拒绝；取消、启动失败和关闭时清理注册、等待已受理操作并释放身份。Session 可恢复对话，不能证明任务完成；恢复后先读取实际成果及版本，不盲目重复创建。

## 开发步骤与验收

1. **核对边界和起始方案。** 对照当前代码与两种世界样例，落实已确认的一个世界起点、多个待审方案及按需拆分的总览和条目；核对组织关系、历史相对时间和人物认知的归属，形成明确验收场景。需要新增业务决定时先讨论，不提前实现依赖该决定的契约。
2. **局势资料契约与受控存储。** 在确认的组织方式下细化版本化 JSON、起始时点、ID、引用、留白、审核状态、候选及旧资料策略；实现局势插件内格式、真实目录与受控存储。验证同名、版本冲突、损坏、未知版本、越权、取消与写入不确定，保留已有用户数据。
3. **查询与引用工具。** 在插件内实现局势及关联查询、来源核验和可核查的一致性报告；为历史、地图、组织、人物逐项绑定现有只读接口，区分目标未建立、未配置、无权、损坏、已变化与未知。验证来源变化、同名候选、分页变动、跨世界引用和非原子读取；不自动更改外部资料。
4. **局势 Agent 与主 Agent 接入。** 创建职责提示词、Preset、独立入口、可信装配和专用委派；注册局势插件、授权只读工具和可选资料目录。覆盖身份占用、不同 Agent 共存、工作目录隔离、取消、释放、失败恢复和同一 Session 继续。
5. **双世界端到端与交付。** 用固定模型替身和真实工具从主 Agent 委派走查修仙世界、城邦群及不同局势方案，核对实际文件、相关资料、未知、冲突和待审状态；覆盖目录过期、无权、缺失、文件版本变化和保存不确定。单独用真实模型检验工具调用和所选样例的规划内容，说明人工审阅及未覆盖范围；更新应用与插件文档、架构及必要 Agent Note。完成模块后等待用户指示，不自动进入宏观发展蓝图。

**验收：** 用户能读取世界起始时的实际处境、所依据资料、未解决事项及未覆盖范围；历史、当前局势和未来规划不混同，关系由所属模块维护，未知和矛盾不被伪造成确定事实。保存、登记和模型返回不代表用户确认；角色运行与世界演化只按实际实现范围报告。

## 已确认方向与后续细化

用户确认一个世界使用一个初始化起点，可以保存多个待审局势方案；局势按需拆成可关联条目，每个方案保留总览，组织间关系由组织模块维护并供局势引用。保存、登记或生成不会自动选定或确认方案，方案选择机制留待后续确认流程设计。

时间是否精确、每个世界需多少条局势、是否存在危机以及未来如何演化均由实际构想决定，不作为固定模板要求。条目与总览的精确字段、读写和引用策略在契约步骤结合样例细化；如遇影响近期实现的新业务歧义，先提出例子和建议与用户讨论。根据用户指示开始第一步开发。
