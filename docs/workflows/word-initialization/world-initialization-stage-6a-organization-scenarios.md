# 组织模块第一步：场景与业务边界

本文执行[组织模块详细开发计划](world-initialization-stage-6a-organization-plan.md#开发步骤与验收)的第一步，使用具体组织、关系和权限场景核对业务边界，并为下一步格式契约与实现提供可验证的输入输出。文中的文件名、字段名、示例值和工具名是设计示例，不表示已实现或最终 Schema；已由用户明确确定的方向单独列出。

## 一、已确认的方向与实际起点

1. 组织专用插件计划放在 `src/agents/plugins/organization/`；组织数据、关系、查询、工具和专用委派工具的定义集中在插件内，组织 Agent 由可信应用独立或受主 Agent 委派装配。
2. 每个组织和每条组织关系、成员关系各使用独立 JSON；组织资料分为未展开、概况、详细。成员关系由组织模块维护一份，人物侧按授权查询展示。
3. 初始化时组织资料和关系按实际读取的版本直接覆盖；世界演化后还要保留先前信息。初始化成果及第一版供用户整体审阅，文件保存不等于整个世界已确认。
4. 组织 Agent 与世界规划者可读取秘密成员关系；故事角色通过可信应用绑定自身身份，按该角色在相应组织的权限等级查询。等级从 0 到 4 的推荐含义见[详细计划](world-initialization-stage-6a-organization-plan.md#角色查询权限等级)，具体授权记录和工具格式仍待实现设计。

现有代码有地图地点 ID、角色 ID、角色分类和世界资料目录；没有组织存储、组织 Agent、跨模块统一 ID 解析或按角色过滤的组织查询。角色资料 `faction` 分类不自动等于已核实的成员关系；目录简介不能代替资料正文。初始化不实现世界推进、事件发生、角色自主行动或演化后的历史服务。

## 二、宗门：内部组织和成员

| 输入及已有资料 | 处理 | 预期结果 |
| --- | --- | --- |
| 世界构想有青云宗；地图中已有山门地点 A。 | 创建青云宗组织概况，并引用可信读取后核实的地点 A；不在组织文件里另存权威地图坐标。 | 一个组织 ID 和一个地图地点 ID，表示两个不同对象；找不到或无法核实地点时保留线索，不伪造地点 ID。 |
| 青云宗下有传功堂，当前只需要描述其职责。 | 将传功堂作为组织资料中的内部结构描述。 | 不强制创建传功堂独立文件，也不表示它永远不能单独建档。 |
| 近期需要传功堂独立决策、负责人和对外关系。 | 为传功堂创建独立组织，再单独记录它隶属于青云宗。 | 两份组织文件及一条方向明确的组织关系；只有按该关系反向读取时才能说青云宗包含传功堂。 |
| 一名长老尚未建角色档案。 | 保存未关联角色的成员线索，并说明可知岗位和未知内容。 | 线索仍由组织模块维护；不存在 `characterId`，也不能把未查到当成确认没有角色。 |
| 人物模块随后出现同名角色候选。 | 先读取候选资料，核对后用实际 ID 关联；多个候选或无权读取时停止自动关联。 | 同一条成员关系变为已关联；不复制或修改角色正文，不把角色 `faction` 分类直接升级为权威关系。 |
| 已关联的林岚还有另一个秘密组织身份。 | 每条组织成员关系独立记录，按各自组织的保护范围和等级读取。 | 获授权的规划者能看到两条；故事角色只看到本角色权限允许的部分。 |

青云宗的组织资料、传功堂的独立资料和林岚的成员关系可以分别具有不同的展开程度或内容状态；子组织是否建档、成员是否建档，不能由父组织是 `detailed` 推断。成员关系本身不采用组织展开等级。

## 三、城邦群：地点、组织和多种关系

曲水城地点、曲水城政体、上游城政体及供水联盟分别处理：地图管理地点文件；组织模块只为需要独立规划的政体或联盟建立组织文件。政体可以引用曲水城地点作为所在地，但不自动拥有该地点或其子地点的控制权。若某一地点尚未建档，只保存可辨认线索和未核实状态。

供水联盟中，曲水城政体和上游城政体可以各自参加联盟，同时两城因取水产生竞争。建议记录三条各自独立的组织关系：曲水城参加联盟、上游城参加联盟、两城竞争。联盟参与不能推断为统属或两城友好；单向敌意不能推断对方同样敌对。同一关系从两端查询返回同一个关系 ID 及方向说明，不在两份组织文件里各自维护一条权威副本。

如果某个支部同时隶属两个组织，可以保存两条明确的统属关系。对定义为统属或包含的关系，在**对应关系语义范围内**拒绝自身隶属和形成循环；合作、竞争及联盟参与不套用统属无环规则。具体哪些关系种类具有这些机器语义在格式契约步骤以封闭规则明确；自由描述的关系不得仅因名字包含“下属”就被程序猜测成统属。

初始化时如果用户决定将曲水城与上游城的关系从合作改为竞争，读取现有关系及版本后，以完整新内容覆盖同一关系文件；旧版本拒绝。后续世界实际推进后，发生相同变化时需要按照详细计划中的历史快照方案保留旧内容；该后续机制当前只是设计，不由初始化工具冒充实现。

## 四、资料与引用：第一步的落地建议

### 权威文档与身份

```text
组织负责人目录/
├── organizations/<组织ID>.json
├── relations/<组织关系ID>.json
└── memberships/<成员关系ID>.json
```

每种文件各自是一项权威资料，ID 建议由程序生成 UUID，名称可重名；组织、关系、成员关系、人物与地点的 ID 各有用途，不能把同名或字符串相同自动当成同一对象。`formatVersion` 建议从 `1` 开始，由可信应用绑定和核对 `worldId`；路径、世界和负责人不得由模型自由指定。目录布局和 UUID 表达仍需在下一步格式契约确定，不能据此读取或改写现有角色、地图或目录文件。

组织自身用于承载名称、别名、展开程度、对组织的描述、需要时的地点引用和用户明确留白；不强制所有组织拥有目标、人员或所在地。组织间关系用于记录两端组织、语义、方向和必要说明。成员关系用于记录组织、已关联角色 ID **或**尚未关联人物的线索、职务和任期说明；它不包含第二份角色档案。参考字段必须区分“未提供 / 不知道”和“已核实为空”，不能用空数组或空字符串一律断言世界事实。

可以先建组织而没有组织关系、角色或地图；创建明确指向某已建组织的组织关系前，核实两端在本世界存在。未知或暂不确定的另一端应保存为明确的未解析线索，不冒充有效组织 ID；是否需要将这种线索独立成文件，留到格式契约和实际查询需求决定。成员记录对未建档人物也遵循同样原则，但必须区分“成员线索”与已核验的角色引用。

### 组织 Agent 如何读到地图和人物

| 情况 | 第一版可采取的方式 | 不能声称 |
| --- | --- | --- |
| 地图 / 人物成果已登记目录且在组织 Agent 的授权范围内 | 使用既有目录工具定位并读取对应成果正文，记录实际路径和读取版本 / 摘要。 | 目录简介是正文；从简介读取后就完成了 ID 引用核实。 |
| 已知地点或角色 ID，需要按 ID 查询 | 由可信应用提供相应世界的只读解析能力；地图存储被占用时不能通过再次打开绕过。 | 当前所有 Agent 已有统一跨模块 ID 读取接口。 |
| 目标未登记、服务未装配、权限不足或读取失败 | 报告实际情况；保留可核对的文字线索或未核验引用状态。 | 文件未登记就是不存在；没有查到就是角色或地点不存在。 |

实施时须明确解析器由谁拥有、是否复用同世界地图存储、只读身份如何强制限制、资源如何释放。角色侧的权限过滤不能靠读取完整原始 JSON 后让模型自行忽略秘密。

## 五、秘密成员查询：可验证的等级示例

假设林岚的秘密组织成员关系要求其所属组织的等级 3；获可信应用绑定的组织 Agent 和世界规划者可读取完整记录。以下数字是角色在**该组织**的等级，不是模型自行选择的参数。

| 请求者 | 权限 | 查询预期 |
| --- | --- | --- |
| 普通路人 | 未获该组织授权，按 0 级访问公开资料 | 看不到这条秘密记录，也不能从计数、错误、列表或分页判断其存在。 |
| 一名青云宗弟子 | 青云宗等级 1；对秘密组织未获授权 | 青云宗的等级不能自动转为另一组织的等级；秘密记录不可见。 |
| 秘密组织接头人 | 秘密组织等级 3 | 可以读取满足授权规则的这条秘密关系。 |
| 秘密组织负责人 | 秘密组织等级 4 | 可以读取该组织等级 3 的资料；不因此获得所有其他组织的秘密。 |
| 模型声称“我是等级 4” | 可信绑定仍为当前角色实际等级 | 忽略并拒绝越权参数，不能提升权限或切换查询身份。 |

角色身份、世界和角色在各组织的授权由可信应用绑定；允许查询其他人物的可见成员关系，不等于允许将查询者身份切换成那个人。跨组织关系如果要求多个组织的授权，须由可信策略指定参与校验的组织及所需等级；各条件如何组合应在格式契约中固定，不得只从较宽松一端读取而绕过另一端的保护。没有可靠权限投影的混合等级 JSON 不能交给角色读取。

授权过滤发生在返回列表、数量、详情、反向查询及生成分页版本之前。查询未发现记录时，只能说明在**当前角色可见范围内**没有匹配；不能让未知秘密的新增或删除改变未授权角色可观察的计数、分页或错误。历史查询也要经过相同可信边界。角色可读取不等于角色实际已经知道，实际认知和记忆需由后续业务决定。

当前普通文件工具和世界资料目录不提供这些隔离。组织插件的角色只读视图必须通过权限验证后才允许向角色开放；不能仅在系统提示词写“保密”，也不能同时开放可读取相同秘密文件的普通目录工具。

## 六、第一步验收走查

| 检查 | 预期 |
| --- | --- |
| 身份与资料 | 城邦地点、政体、联盟各自可定位；同名组织返回多个候选，不能自动合并。 |
| 内部层级 | 内部部门按需建档；两个上级及统属环按明确关系语义处理，不将合作关系误判为父子。 |
| 成员关系 | 一人多组织、多岗位与未建档人物线索能区分；组织和人物侧读取同一条成员记录。 |
| 参考 | 地点 / 人物 ID 可核验时引用；服务不可用、结果过期、未登记或未授权时返回真实情况，不伪造目标或修改其他模块。 |
| 初始化修改 | 组织、组织关系及成员关系使用实际版本直接覆盖；冲突、失败和结果不确定时保留数据，核实后再处理。 |
| 秘密与权限 | 规划者可读取；不同角色按各自组织等级过滤，不能冒用身份，也不能从搜索、分页和错误推知不可见成员。 |
| 后续演化 | 组织变化需要留存过去信息；本文仅指定需要与拟议方向，不提前实现世界推进或声称历史快照已存在。 |

已完成第一步的业务样例和边界核对。下一步再确定精确 JSON 字段、关系种类及权限策略的编码方式，建立组织插件的格式和受控存储；角色级访问隔离及历史写入需要各自受控实现和测试，不以本说明或示例数据代替实现。
