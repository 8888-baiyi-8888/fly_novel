# docs/AGENTS.md

`docs/` 用于存放面向项目维护者和贡献者的开发文档，包括架构说明、模块设计、开发流程、决策背景、接口约定、生成参考和排障记录。本文是 `docs/` 子树的协作规则；仓库根目录的 [AGENTS.md](../AGENTS.md) 仍然同时适用。

## 文档结构

这些规则适用于面向人的持久文档，不替代提交记录、Issue、PR 或后续建立的 agent 决策记录。文档的主题和所在位置决定它能写多深：当前文档描述自己的主题和直接子主题，高层文档只说明下级内容的目的、职责和高层行为；更低层的字段、协议、测试夹具和实现细节应放到拥有它们的文档或源码附近。

文档应先判断类型：教程或参考。教程按步骤引导读者完成一个结果，只引入当前步骤需要的概念；参考文档定义一个可查找的范围，说明当前行为、约束和接口，不按教学顺序铺陈。教程和参考内容较多时分开写；少量混合内容应在章节标题或开头说明用途。

写教程前，先判断读者的起点和概念难度。先交代前置知识，再逐步增加难度；与当前目标无关的高级内容移到后续教程或参考文档。写文档时按这个顺序处理：确定文档在目录树中的位置，确定允许的细节层级，选择教程或参考类型，按前置关系组织教程，把下级拥有的细节移走，并用链接替代重复解释。

## 分层归属

同一事实只维护在一个最合适的位置，其他地方链接过去。位置选择遵循下表；项目尚未建立的目录或文档不需要预建。

| 位置 | 职责 | 不应放入 |
|---|---|---|
| 根目录 `AGENTS.md` | 每次协作都需要读到的全局规则，每条保持简短，并链接到细则归属处 | 长篇示例、局部流程、只属于某个子目录的规则、从其他文档复制来的说明 |
| 子目录 `AGENTS.md` | 只适用于该子树的协作规则 | 根目录已经规定的仓库级规则 |
| `README.md` | 项目入口、用途、最短启动信息和关键文档索引 | 深入架构、完整流程、详细排障、内部决策历史 |
| `docs/architecture.md` | 系统组成、核心模块、数据流、生命周期、边界和扩展点 | 逐字段类型说明、模块内部细节、决策来龙去脉、临时状态 |
| `docs/development.md` | 开发环境、日常命令、测试策略、构建、发布前检查和 CI 摘要 | 与项目配置不一致的手写命令清单、运行时选择的长篇理由 |
| `docs/modules/` | 模块级设计、接口、限制、配置、语义和扩展点 | 其他模块的职责、从源码或生成目录复制的大段清单 |
| `docs/workflows/` | 项目核心业务工作流的目标、输入、流程、节点职责、输出和状态变化 | 开发者操作步骤、技术模块的内部实现细节、与工作流无关的架构说明 |
| `docs/decisions/` 或 agent 决策记录 | 重要工程决策的背景、取舍、影响和验证方式 | 已过期计划、一次性任务清单、可以直接写进当前事实文档的规则 |
| `docs/postmortem/` | 事故或严重缺陷的时间线、影响、原因和后续改进 | 普通教程、常规排障猜测、与事件无关的架构说明 |
| `docs/cookbook/` | 可重复执行的操作指南和操作后验证步骤 | 设计理由、完整接口参考、一次性处理过程 |
| 生成参考文档 | 从源码、配置或工具输出生成的权威清单 | 手工编辑的生成区域、会与源头漂移的复制内容 |
| 源码注释和 JSDoc | 紧贴代码的非显然约定、参数、返回值、失败条件和副作用 | 评审过程、测试流水账、可从代码直接读出的复述 |

常见归属规则：缺陷复盘放 `postmortem/`；开发或维护操作流程放 `cookbook/`；项目核心业务工作流放 `workflows/`；设计理由放决策记录；系统地图放 `architecture.md`；模块契约放 `modules/` 或模块 README；全局站立规则放根目录 `AGENTS.md`；文档目录规则放本文件。

## 写作规则

- **记录当前状态，不写变更历史。** 避免在持久文档中使用“以前”“现在”“不再”“曾经”“改名为”等叙事。直接写当前机制；变更过程放到提交、PR、Issue、决策记录或复盘。
- **非简单变更要有决策归属。** 涉及架构、跨模块行为、数据格式、生命周期或重要工程取舍时，同步新增或更新决策记录；机械修改、局部文案和格式整理可免除。
- **一个事实只维护一处。** 发现同一规则在多个文件重复时，保留拥有者处的完整说明，其他地方改为简短链接。
- **Markdown 普通段落保持一个物理行。** 使用编辑器软换行；代码块、表格和列表按可读性保留必要换行。
- **代码示例必须可验证。** 文档中的命令、配置和代码片段应来自当前项目实际配置；不能验证时说明限制，不把计划中的脚本写成已可运行。
- **类型和接口文档跟随拥有者。** 修改已记录的类型、事件、配置或持久化格式时，同步更新最接近拥有者的文档；不要只在高层文档补一句。
- **注释和 JSDoc 写契约，不写推理过程。** 保留行为、失败方式、时序、资源归属、异常和副作用；删除实现流水账、评审分析、测试过程和代码复述。
- **语言直接具体。** 默认使用简体中文；专有名词、代码标识符、命令和错误原文按实际形式保留。命名具体对象，不用“某个东西”“相关内容”等模糊表达替代实际主题。
- **链接可机器检查。** 仓库内引用使用相对 Markdown 链接，避免裸文件名；不要添加指向不存在文件、脚本、目录或锚点的链接。
- **敏感信息不得入文档。** 不提交真实密钥、令牌、密码、私有证书或本地私有路径；示例值使用占位符。

## 篇幅控制

项目建立文档预算或链接检查脚本后，在 `development.md` 记录实际命令和适用范围。建立自动化前，按以下顺序处理过长文档：

1. **迁移。** 把属于其他层级的内容移到拥有者文档，只留下必要的一行说明和链接。
2. **压缩。** 保留当前文档必须承担的事实，删掉重复解释、推理过程和过时背景。
3. **拆分。** 当一个文档同时承担多个稳定主题时，拆成专题文档，并在原文留下索引。

篇幅限制是防止漂移的护栏，不是越短越好。能清楚表达当前契约、读者入口和验证方式时，优先保持稳定；需要扩展时说明新增内容的归属理由。

## 文档审查清单

修改任何文档时，顺手检查这些问题：

- 同一规则是否在多个地方重复。保留一个归属地，其余改成链接。
- 是否写了历史叙事或一次性过程。持久文档写当前事实，过程信息移到决策记录、复盘或提交说明。
- 是否出现实现状态标注，例如“已实现”“未来会做”“临时方案”。状态容易过期，必要时改成当前结构、当前限制或待办触发条件。
- 是否手写了可从源码、配置或生成器得到的清单。能生成的内容应说明来源和刷新方式。
- 是否把推理过程、测试流水账或评审对话写进了长期文档。保留结论、契约和验证入口。
- 是否把同一个理由分散写在多个相邻函数、章节或模块旁。把理由收敛到拥有该能力的文档或决策记录。
- 是否出现大段混合多个规则的段落。拆分主题，或把细节下放到拥有者。
- 是否滥用加粗、全大写或强调词。只强调会改变行为的关键词。
- 是否用“应该”描述已经确定的当前行为。当前行为直接写“使用”“拒绝”“返回”“要求”等明确动词；未定事项标明触发条件。

## 交叉引用

仓库内文档引用使用相对 Markdown 链接，并尽量链接到拥有该事实的具体章节。新增或修改链接后，至少人工确认目标存在；项目建立链接检查命令后，按 `development.md` 中登记的命令运行。
