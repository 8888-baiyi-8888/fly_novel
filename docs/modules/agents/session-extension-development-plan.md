# Session 扩展能力开发计划

本文细化[长期开发计划](../../development-plan.md#开发顺序)第 7 项，与[Session 基础开发顺序](session-development-plan.md)衔接。需要跨进程继续对话时，按本计划开发独立的 Session 持久化能力；长历史检索和上下文压缩仅在出现具体需求时另行设计。

## 目标与当前边界

当前 [`@fly-novel/session`](../../../src/agents/plugins/session/README.md) 在内存中保存只追加事件，并从事件派生模型消息；Agent 销毁时关闭并清空 Session。[Agent Loop](../../../src/agents/plugins/loop/README.md) 创建并持有该实例，进程退出后无法恢复。`Session.append()` 是同步操作，事件使用连续 `seq` 和时间戳；持久化读取、异步写入与恢复不能仅靠把 `read()` 的结果写入文件完成。

目标是在调用方明确选择并配置持久化时，保存已有 Session 事件，并在进程重启后恢复同一会话、继续模型调用。对话事件归 Session；小说角色档案、经历、认知和正式剧情数据不属于本计划。旧角色 Agent 的 SQLite checkpointer 与新 Session 使用不同执行路径，是否需要读取或迁移旧数据另行决定，本计划不自动读取、转换或删除旧数据。

## 官方参考与差异

- 官方 [`@deepseek-ai/dsh-session-persistence`](https://github.com/deepseek-ai/deepseek-harness/blob/f3803c96974ad4a94195fb97e5c637e9c2a3afe3/packages/session/session-persistence/README.md) 定义 `ctx.sessionPersistence` 存储服务，以及 Session 句柄的读取、追加、刷新和关闭契约；[`@deepseek-ai/dsh-session-persistence-jsonl`](https://github.com/deepseek-ai/deepseek-harness/blob/f3803c96974ad4a94195fb97e5c637e9c2a3afe3/packages/session/session-persistence-jsonl/README.md) 提供 JSONL 后端。开发前以当时实际官方源码及固定版本为准，核实名称、签名和行为，明确本项目适配差异。
- 基础 Session 保持通用，存储实现使用独立插件；在现有 Harness 的注册和生命周期内按需装配，不因计划预先更改所有 Preset。
- 本项目的事件结构、同步追加、Surface 和 Loop 生命周期与官方存在差异。恢复、事件订阅和写入确认方式须在对应步骤对照官方后确定，不能假定当前已有官方的持久化、重放或发布机制。

## 每步执行规则

每一步开始前说明要解决的问题、官方实际方案、本项目示例、输入输出和预期行为，等待用户确认接口与方案。确认后只实现该步的最小功能；验证完成后对照官方解释异同并停下，等待下一步指示。开发时提供独立、可在 VS Code 调试的测试及操作说明。不得把未实现接口或示例命令写成当前可运行功能。

## 开发步骤

**1. 确定持久化使用场景与会话身份**

用一个角色 Agent 的跨进程续聊例子确认：调用方如何指定或取得 Session ID、创建新会话与打开已有会话如何区分、Agent 与 Session 谁拥有谁、存储位置由谁配置，以及同一角色不同场景是否共享会话。说明输入、输出、缺失会话和重复创建的预期行为；检查现有 Session Manager、Loop、Preset 和调用链。确定当前阶段支持的使用场景，不将 Agent ID 直接当作小说角色 ID，不预设旧数据迁移。本步以设计和现有代码核对为主，不实现文件读写。

已确认的使用约定：Agent ID、Session ID 和小说角色 ID 分别表示运行实例、对话和业务人物，不互相替代。新建会话时生成或由调用方指定 Session ID；恢复时明确提供已有 Session ID，恢复不存在的会话和重复新建已有 ID 均报错。同一人物是否复用会话由调用方按场景决定。应用配置持久化根目录；Agent 运行时持有会话，关闭运行实例释放句柄并保留已保存的会话。跨进程如何持久记录业务人物、Agent 配置与 Session ID 的对应关系，以及如何校验恢复时的绑定，结合具体业务存储方案另行确定；不得假定持久化服务自动建立这层关系。

**2. 定义持久化服务与会话句柄契约**

对照官方 `sessionPersistence` 和句柄实际代码，确定创建、打开、读取、追加、刷新和关闭各自的输入、输出、失败及资源归属；按确认的需求决定是否同时实现 `stat`、`list` 等官方能力，不另造同职责命名。明确写入成功、flush 完成和关闭的区别，以及 Session 事件顺序。先实现最小独立契约和 Cordis 装配，使用受控内存实现验证；不把读写逻辑塞进基础 Session。

**3. 实现 JSONL 持久化后端的最小闭环**

参照官方 JSONL 后端，根据已确认的契约实现创建、顺序追加、读取、flush 和关闭。先明确头部、事件记录、存储路径与文件命名、格式版本和不支持版本的拒绝或迁移策略；明确首版压缩和耐久性边界，以官方实际代码和项目环境核对后决定。验证空会话、事件与 ID 原样往返、连续序号、重复创建、缺失文件、无效或不支持的记录，以及失败不静默覆盖用户数据。

**4. 接入 Session 事件并恢复模型历史**

对照官方事件持久化和恢复流程，补齐本项目所需的事件观察、写入和重建能力，使已持久化事件按原始顺序、ID 和时间恢复，并重建 Surface 与 `deriveMessages()` 所需状态。针对同步 `append()` 与异步存储，先确认写入顺序、失败传播和 flush 时机；验证工具调用及结果按 ID 配对、最新系统提示词和连续序号保持正确。异常或不完整历史的处理必须明确，不静默丢弃事件或重复执行工具。

**5. 让 Agent Loop 按需创建或恢复会话**

通过第 1 步确认的调用入口选择新建或恢复的 Session，将持久化服务和 Loop 按 Preset 或调用方配置组合；明确缺少插件或存储时的行为。恢复后下一次 `run({ prompt })` 使用此前消息继续请求，Turn/Step 编号不与历史冲突；不影响不装配持久化的内存模式。固定 LLM Adapter 验证关闭、重新创建 Harness、恢复会话后的模型输入及新增事件；说明 Session 与 Agent 的绑定和清理责任。

**6. 完善异常恢复和资源释放**

以实际后端与运行场景为依据，对照官方验证顺序追加、flush/close 幂等性、写入失败传播和销毁时等待完成。明确进程中断后未完成的 Turn、Step 和工具调用的恢复语义：区分已记录结果、尚未开始和已开始但结果未知；不能把未知结果当作成功，也不能自动重复可能产生副作用的工具。检验文件尾部截断、格式损坏和恢复失败；修复或截断策略需先确认，并保留可恢复数据。

**7. 端到端验收与官方对照**

固定 LLM Adapter 配合真实持久化后端验证新建、运行、flush、关闭、重建、恢复和再次运行；覆盖普通消息、工具结果与错误路径，并验证未启用持久化时的内存行为。需要时再执行受控真实模型测试。对照官方契约列出完成能力、明确差异和推迟功能；提供独立 VS Code 调试测试与操作说明。未通过的验证和暂不支持的恢复情况明确报告。

## 按需另行设计

同一会话的并发打开与写入、恢复时模型或提示词变化的处理，以及长历史检索、上下文压缩、其他持久化后端、旧 SQLite 会话迁移和小说业务数据读写，当前不作专项设计，出现具体需求时另建步骤并确认接口。会话存储包含模型输入输出，日志、测试和文档不得写入真实凭据。
