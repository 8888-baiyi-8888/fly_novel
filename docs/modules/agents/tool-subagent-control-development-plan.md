# Tool SubAgent Control 详细开发计划

本文细化[第三阶段 Tool SubAgent Control](../../workflows/word-initialization/world-initialization-stage-3-plan.md#6-tool-subagent-control)，按官方学习、本项目契约设计、底层能力和控制工具的顺序推进。每步开始先说明问题、使用方式、输入、输出及预期行为；完成后记录实际观察与验证，等待用户指示，不自动进入下一步。文中的示意名称和拟议行为不代表当前接口已经存在。

## 一、要解决的问题

当前通用和角色委派工具启动一次子任务，前台等待结果并释放运行。父 Agent 只有工具返回后才能进行下一模型步骤；不能拿到一个可持续管理的子 Agent，再在工作期间查询或补充要求。可信代码可以持有一次性 Run、等待结果和通过信号取消，但这不等同于模型按子 Agent ID 发送消息或管理子 Agent。

本阶段先研究如何启动和管理可继续交互的子 Agent，再给父 Agent 装配控制工具。目标是让可信装配允许的父 Agent 能启动子 Agent、发现它、发送后续消息和请求中断；结果如何回到父 Agent，需要在设计步骤明确，不能把“消息已接受”当作“子任务已完成”。

例如，世界初始化主 Agent 启动角色 Agent 分析一名角色，在子 Agent 工作时收到用户补充设定：父 Agent 可以选择向该角色 Agent 发补充消息；如果任务方向改变，也可以请求中断。角色 ID、子 Agent 实例 ID 和一次运行 ID 各自含义不同；是否支持消息中途生效、空闲后续轮次以及如何通知结果，必须在核对现有 Loop 和官方行为后确定。

## 二、官方参考与当前项目

固定参考 DeepSeek Harness commit [`0d1f50007f9bca3f52b06e1c3074fa14d5fb0720`](https://github.com/deepseek-ai/deepseek-harness/tree/0d1f50007f9bca3f52b06e1c3074fa14d5fb0720/packages/subagent)。[控制工具](https://github.com/deepseek-ai/deepseek-harness/blob/0d1f50007f9bca3f52b06e1c3074fa14d5fb0720/packages/subagent/tool-subagent-control/src/index.ts)将 `send_message` 和 `interrupt_agent` 委托给 SubAgent 服务；[列表工具](https://github.com/deepseek-ai/deepseek-harness/blob/0d1f50007f9bca3f52b06e1c3074fa14d5fb0720/packages/subagent/tool-subagent-control/src/list-agents.ts)独立装配并列出可继续子级。官方的 `send_message` 返回接收回执而非对方回复；`interrupt_agent` 接受请求不等于已经完全停止；列表是状态快照，不能代替发送时的权限与存在性校验。官方的持续会话、激活、持久化、后台通知和一次性调用是不同的路径，具体调用链在第 1 步核对。

本项目的 [SubAgent 核心服务](../../../src/agents/plugins/subagent/subagent/README.md)按作用域注册 Provider；[Run 契约](../../../src/agents/plugins/subagent/subagent/types.ts)提供 `result` 与 `dispose()`，不维护已交付运行的父子目录或消息服务。[共享 Driver](../../../src/agents/plugins/subagent/subagent-in-process-driver/README.md)执行一次任务。现有 [Spawn](../../../src/agents/plugins/subagent/subagent-spawn-in-process/README.md) 和 [Fork](../../../src/agents/plugins/subagent/subagent-fork-in-process/README.md)是一次性运行；Fork 控制初始历史，不代表子 Agent 可以持续对话。Fork 当前还拒绝包含工具调用等不支持的父历史。

[Agent Loop 契约](../../../src/agents/plugins/loop/types.ts)提供 `run`、`cancel` 和 `dispose`；标准 Loop 的多次 `run` 排队执行，`cancel()` 还会拒绝已排队调用。当前没有官方式的执行中消息注入或持久化子 Agent 恢复契约，不能把排队执行声称为在当前模型步骤中途引导。[通用委派工具](../../../src/agents/plugins/subagent/tool-subagent/README.md)和[角色委派工具](../../../src/tools/README.md)均使用前台 Spawn；角色工具传递角色 ID，角色 Agent 目前不按 ID 检索资料。

## 三、首版设计需要解决的边界

以下问题在第 2 步形成明确决定和测试矩阵，再实施；不预先复制官方全部能力。

### 1. 子 Agent 如何启动并保有

区分一次性前台任务与可继续子 Agent。可继续实例需要明确创建入口、返回给父 Agent 的标识、何时交付、谁持有 Agent 与 Session、任务运行期间父 Agent 如何继续执行、空闲状态保留多久以及何时释放。应先复用既有 Preset 注册和可信配置：通用与角色 Agent 按父 Agent 职责装配相关工具，角色 ID 是业务输入，不让模型指定适配器、插件配置或授权目录。是否修改现有委派工具或增加独立的后台 / 可继续入口，在第 2 步明确；不能悄悄改变现有工具等待结果的行为。

### 2. 发送、回复与通知

需要分别定义：请求已接收、进入队列、开始执行、完成或失败各自代表什么；消息 ID 的来源、顺序、重复请求、取消和拥塞如何处理。发送回执不是子 Agent 的回答。子 Agent 的输出如何进入父 Agent 可读的消息或事件、父 Agent 已结束或关闭时怎样处理、是否需要应用层主动读取，必须有明确交付方式；不能假定父模型会自动收到后台结果，也不能隐式拼接额外提示词。

执行中收到消息时，先比较“当前轮次后排队”与“下一 Step 边界中途引导”。项目当前只有前者可作为已知的 Loop 基础，且取消会影响排队任务；是否需要改 Loop 才能实现官方式 steering，由第 1、2 步确认。首版未实现真正的中途引导前，工具描述必须准确说明消息何时可能生效。

### 3. 中断和关闭

中断当前轮次、取消队列、销毁 Agent 是不同操作。明确中断请求返回时机、已排队消息及后代的处理、空闲 / 已结束 / 不存在目标的响应，以及中断后能否继续。评估现有 `Agent.cancel()` 会同时拒绝排队调用的影响，不能直接包装后宣称符合官方“队列保留”语义。父关闭、服务卸载和应用退出时必须定义持有者、通知、清理和错误传播；不得让后台任务成为无所有者任务。

### 4. 身份与关系

区分 `SubagentRunId`、Agent 实例 ID、Session ID、消息 ID 和业务角色 ID；只有在语义一致时才复用，跨模块类型不能混用。父子关系由可信创建和管理服务记录，不能由模型传入的目标 ID 或请求自报父 ID 授权。查询、发消息和中断分别定义允许直接子级、后代或父级的范围；校验调用时的真实实例和当前关系，处理目标已销毁、ID 复用和过期列表，不暴露其他父 Agent 的实例或敏感记录。

### 5. 状态、并发与存储

状态必须由真实受管理实例和任务结算推导，避免把消息回执当作完成。确定最少状态、快照一致性、重复关闭、并发发送与中断、初始化 / 发布 / 销毁竞争、父子清理顺序和资源上限；采用受控门闩测试，不依赖任意等待。先评估内存中可继续运行是否满足首版，重启恢复、冷激活、持久化目录和跨进程租约不是当前已有能力；如决定支持持久化，必须另行明确格式版本、迁移 / 拒绝策略、句柄与写入失败，不能静默修改或删除已有数据。

## 四、详细开发步骤

### 1. 追踪官方控制与继续运行调用链

**问题与使用方式：** 弄清控制工具与后台子 Agent 底层如何分工，再核对项目真正具有的能力。本步以固定 commit 的源码、测试和必要的只读验证为主，不先开发。

1. 阅读官方 `tool-subagent-control`、独立 `list-agents`、`tool-subagent` 的后台 / 可继续配置；跟踪工具参数、`exec.agent`、服务调用、回执和失败，不把工具描述当成服务实现。
2. 跟踪官方 SubAgent 服务中的子级创建、关系记录、消息投递、inbox、Activation、运行中 / 空闲消息处理、interrupt 和结果通知；区分一次性任务与可继续任务、驻留和冷恢复路径，记录关键调用链与资源所有权。
3. 阅读官方相关测试，核对父子 / 同级 / 后代权限、列表状态、消息和中断的竞争及清理；区分源码推断、测试用例与真实运行观察。若运行官方示例受环境、凭据或网络限制，记录具体限制，不使用替身结果冒充真实模型运行。
4. 对照本项目 SubAgent、Manager、Loop、Session、Tools 及通用 / 角色委派工具，画出当前一次性调用链与可继续控制缺口；重点核实 Loop 排队、`cancel()`、Session 和服务作用域的真实行为。

**完成条件：** 文档记录固定 commit、官方与本项目调用链、状态 / 消息 / 中断 / 通知边界及缺口；不实现工具或声称官方全部语义已具备。

### 2. 确定最小可继续委派与控制契约

**问题与使用方式：** 先明确父 Agent 如何获得可控制的子实例，以及各操作对状态和资源意味着什么；输入与输出需能用于后续真实测试。

1. 确定首版是否只支持进程内驻留和直接子级，是否需要后台启动、结果通知、子向父消息、后代列表或重启恢复；逐项记录支持、拒绝和延后范围，不把可选能力混成默认承诺。
2. 设计一次性前台和可继续委派的入口、返回值及资源所有者；考虑通用与角色两类工具和内部固定 `presetId`，角色工具接收 `characterId`，子实例的具体业务参数仍由各专用工具提供。配置由可信装配提供，不预建固定数量的子 Agent。
3. 选定标识类型与记录归属，定义父子关系如何建立、发布和移除；设计父身份的作用域验证、调用者活跃性与关系授权，分别明确查询、发送和中断的可访问范围。
4. 定义状态机、消息接收和执行顺序、输入 / 输出、回执、结果投递和父 Agent 可见性；说明运行中消息是排队还是 Step 边界引导，以及取消和中断是否影响队列。
5. 为失败与竞争建立表格：不存在、非子级、父已关闭、目标已销毁、状态过期、重复请求、创建中关闭、投递并发中断、消息接受前后取消、Agent / Session 初始化失败及释放失败；确定错误传播和回滚。
6. 确定资源容量、消息大小 / 排队上限是否属于当前需要及配置归属；不能静默丢消息。确定 Session、持久化与敏感信息边界；如首版仅内存，明确进程退出不能恢复。
7. 确定需要修改的现有模块、面向模型的工具 Schema、装配方式和测试；对官方差异说明理由。若功能取舍需要用户决策，先记录可核实的方案与影响，再请求指示。

**完成条件：** 文档包含可运行目标的时序示意、状态 / 权限 / 错误 / 清理矩阵、可信装配与接口边界、各后续步骤；不提前实现控制工具。

### 3. 建立受管理的可继续子 Agent 核心

**问题与使用方式：** 按第 2 步契约让可信代码启动并管理子 Agent，形成可信父子关系和独立资源；本步先不依赖模型工具。

1. 在已有服务和 Manager 的实际扩展点上实现创建、发布、查询与释放；明确内部实例、Session、任务状态和拥有者，复用现有 Preset 及可信模型配置，避免维护两套不一致的真源。
2. 公开最小可信操作与独立标识类型，执行父身份 / 关系校验；一次性 Run 的所有权和现有前台 Spawn / Fork 行为不得意外改变。
3. 建立与设计一致的生命周期和状态投影；发布失败回滚未交付实例，服务关闭处理已拥有的实例和后台任务，重复释放等待同一次清理并报告失败。
4. 使用固定替身与真实 Manager 验证允许的通用 / 角色 Preset、角色参数、隔离、未知或不允许的类型、跨父访问、创建失败、关闭与并发释放；新增必要的架构和决策记录。

**完成条件：** 可信代码可创建、发现和释放一个受管理子 Agent，状态和父子关系有确定所有者；尚不声称消息控制工具可用。

### 4. 实现后续消息与结果交付

**问题与使用方式：** 可信调用方对已管理子 Agent 提交后续消息，观察接收回执、执行时机与结果的交付；模型工具暂不参与。

1. 按第 2 步实现消息准入、队列、顺序、容量与消息 ID；明确接收后取消、目标消失、失败及关闭时每条消息的去向，不能重复执行或静默丢失已接受消息。
2. 让受管理子 Agent 使用自身 Session 执行后续工作；对运行中消息按约定排队或实现经确认的 Step 边界引导。若需修改 Loop，先读其设计和测试，明确与现有 `run` / `cancel` 的关系。
3. 实现已确认的结果交付方式：记录来源和关联关系，区分接收回执与完成结果；父关闭或消费者不可用时按契约处理。子输出属于建议，不自动变为已确认的世界事实。
4. 用门闩验证空闲发送、运行中发送、顺序、取消、容量、任务失败、父 / 子关闭和结果交付；检查未授权目标不可访问，并核实内容未被隐式添加额外提示词。

**完成条件：** 可信代码可以向允许的子 Agent 发送消息，并明确观察接受、执行和结果的独立状态；未实现的实时 steering 或持久化不得伪装成已支持。

### 5. 实现中断与列表服务

**问题与使用方式：** 在底层服务中查询受管理子 Agent，并对授权目标请求中断；工具仅在后续步骤适配这些能力。

1. 实现与第 2 步一致的中断语义，区分中断接受、当前轮次结束和实例销毁；检查现有 Loop 取消对排队任务的影响，必要时仅作经设计确认的最小调整。
2. 实现作用域内列表与状态投影，明确是否只返回直接子级；以实际管理记录和 Loop 状态为依据，不暴露无权访问的对象。状态为瞬时快照，控制操作再次验证权限。
3. 验证运行 / 空闲 / 已结束 / 不存在目标、父子关系变化、同级和外部调用、并发发送与中断、重复中断、关闭竞争；确认子任务失败与清理失败不会丢失。
4. 若首版不支持一次性 Run、后代或子向父控制，使用明确错误和文档边界，不将其显示为可控制目标。

**完成条件：** 可信调用可发现并控制授权子 Agent，状态、权限、中断与资源清理均有行为测试。

### 6. 装配模型控制工具

**问题与使用方式：** 在底层能力通过验证后，把控制操作映射为模型可调用工具；工具作为适配层，不自行维护第二份子 Agent 状态。

1. 对照官方工具分别定义 `send_message`、`interrupt_agent` 与 `list_agents` 的名称、Schema、描述和输出；是否让列表工具独立装配按第 2 步确定。描述明确消息接收与完成不同、中断接受与停止不同、状态可能变化。
2. 使用实际工具调用上下文中的可信 Agent 身份，服务重新校验权限；不接受模型自报的父身份，不将业务 `characterId` 当成运行目标 ID。
3. 接入通用 / 角色子 Agent 的可信启动入口与按职责装配；保留现有一次性工具契约，除非第 2 步明确决定修改并同步所有调用方。
4. 测试 Schema、成功 / 拒绝结果、工具注册和卸载、未装配不可见、不同父作用域隔离、取消信号与错误；工具接收回执不能被渲染成子 Agent 回复。

**完成条件：** 已装配控制工具的模型能够对允许的子 Agent 发起第 2 步定义的操作，工具名称与实际能力一致；不存在底层未实现但对模型宣称支持的行为。

### 7. 端到端验证与交付

**问题与使用方式：** 从公开入口组装父 Agent、受管理子 Agent 和工具，通过固定模型适配器驱动真实 Loop，验证完整交互与释放。

1. 用可重放的模型步骤验证：父 Agent 启动受管理子 Agent → 获取可用标识 → 查询状态 → 发送补充要求 → 按约定取得结果 → 对适当任务请求中断 → 父子资源清理。按实际首版语义构造时序，不用轮询冒充自动通知。
2. 验证通用与角色专用入口、角色 ID 传递、父子 Session / 工具 / 权限隔离；检验未知目标、非子级、已关闭目标、消息拒绝、任务失败与取消。角色资料是否按 ID 加载按真实实现说明。
3. 用受控门闩覆盖发布、消息投递、中断、父 / 子关闭和服务卸载的竞争；检查 Manager、后台任务、监听器和 Session 句柄无泄漏，并覆盖清理异常。
4. 同步 SubAgent、Loop、控制工具和应用装配说明、工作区结构、架构与必要 Agent Note；若改变持久化格式，附带明确的版本和迁移 / 拒绝策略及测试。
5. 运行受影响的聚焦测试、类型检查、必要构建和文档链接 / 空白检查；固定替身不代表真实模型调用。如另行执行真实模型冒烟，只用已有可信配置，不记录密钥、完整私有配置或敏感会话。

**完成条件：** 已确定范围内的控制链可从公开入口复现，状态、消息、结果、中断、权限和清理均有证据；记录尚不支持的官方能力。完成后等待用户指示，不自动进入下一阶段。

## 五、交付与非目标

本计划的目标是先建立确有底层支持的控制能力，再提供相应模型工具。首版具体是否包含后台通知、子向父消息、后代控制、运行中 steering、持久化恢复及跨进程运行，由第 2 步在核对需求与实现后确定；未纳入的能力明确留待后续设计。不会因为提供 `characterId` 就声称角色资料已经加载，也不会将子 Agent 输出自动写成用户确认的世界事实。
