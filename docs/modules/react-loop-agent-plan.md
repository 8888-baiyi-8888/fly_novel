# ReactLoopAgent 分阶段开发计划

本文是开发与教学计划，不表示各阶段已经实现；V0～V6 是学习里程碑，不是 npm 版本号或正式发布标签。每次只推进指定阶段，验收后再接入下一阶段的依赖。

## 项目起点与参考基线

本地已有 [Session](../../src/harness/session/session.ts)、[LLM 模块](../../src/llm/index.ts)、[作用域](../../src/harness/scope/index.ts)和[事件分发器](../../src/harness/agent/dispatch.ts)。[Agent 接口](../../src/harness/agent/type.ts)只要求 id；[ReactLoopAgent](../../src/harness/agent-loop/agent.ts)仍是构造阶段的开发稿。工具目录主要是职责说明，系统提示词入口主要是组装结果类型，不能视为完整服务。已有消息、事件及错误协议优先复用。

上游参考仓库为 deepseek-harness，本计划核对的提交为 `0d1f50007f9bca3f52b06e1c3074fa14d5fb0720`。以下上游路径均相对于该仓库；开始每版时检查实际提交及工作区差异，不能把文件行号或最新上游行为当作固定不变的事实。

| 上游位置 | 用于学习的内容 |
| --- | --- |
| `packages/core/agent-loop/src/agent.ts` | constructor、status、setPhase、send、cancel、whenIdle、turn、step、prepareRequest、buildRequest |
| `packages/core/agent-loop/src/assistant-stream.ts` | 模型流的组装及尝试结算 |
| `packages/core/agent-loop/src/tool-calls.ts` | 工具调用执行与结果记录 |
| `packages/core/agent-loop/src/inbox.ts` | 输入排队、领取、替换和取消 |
| `packages/core/agent-loop/src/runtime-context.ts` | 系统提示词与动态上下文更新 |
| `packages/core/agent-loop/src/index.ts` | 工厂组装、会话发布、创建和恢复；不与基础循环一起整体移植 |
| `packages/core/agent/src/runtime-types.ts`、`dispatch.ts`、`projection.ts` | Agent 接口、事件协议及轮次状态投影 |

| `packages/session/session-projection/src/index.ts` | 状态投影注册、历史初始化与增量更新 |

## 保持一致的边界

优先保留已接入能力的上游名称、参数、返回值、消息结构、事件载荷和时序。未接入的成员暂不声明，不用空方法、类型断言或无条件默认值伪装完整接口。基础阶段对输入并发、历史恢复等限制必须明确记录，不能声称与完整上游行为兼容。

本地包使用自己的类型与入口；不混用上游 Session、Message 等类型来消除错误。上游辅助函数须先核对与本地协议是否兼容。共享取消原因和轮次结束类型时确定单一维护位置，不继续复制两套定义。

上游已弃用的同步历史读取方法仅维持已有调用；不把它们作为新状态投影的基础。恢复相关能力尚未进入版本时，只允许构建在空会话上的新 Agent；同一实例内连续轮次不属于跨实例恢复。

## 版本总览

| 版本 | 可演示的结果 | 本阶段新增主要依赖 |
| --- | --- | --- |
| V0：可构造与可释放 | 创建 Agent、读取 idle 状态、释放作用域 | 现有 Agent、Session、scope、dispatch |
| V1：单请求闭环 | 输入一句话，记录并得到完整模型回答 | 本地 LLM 流、固定系统提示词、轮次与步骤事件 |
| V2：工具循环 | 模型调用一个工具，再根据结果回答 | 工具注册与执行、步数限制 |
| V3：输入队列与状态投影 | 执行时接收后续输入，按边界消费 | Inbox、inbox/turnBoundary 投影、可靠的会话提交通知 |
| V4：提示词与动态上下文 | 每步按需更新提示词和上下文，不重复注入 | 系统提示词组装、上下文状态投影 |
| V5：保存与恢复 | 重启后读取会话并安全开始后续轮次 | 会话持久化、版本检查、恢复组装 |
| V6：小说单章节流程 | 从设定和大纲生成并保存一章，可继续修改 | novel 业务组装及成果保存 |

V1 是第一个可运行验收点，V2 是基础工具 Agent 验收点。小说的固定提示词试用和成果保存可以从 V1 开始，不必等全部框架功能完成；V6 是集成验收，不是第一次接触业务。多 Agent、团队协作、自动压缩、调度与完整诊断体系不属于这条基础路线。

## V0：先完成构造与资源归属

学习顺序：Agent 的 id 契约 → Scope 的所有权 → agentEvents 的绑定 → Phase/status → constructor → 释放入口。

- 保留构造参数 `loopCtx`、`id`、`options`、`session`，保留已有作用域和分发器定义；只保留本阶段实际用到的字段。
- 初始化 `scope`、`ctx`、`dispatch`、idle 状态；明确只接收空会话，在创建资源前检查不支持的输入。
- 暂不声明或初始化 `inbox`、`runtimeContext`、`systemPrompt`。删除不完整赋值前先说明改动位置，不覆盖其他开发稿。
- `status` 沿用上游含义；所用 Agent 事件在所属模块声明。`whenIdle()` 在没有活动时立即完成。
- 明确由谁持有并释放 scope；用组装层或已有所有者完成清理，不为了测试额外设计与上游不一致的销毁接口。
- 处理选定路径的语法、导入和类型问题。未完成文件仍在编译范围时，要明确整理方案；不能通过关闭 strict、整体排除 harness 或删除用户草稿取得通过结果。

验收：空会话可以创建；初始状态为空闲；非空会话被明确拒绝且不遗留资源；作用域清理可重复等待，所属监听器和注册被释放。此版不调用模型。

## V1：完成一次模型调用

学习顺序：运行接口与状态转换 → turn/step 边界 → 请求组装 → 流结算 → 错误、取消与 whenIdle。

- 对照上游 `followup`、`cancel`、`whenIdle` 的签名逐项接入；第一版只接收空闲时的输入，忙时明确拒绝。该限制属于基础版支持范围，V3 才扩展为完整排队语义。
- 使用本地 UserMessage、AssistantMessage、调用配置及结构化错误；从 Session 派生模型历史，不建立第二份权威对话数组。
- 实现 turn/step 的开启和结束、用户消息、请求头和助手结算记录。流式输入可以先只向调用方展示最终结果，但必须正确消费流、保留协议要求的尝试信息。
- 固定系统提示词使用现有 system/message 格式；暂不接动态组装和上下文投影。
- 复用应用配置与适配器机制，通过声明的组装入口运行；Agent 不自行解密凭据或建立旁路模型客户端。
- 无工具版本不执行模型返回的工具调用；明确不支持的结果如何结束，不能把它当作普通完成忽略。
- 失败和取消均结束本次活动；保留已输出内容时遵守现有中断标记。取消向模型请求传播，异步任务结束前不释放其资源。

验收：固定替身完成成功、空响应、模型错误和取消用例；日志边界正确；whenIdle 等待实际收尾；同一实例下一次输入可运行且轮次递增；忙时输入不会被偷偷丢弃。真实 API 冒烟缺少凭据时报告跳过，不影响无密钥测试。

## V2：加入工具循环

学习顺序：ToolSchema 与工具参数 → 工具注册和所有者 → tool-calls → step 的继续或终止条件。

- 先实现一个无外部副作用的固定测试工具，形成模型请求工具、执行、记录结果、再次请求模型的闭环。
- 沿用工具调用 ID、tool/call、tool/result 和消息来源规则；schema 校验和工具执行职责明确。
- 支持单次响应中的多个工具调用，第一版按确定顺序执行；不先引入并行调度。
- 明确未知工具、参数错误和执行异常如何形成工具结果或终止原因；取消后尚未开始的工具不得继续执行。
- 循环设置经过校验的步数上限，复用上游已有配置位置；本地缺失时只引入当前所需配置，不增加通用调度体系。

验收：工具结果能进入下一次模型请求，调用和结果一一对应；工具失败、取消和步数耗尽有明确结果；纯文本 V1 用例仍通过。实际写文件或调用外部服务的工具按其授权边界另行接入。

## V3：加入队列和最小状态投影

学习顺序：已提交事件的通知边界 → 投影 init/apply/stateOf → turnBoundary → Inbox 的 splice/claim → send/followup/steer/inject。

- 先接通本地 Session 的受控发布和订阅生命周期：只有事件声明不够，需验证存储关联或等价所有者确实建立，追加后通知能送达。
- 围绕 inbox 与 turnBoundary 实现必要的状态投影，不整体搬入客户端视图发布、投影落盘缓存等未使用能力。单独核对上游定义与本地 Session 接口。
- 在读取队列前完成规则注册与状态初始化；订阅有明确所有者和取消方式，不在对象销毁后更新状态。
- 沿用 `agent/inbox/spliced` 及 next-turn/next-step 的语义，补齐事件类型、生产方和消费方。
- 接入 ReactLoopInbox，再扩展 send、followup、steer、inject；核对唤醒、执行中取消及 keepInbox 行为，避免队列出现两个权威状态来源。
- 轮次读取通过状态投影完成；本阶段仍不宣称支持磁盘恢复。

验收：执行期间的新输入按预定轮次或步骤消费，重复消息标识拒绝；领取、取消、唤醒无丢失或重复；缺少必要投影明确报错；旧轮次数不会默默归零；取消和入队竞争有聚焦测试。

## V4：加入系统提示词组装与动态上下文

学习顺序：PromptAssembly → 固定提示词与上下文的归属 → SystemPromptProjection → RuntimeContextProjection。

- 实现章节设定、人物信息等上下文贡献的组装，保持 sections、contexts、tools、variables 的现有格式。
- 接入系统提示词更新规则，区分可在历史内更新的模型路由与需替换头节点的路由。
- 动态上下文只在有效内容改变时生成消息；正确区分从未存在、已失效、仍被保留的状态。
- 通过初始化状态与增量事件维护所需信息，不新增 snapshotEvents/eventAt 扫描；现有移植稿中的相关调用在迁移此功能时处理。

验收：相同内容不重复注入，清空和替换不留下有效旧指令；不同路由和新系列行为正确；试用小说设定变更后下一步模型输入包含新的上下文。

## V5：保存与恢复

学习顺序：保存的数据契约 → 顺序写入和刷新 → 文件读取及版本策略 → 投影重建 → 恢复组装。

- 在 `session/persistence/` 实现单一存储方式，优先评估 JSONL；目录在实现时建立，Session 不直接操作文件系统。
- 明确事件提交与落盘成功的区别、刷新失败传播、关闭等待、日志不完整及未知版本处理，不静默丢弃必需事件。
- 从显式读取的历史重建 Session 和投影，恢复轮次、待处理输入及上下文状态，再开放 Agent 接收请求。
- 未结束轮次与结果不明的工具调用要明确标记和处理；第一版禁止自动重新执行可能有副作用的工具，不把“加载会话”当成“任意位置自动续跑”。

验收：重启后历史和必要状态一致，继承边界正确；损坏尾部、版本不支持及写入失败有明确结果；不存在重复工具副作用。移除空会话限制前覆盖恢复测试。

## V6：小说单章节集成

- 使用 novel 模块承载设定、大纲、章节正文和修订规则，harness 保持通用。
- 完成“读取设定与大纲 → 生成一章 → 保存正文 → 用户提出修改 → 生成修订”的流程。正文保存与会话日志保存分别管理，已有文件不能无提示覆盖。
- 先做单 Agent 顺序流程；workflow、并行评审和 subagent 只有出现具体需求时再加入。

验收：用户能够完成并保存一章，重启后继续修改；失败不丢失已保存成果；可追溯本次修订使用的输入。必要界面明确运行、完成、失败及取消状态。

## 每版的指导与分支约定

本次只制定计划，不创建分支，不修改上游，也不自动实现 V0。后续开工指令应包含版本号、目标仓库及工作模式；“原项目”需明确为 deepseek-harness 或 fly_novel。

建议的分支名称为 `learn/react-loop-v0`、`learn/react-loop-v1` 等。上游学习分支从记录的参考提交创建，只添加本版阅读指引、中文说明和必要的验证示例，不把删减后的上游当成生产实现；fly_novel 实现分支从上一版已验收提交开始。第一版从用户指定的开发基线开始。两条分支线分别记录提交，不交叉合并不同仓库。用户也可只选择其中一种工作模式。

创建前检查工作区，未提交改动先确定归属，不能直接切换导致混入或丢失。必要时使用独立 worktree；不自动 stash、提交、推送或重写历史。新增分支也不改变后续操作的授权边界。

每版先交付一份可操作清单：本版目标和非目标、上游阅读顺序及符号、本地成员保留/新增/延后表、每一步的修改文件及验收方法、相较上游的明确差异。指导模式下一次讲解一个可验证步骤，由用户实现；代实现模式仅在用户明确要求时执行。不要在一个步骤中同时要求补完多个新模块。

验证按版本风险选择聚焦测试，放在 `src/harness/tests/`，应用组装测试归 app。根目录已声明的检查入口包括 `pnpm run typecheck`、`pnpm run build` 和 `pnpm run build:tests`；具体聚焦测试命令在测试文件实际建立后提供。已有无关错误须记录，不把局部通过说成全仓通过；版本涉及的代码必须通过对应检查，不通过不得合并。

问题修复与新能力开发分清范围：事先列出必须处理的已知问题，获得确认后改动；尤其修改 Session 既有方法时明确指出影响。每版结束记录实际通过的检查、剩余限制及基线提交，供下一版使用。
