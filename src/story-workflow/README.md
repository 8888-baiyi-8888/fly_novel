# 故事级工作流业务模块

`workflow.ts` 负责故事推进顺序。继续时由 `progress.ts` 核对暂停位置，演绎时由 `simulation.ts` 处理模拟器和提前汇报。数据定义和文件读写分别由 `types.ts` 和 `store.ts` 维护。

当前模块管理单轮初步事件规划：调用方提供任务、已知事实和发展方向，导演返回事件初步安排或无可推进事件及原因。程序生成独立运行 ID 与事件 ID；计划不代表事件已发生，也不更新世界状态。导演和模型由[应用入口](../app/story-workflow.ts)装配。

### 读取父子故事

`readStory({ planRoot, collaborationRoot, protectedRoots }, planId, storyId?)` 查询多层推进记录。省略故事 ID 时返回根故事。结果包含保存的任务节点 `node`、直接上级 `parent`、从零开始的 `siblingIndex`、当前演绎或拆分安排 `decision`、可核实的回报 `result`，以及按拆分顺序排列、补充项在末尾的 `children`。根故事的上级和同层位置均为 `null`。

子项状态为 `planned`（安排存在，尚无推进决定或节点）、`cancelled`（上级已取消）、`incomplete`（开始推进但结算证据不足）或 `completed`（回报及其所需证据存在）。拆分故事核对评估与回报，直接演绎故事核对模拟经过与回报。目标节点缺失时可从上级的子项列表核查其安排。目标或上级记录缺失、身份或归属冲突、格式无效时抛错。该入口只检查所查故事的上级链及直接子项，不消费暂停批次。

### 保存和读取场景设置

从[应用入口](../app/story-workflow.ts)调用 `createStoryScene(options, planId, storyId, { order, situation, preparation })`。目录配置沿用故事查询，故事必须已保存直接演绎决定。顺序使用故事内的正安全整数，处境与准备信息必填。程序按运行 ID、故事 ID 和顺序生成 `sceneId`，以 `<sceneId>.setup.scene.json` 在协作目录独占创建版本 1 设置。同一故事内重复使用同一顺序会占用同一场景身份，后一次创建抛错并保留原记录。

`readStoryScene(options, planId, storyId, sceneId)` 按身份读取并核对归属。`listStoryScenes(options, planId, storyId)` 按顺序升序返回该故事的场景。读取会拒绝身份、顺序或格式与文件不一致的记录。只有设置时返回 `pending`。旧运行没有设置文件时列表为空，旧模拟经过和回报仍通过故事记录读取。

### 保存模拟结果并形成故事回报

多层推进将当前 `runId` 和 `storyId` 提供给可信模拟器，供它调用 `createStoryScene` 保存设置，再使用当前调用的 `recordSceneResult(sceneId, { status, simulation })` 保存结果。模拟器应等待每次写入，`simulation` 使用已有的模拟经过格式，包含摘要、变化、未解决事项和依据。只有当前子故事已保存设置的场景可独占写入 `<sceneId>.result.scene.json`。结果文件使用版本 1，保存后由场景查询返回原始记录及状态。状态 `completed` 表示正常结束，`terminated` 表示提前终止且已结算截至终止的经过，`unresolved` 表示结果未决且需要核查。每个场景只写一次，结果保存后可继续处理同一故事的其他场景。

模拟器返回后，程序重读该故事的所有设置和结果。存在待演绎或未决场景时停止形成回报。全部场景结算后，导演获得各场景的模拟原文和模拟器返回的故事级汇总。故事级模拟记录写入后，创建入口拒绝追加场景。场景结果和故事回报分别保存，模型回报失败时仍可单独读取原始场景。

含场景的直接演绎回报使用版本 2，在 `sceneIds` 中保存按顺序排列的引用。调用方可用 `readStory` 的 `result.sceneIds` 逐项调用 `readStoryScene`。每次写读回报时核对场景归属、顺序和结算证据。携带版本 2 回报的暂停快照也使用版本 2，现有版本 1 的回报和暂停文件继续可读。没有场景记录的模拟流程仍按原格式保存。故事级批次计数仍在子故事回报保存且重读后发生。

### 核查运行进度

`inspectStoryProgress(options, planId)` 只读重查规划、推进树和最新批次，目录参数与 `readStory` 一致。返回 `not-started` 表示只有规划，`paused` 表示有已核验且未消费的正常暂停，`needs-review` 表示运行尚无可用暂停或存在证据缺口，`completed` 表示根故事及此前推进结果均已核对。运行中的查询可能读到部分写入，结果仅反映本次观察。

结果按可用证据返回当前待核查故事 `current`、可定位的下一项 `next`、当前故事的场景 `scenes`、已确认回报 `confirmed` 和最新批次号 `batch`。其中 `completedCount` 是本轮已核实的直接演绎数量，同一个故事的多个场景只计一次，提前终止的故事不计。可以通过已确认回报中的 `sceneIds` 重读场景。在 `needs-review` 状态下按 `reason` 核对已有记录，可能已经保存了个别场景结果，但仍缺故事回报。Session 内容不参与进度判定。

`paused` 和 `review-ready` 提供可继续的批次。查询为只读，`continueStoryTree` 会再次核对推进栈、已结算后代的场景与回报及下一项是否已开始，再独占领取推进位置。缺失证据、存储中已有后续推进文件或领取后未形成新暂停时，保留现有记录供核查。

### 统一运行记录

统一入口在独立记录根保存格式 1 运行意图、稳定规划和根故事身份及经过校验的步骤输出。导演派生输出绑定当时的输入摘要。角色首回合、地图采纳、场景结束和商队操作使用自身稳定标识，并在恢复时复查原业务证据。故事树仍保留独立的规划、拆分、回报、审阅与暂停格式。

恢复先核对运行归属和当前版本。程序沿已经证实的父子推进前缀定位缺口。已有结果时补齐派生报告或引用，角色已领取但没有可确认的响应时保持待核查。无角色领取的已保存调度可以按相同参与身份补做。排期接管沿用原场景领取，尚未确定的作用不释放给依赖方。商队状态使用原授权、期望版本和操作回执判断是否继续应用。具体应用入口见[故事完整运行与恢复](../app/README.md#故事完整运行与恢复)。

### 世界时间记录

世界时间使用从获准起点计量的整数分钟。排期时间窗和场景占用都使用半开区间。世界排期独立于故事进度文件，格式 1 保存单一活动时间窗、角色起始位置、可信直连路线、资源、依赖及每个场景的领取与结算。不可变的修订由上一版本摘要连接。活动窗批准后仍可修订未开始的场景，变更需保留已领取或结算的排期及其前置范围。前窗所有场景结算或明确取消后，下一窗承接已核实的角色位置和共享状态。

同一角色不能占用重叠时段。后续场景重读前场结算位置，以路线方向、通行时间、条件和版本核对可达性。相同状态的读取可以重叠，读写或写写安排按世界时间串行并核对前置。领取固定准入状态和路线版本。商队变化需要引用实际回执，按结算时刻形成可用于后续场景的版本。缺少前置或卡在部分写入时，相关场景保留等待原因。

角色经历按已结算角色参与、感知及行动证据重建。来源版本、角色和目标场景共同限定传递范围。应用操作见[世界时间与并行故事](../app/README.md#世界时间与并行故事)。旧故事、审阅和暂停原有格式可独立重读。

### 父故事安排审阅记录

启用审阅的轮次使用格式 4 保存推进栈。初步拆分与首个子项决定之间，审阅批次还包含版本化快照，绑定父故事、初步子项、原规划摘要和当时采用的世界状态。稳定选项只排列本层初步子项，需要满足应用给定的先后约束。对应的决定文件保存用户选择、取消或超时采用，并用审阅 ID 和所见版本绑定该快照。限时手选和取消均要求当前时间早于截止时间，超时决定保存原期限及实际结算时间。

保存的决定与推进领取记录各有独占写入点。采用后，`readStory` 通过 `adoptedReview` 返回版本和选项引用，按采用顺序展示子项，并保留原拆分的 `decision`。之后的暂停核对推进栈中的引用与实际采用顺序。若同一可信商队状态升版，应用可保存带新版本和期限的审阅批次。旧批次仍可重读。推进中遇到设定的单次补充安排时，按已有流程处理。

进度查询使用 `awaiting-review` 表示等待决定，`review-ready` 表示已保存可继续的选项决定，`review-cancelled` 表示明确取消，`needs-review` 表示证据缺口或已获准推进但结果待核查。旧格式 1 至 3 继续按其回报和暂停规则读取。操作及选项装配见[应用入口](../app/README.md#父故事安排审阅)。

`PlanStore` 在可信应用选择的现有真实目录中，以运行 UUID 为文件名独占创建版本 1 JSON，保存输入和规划结果。调用方必须提供全部需要隔离的业务根和 Session 根；记录目录不得与它们重叠。未知版本、重复键、损坏、无效身份和不符合格式的记录拒绝读取并保留原文件；不自动迁移其他格式。创建失败或结果不明时报告运行 ID，调用方须核查原文件，不盲目重试或覆盖。单个文件只创建不更新，不承诺跨文件事务、跨进程锁或断电持久性；路径检查不能防止恶意并发替换及硬链接。

`CollaborationStore` 在与规划根隔离的可信目录中，按规划 ID 和事件 ID 保存独占尝试记录、模拟经过和最终协作结果，格式均为版本 1。一次协作仅处理一个初步事件：程序创建父故事与协作身份，并将所选事件作为子故事；最终记录保留所用完整规划、父导演任务、子导演安排、明确标记的模拟经过、子导演回报和父导演接收结果。重新读取时核对尝试、经过和结果的身份及内容；未知版本、损坏或不一致拒绝读取并保留原文件。

调用导演或模拟器前先独占创建尝试记录；同一规划的同一事件已有尝试时拒绝再次执行。模拟经过在回报前单独保存；失败、取消或结果不明时保留已有记录，调用方可读取模拟经过并核查，但不能自动重试。完成结果与尝试和经过是多个文件，不声称跨文件原子、跨进程锁或断电持久性；删除占用、重新尝试及完整恢复不属于本阶段。调用方保证记录根与世界、Session 和其他业务根隔离。

`runStorySiblings` 顺序处理一轮规划中的事件，为它们分配共同的父故事身份。每一项开始前，父导演依据已保存的模拟回报决定继续、调整或取消，程序保存决定及原因；继续或调整时再由父导演结合已有回报制定任务。每次判断和协作使用独立导演实例，相关上下文由程序传递，不依赖实例持续驻留。取消的事件不演绎；任何失败或结果不明都会停止后续处理。

兄弟推进新增版本 1 的父故事身份记录和事件决定记录，不修改已有版本 1 规划、模拟和协作文件。每轮独占创建父故事身份，同一规划不能自动重新开始；失败后保留已有记录以供核查，目前不提供自动恢复或重试。`readStorySiblingDecision` 可读取决定并核对身份。调用方仍须保证单可信写入进程，记录不构成跨文件事务。

`runStoryTree` 使用程序维护的栈逐层推进初步事件：父导演依据本层已完成回报决定当前子故事，子导演判断继续拆分还是直接模拟。拆分后先按顺序处理下级，再形成回报并交给直接上级；每次导演调用后释放实例，不要求上级持续等待。故事节点、拆分安排、逐项决定、模拟经过和回报分别独占保存。子节点要求上级已经存在，节点本身不代表演绎完成。取消或失败时停止推进并保留已有记录，当前不自动恢复或重试；模型输出和模拟结果不是实际世界事实。

多层推进时，父导演根据已经保存的子故事回报评估目标。程序允许每个父故事最多安排一个补充子故事，补充安排保存后沿用原有推进流程。目标仍未达成时，最终评估记录调整内容和未解决事项，历史记录保留。条件变化时，父导演也可以提前终止父故事，剩余子故事不再启动。补充安排和最终评估作为独立的版本 1 记录保存，父故事的结果回报沿用原记录。

多层推进的每批数量默认是 5。直接演绎的子故事在回报保存并重读成功后计入本批。拆分、取消和父故事评估均不占用数量。用完数量后，程序仍会结算已经处理完下级的父故事，并在即将启动下一项时保存暂停记录。继续时核对原规划、父子关系、决定及结果，再独占消费该暂停批次。失败或取消时保留已有记录供核查。

在多层模拟演绎中，重大情况可使当前故事在 `reportEarly` 处等待。程序请子导演整理提前回报，保存后，依据已记录的父子关系请直接上级决定继续、调整或终止。程序先保存决定，再返回给模拟器。同一子故事中的相同通知只处理一次，内容冲突或并发提交不同通知会停止当前故事。提前汇报和上级决定使用独立的版本 1 记录。上级失败或取消后保留已有记录供核查。终止时保存至终止为止的模拟经过和单独形成的最终回报，并记录终止原因。该子故事不增加本批完成数。

整轮结束以根故事结果和一致的评估记录为凭据。正常的按量暂停使用独立的暂停记录，结果不明的批次只保留已写入的数据供核查。用户选择继续演化后，应用层可以核查上一轮结果并提交更新后的资料形成新计划。调用方区分新一轮的已知事实与本轮模拟经过。

本阶段运行在调用方提供的模拟器上。导演实例按调用创建并释放，程序使用业务记录推进故事和核对恢复位置。

### 曲水城整轮验证

在仓库根目录执行 `pnpm run build:tests`，再执行 `node --test .test-dist/story-workflow/tests/round.test.js`。该用例用固定模型替身和模拟器运行三批，并在下一轮验证无场景回报的兼容路径。运行使用临时记录目录，测试完成后清理。见[曲水城整轮用例](tests/round.test.ts)。

从规划 ID 调用 `readStoryPlan` 重读初步计划，并用 `readStory` 获取根故事和下级身份。以规划 ID 和目标最小故事 ID 调用 `readStory` 读取回报，再根据 `sceneIds` 使用 `readStoryScene` 重读处境、准备和原始模拟经过。轮次暂停时用 `inspectStoryProgress` 找到批次和下一项，整轮结束后用 `readStoryRoundResult` 获取根回报及评估。

在仓库根目录执行 `pnpm run story-workflow-debug` 可用本机 DeepSeek 配置测试真实导演回复。调试入口把曲水城合成资料发送给模型，使用模拟器提供演绎经过，并把记录保存在终端显示的 `tmp/story-workflow-debug-*` 目录。也可通过 `pnpm run story-workflow-debug qwen` 选择本机已配置的 Qwen。 [调试入口](../app/story-workflow-debug.ts)
### 世界绑定规划

`prepareStoryWorldInput` 将历史交付、选定的当前目录正文和可信固定输入组成同一轮的资料快照。每项保存资料类别、来源、版本、正文和摘要。规划格式 2 保存该快照，格式 1 保留独立规划。读取重算资料摘要，单次规划的大小限制为 1 MiB。父子导演与分批继续沿用规划保存的正文和范围。应用如要采用变化后的来源，须读取并形成新一轮输入。

包含地图需求的直接演绎决定使用格式 2，其场景设置也使用格式 2，保存交付身份、地图核查引用和摘要，以及提案采纳人、理由和提案摘要。未采用提案的已覆盖场景只保存核查依据。场景读取验证核查及所采纳提案，模拟结算要求已经保存可核对的场景。旧格式 1 可继续重读。

### 角色参与记录

角色参与另存格式 1 的请求占用与结果。请求保存世界、运行、故事、场景、角色与参与 ID、档案和配置版本及实际使用的认知片段。结果绑定请求摘要并引用同一角色的历史参与，保存结构化响应或失败终态。缺少结果时报告待核查。重读已有请求不会重复运行模型，显式重试需要新的受验参与请求。角色参与记录可随场景重读，场景仍按其独立结果结算。

### 场景互动记录

格式 1 的互动事件按场景连续编号，引用场景设置摘要和已完成的参与响应。事件保留可供场景处理的发言、行动尝试及当时的参与者与感知条件。角色私有字段继续由参与记录管理。已有场景可在没有互动记录时按原格式读取。

每个事件的感知与下一位选择合并保存，调度按事件独占取得，绑定决定摘要和实际使用的观察引用。没有角色参与文件或只有参与占用的调度留待核查，重读时不重复启动。未选角色的感知仍可追溯，获准的旧观察可作为其后续轮次输入。

行动记录把尝试、规则判断和导演确认的结果分开。已经确认且可观察的部分可作为感知来源。场景结算重查事件、感知和角色调度链，以结果格式 2 绑定其摘要。没有互动的旧场景仍使用结果格式 1。等待或待核查可保存为未决结果，未决场景保持待处理。

### 已采用的场景事件

`openStoryEvents` 显式采用所选世界与运行中已结算的互动场景。同一场景只保存一次格式 1 的事件，事件引用场景结果及互动摘要，按序保存发言、行动判断和未决事项。重读时回查场景及原始证据。旧场景结果、未结算场景及未明确采用的记录继续作为原有类型读取。

### 商队运行状态

状态根独立于世界正文、交付、场景和 Session。商队从带来源的版本 0「已抵达」迁移到版本 1「已安置等候」。获准操作冻结目标、事件、预期版本和授权。最终状态文件独占发布，嵌入操作和上版摘要。回执由当前状态与事件重读重建，未写、冲突与无法核查分别处理。此状态仅支持单个目标及首次安置迁移。

启用 `worldProgress` 的多层运行使用可信状态及已采用事件形成回报。回报格式 3 保存证据，并按场景重核实际行动。父导演的评估与后续任务读取核实过的当前状态。变化清单由程序根据已应用状态生成。携带格式 3 回报的暂停要求使用同一世界商队状态来源继续，旧回报及暂停仍可读取。
